## 2. 对 NapCat 日志归属建议的落实

示例日志中的“安心的理想(3111236810)”已经表达了发送者身份；生产程序使用对应事件的 `user_id=3111236810`，与 `group_id=912621429` 组合查询当前成员任务。显示昵称只作展示，模型不从日志正文猜 QQ 号。

这种方式支持本人改名、同昵称不同成员、群内他人插话和重启后的任务接续。事件缺少必要身份字段时拒绝处理，不用显示名补猜身份。粘贴别人的日志不会获得对方任务权限。

未 @ 消息需要 NapCat 正常上报。排查顺序是：NapCat 收到该消息 → Python HTTP 接收事件 → 允许群校验 → 入 Inbox → 是否匹配该用户任务 → 工具及 Outbox。控制台日志只证明第一步，不能替代其余步骤。

目前按任务类型、待补字段和 30 分钟有效期选择接续，不会把该用户之后所有群聊都当 Bot 指令。明确的旅行请求及控制命令可直接触发；普通闲聊保持安静。

## 3. 一致性和恢复

- SQLite 持久保存 Task、Inbox、Outbox、图片检查点、提醒及行程版本。接入先保存输入，再由后台执行；同一用户保持顺序，定时只读任务使用独立通道。
- 幂等键防止相同事件重复创建；提交的回复可在崩溃后恢复，无需再次让模型猜结果。取消、超时及失去租约后，旧线程无法提交业务修改。
- 行程改动影响提醒时先预览，确认时重查规则和版本；行程与提醒同事务更新。用户取消的提醒不会重建，人工改过的时刻保留。
- 规则监测有明确截止时间，默认每小时核查，支持 15 分钟至 24 小时。无变化不通知；首次读取失败、恢复或规则语义变化才通知。停止监测使旧轮次失效。
- 单轮最多两个独立旅行只读工具并行，写操作仍按顺序。模型客户端并发、每事件调用数和估计 token 预算受限；实际 usage 单独记账。估计量不是精确计费上限。
- 文字提醒及所支持的时效查询超过 24 小时补发窗口后标记错过/取消；旧预约提醒过了参观日不再发送。不能把长期离线后的旧天气包装成当前天气。

## 6. 需要你进行的 QQ 验收

先在 VS Code 中停止旧 Python Bot 服务，保留 NapCat 登录；在 `(agent)` 终端启动更新代码，确保只有一个 Python 实例处理该群：

```powershell
conda activate agent
cd E:\Agent\travel_agent
python -m uvicorn adapters.onebot_app:create_runtime_app --factory --host 127.0.0.1 --port 8000
```

上述端口须与 NapCat 已配置的 HTTP 上报目标一致；若原来使用其他监听端口，沿用原端口。无需重新登录 QQ，也不要运行用于官方 QQ Bot 的 `run_bot.py` 来替代 OneBot 服务。

| 步骤 | QQ 输入/操作 | 应看到什么 |
| --- | --- | --- |
| 1 | 甲 `@彼岸 现在天气怎么样`；乙直接发“武汉”；甲直接发“武汉” | Bot 追问城市；乙不接续甲的任务；甲不必再次 @ 即得到天气 |
| 2 | 两人用相同昵称重复步骤1；甲改昵称后再补城市 | 始终按 QQ 号归属，不串用户、不因改名丢任务 |
| 3 | 甲 `@彼岸 明天提醒我抢高铁票` → “上午十点” | 不索取攻略图或车次，回执显示完整日期、10:00、原群接收；“查看我的提醒”可查 |
| 4 | `@彼岸 1分钟后提醒我检查测试结果` | 一分钟以后实际收到群内 @ 提醒；默认扫描约60秒，加排队及网络延迟，不承诺到秒 |
| 5 | `@彼岸 1分钟后告诉我武汉当前天气` | 创建时只确认计划；到期才收到带原定/实际执行时间的查询结果 |
| 6 | 规划武汉3天行程，指定开始日及湖北省博物馆并提醒预约 → 按提示核对 → 改开始日期 | 行程可查看和修改；影响提醒时先预览，确认后日期一致，另一成员不能修改 |
| 7 | `@彼岸 监测湖北省博物馆预约规则，到明天下午三点` → “查看规则监测” → “停止规则监测 W-实际编号” | 回执包含明确截止时刻；无变化不刷屏；停止后不再排后续轮次。真实页面何时变化无法人为保证 |
| 8 | 发起缺城市任务，重启 Python 后直接补城市；再测试引用本人 Bot 回复继续 | 有效任务能恢复，引用不突破用户归属；若失败记录两端消息 ID 与时间 |

使用测试群做提醒和重启验收，结束后取消测试提醒、定时查询及规则监测。不要用过去的演练日期创建任务；所有日期以实际消息时间为准。

如果未 @ 的消息仍无反应，先对照同一 `message_id` 的 NapCat 接收日志和 Python 接收/任务日志。只提供相关时间段、请求编号和现象即可定位；无需贴出 `.env`、token 或完整群历史。

## 7. 明确保留的后续范围

本轮交付为已接入能力的可靠首版，而非任意旅行要求都能自主完成。更多场馆的自动发现、复杂节假日适用性、反复/工作日提醒、票务库存与真实预订、消费账本和多人共同编辑，以及跨多个专用业务的一条消息执行，仍需独立设计和验收。

QQ 人工验收、Linux/容器运行、正式历史库替换未在本轮自动执行。已有代码和测试结果只能支持上述具体范围，不能替代这三类验证。
