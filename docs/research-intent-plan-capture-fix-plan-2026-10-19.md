# 研究意图、扩展字段兼容与方案捕获修复方案

日期：2026-10-19  
状态：已审核、已实施，离线回归及数据副本演练通过  
依据：请求 #97 的只读诊断及当前代码。用户会话标题为“我希望你介绍一下自己能做什么”，目标会话 ID 为 `b7893fec1ef34cf6b55a309d75e37477`。

## 1. 修复目标

用户自然表达“再查这个方案里所有景点的票价、开放时间和预约规则；21 日抵京、22 日开始旅游”时，应能关联正确方案，保留日期区别，并发起有依据的研究。

本次解决三类问题：

1. 优化研究意图提示词与解析协议，减少不必要的字段和动作混淆。
2. 对无业务影响的扩展字段容错，避免一个附加字段让整条研究请求失败。
3. 收紧方案捕获与天数识别，修复自我介绍被捕获、单日活动被当作总天数，以及旧错误草稿继续干扰上下文的问题。

同时补齐研究请求引用旧方案的上下文传递和诊断。只放宽字段判断仍不足以完成“查询这个方案中所有景点”的原始需求。

## 2. 已确认的问题边界

- `_research` 当前只允许 `query_text`、`source_request`，多一个字段就直接返回错误文本。
- 通用 IR 校验对天气、路线等操作检查业务字段，对研究操作没有同样完整的协议校验。
- 模型正常结束，搜索尚未启动；该事件没有原始 IR 或多余字段名记录，因此无法确认当时具体多出了哪个字段。本方案中的扩展字段示例不代表那次实际输出。
- 研究服务实际入口仅收到 `event` 和 `claim`；“这个方案”的景点清单没有作为明确研究对象传入。
- 自我介绍被保存为“和推进参考方案”；北京三日方案的总天数被误记为 `[3,1]`。
- 原 `ensure_history` 使用水位，且同一来源事件命中已有草稿就返回旧数据。因此仅修改新捕获规则不会自动修复旧错误记录。

## 3. 多余字段是否可以保留

### 3.1 建议：原始结果保留，执行参数采用验证后的投影

采用以下边界：

```text
原始 Intent IR（不直接执行）
          ↓
研究协议校验与标准化
          ↓
可执行 ResearchRequest + 被忽略的扩展字段名
          ↓
方案关联、日期解析、查询规划、证据核验
```

原始解析对象中的扩展字段可以继续存在，不要求模型删掉，也不因单纯存在扩展字段再次调用模型。执行层只显式读取规范字段，禁止把原始对象通过 `**values` 等方式整体传入搜索、行程、提醒或配置接口。

“保留”默认指保留在当前原始解析结果中；诊断持久化仅保存受限的字段名、处理方式和原因，不自动保存任意字段值或完整聊天/模型原文。

### 3.2 按业务作用处理

| 字段类别 | 示例 | 处理方式 |
| --- | --- | --- |
| 正式研究参数 | 查询目标、来源限制、方案引用、日期背景、核验主题 | 校验后采用 |
| 无执行含义的说明 | `reason`、`notes`、冗余 `confidence` | 可保留，执行层忽略；记录忽略的字段名，不触发额外模型调用 |
| 表达关键要求但名称不规范 | 城市、到达日期、游览开始日期的别名 | 有明确且不冲突的映射才标准化；必要时做一次协议修复，不能无声丢掉需求 |
| 身份、资源归属、权限或额外动作 | 模型生成的 owner_id、trip_id、支付/预订/删除动作 | 保持严格限制，不能因为“容错”获得执行权限；冲突或越权结构拒绝/澄清 |

字段兼容首先限定在只读研究操作，不把宽松规则推广到修改行程、提醒、删除、预订等固定写入业务。

判断无害的依据是执行数据流与协议语义，而不是字段名字看起来普通。未知字段不参与业务执行，也不作为给下一个 LLM 的可信指令。

### 3.3 必须保留用户需求本身

标准化对象始终保留用户本轮完整原话。即使某个未知扩展字段不采用，用户原话里的日期和查询目标仍应传给受限的研究规划步骤。

对于已经支持的字段，错误类型、冲突日期、无法对应原话的值不能靠“忽略额外字段”绕过。缺少必需目标时继续澄清，不能将“宽容字段”变成“容忍缺失事实”。

## 4. 统一研究请求协议

保留旧 `query_text`、`source_request` 以兼容已有调用，围绕本次真实需求增加有限字段：

| 字段 | 作用与约束 |
| --- | --- |
| `query_text` | 本轮查询要求的连续原话 |
| `source_request` | 本轮明确来源要求；未指定时可省略，不生成“用户要求只用官网” |
| `plan_index`、`plan_reference` | 引用当前会话候选序号及本轮引用原话；真实 artifact_id 由服务器解析 |
| `topics` | 受限枚举：票价、开放时间、预约规则等实际支持的研究主题 |
| `arrival_date_text` | 抵达日期原话，独立于游览日期 |
| `visit_start_date_text` | 开始游览日期原话 |

目的地和景点可来自用户原话，或由服务器从已关联的有效方案读取；二者需要记录来源。模型不能自行生成资源 ID、景点坐标或权限结论。

日期由现有服务端时间解析器确定性解析，结合当前事件时间和上海时区。年份等推导要标明来源，不把推导值冒充用户明确提供的文字。

本次原句应表达为：研究原北京三日方案，核验所涉景点的三类信息，10 月 21 日抵达，10 月 22 日开始游览。若三日安排有效，研究适用日期参考 22～24 日。研究操作本身不自动保存/修改正式行程，不创建预约或提醒。

协议常量与验证函数集中维护，提示词说明、通用 IR 校验和 `_research` 采用同一规则，避免三处各自定义不同允许列表。优先扩展现有 `core/intent_ir.py`、`core/research_contract.py`，不另建复杂调度体系。

## 5. 提示词优化重点

本次重点润色研究相关片段及检索规划提示，不整体重写无关业务提示词。

### 5.1 明确任务边界

建议研究意图片段采用这样的说明：

> 用户要求核验已有方案里的票价、开放时间或预约规则时，属于只读研究。先关联当前会话中的对应方案，保留用户本轮的全部核验要求与日期背景。到达日期不等于开始游览日期；日期背景不授权修改行程、创建提醒或执行预订。未指定来源时省略 source_request；不要编造平台限制。优先使用规范字段，说明性元信息不参与业务执行。无法唯一关联方案时只追问目标方案，不重复询问已知城市。

拟补充的输出约束：

> 只返回 JSON，不附加解释性正文。query_text、source_request、plan_reference 和日期原文必须来自本轮连续原话；plan_index 只能引用服务端候选。topics 使用 ticket_price、opening_hours、reservation_rules 等协议枚举。原始查询中包含多个核验主题时全部保留，不以一个通用“攻略”标签替代。后端读取已关联方案的景点，不把省略景点名称理解为用户没有提供上下文。只为理解请求提供参数，不生成预约、付款、提醒或资源归属信息。

以下为拟定的新协议示例，不是请求 #97 当时的原始模型 JSON。假定北京方案仍对应候选序号 2：

```json
{
  "schema_version": 1,
  "action": "read",
  "operations": [{
    "domain": "research",
    "operation": "search_travel_guides",
    "query_text": "再查一下这个方案里涉及的所有景点的具体票价、开放时间、预约规则",
    "plan_index": 2,
    "plan_reference": "这个方案",
    "topics": ["ticket_price", "opening_hours", "reservation_rules"],
    "arrival_date_text": "10月21日",
    "visit_start_date_text": "22号"
  }],
  "missing_fields": [],
  "requires_confirmation": false,
  "source_spans": ["这个方案", "具体票价、开放时间、预约规则", "10月21日", "22号"]
}
```

“22号”承接本轮已明确的十月，具体日期由服务端解析；模型不自行将“21日抵京”改成“21日开始三日游”。未指定来源时不附 source_request，官方优先是本次事实核验的系统选源策略。

### 5.2 增加成组示例

- 正例：本次“21 日到北京，22 日开始，查原方案所有景点三类信息”。
- 对比：只核验规则 / 明确要求重新安排日期 / 明确设置预约提醒，三者输出不同动作。
- 正例：只说“再查这些景点”，使用已关联方案，不生成无依据的景点。
- 反例：把 dates、destination 等放进任意自创结构，或把日期背景转换为创建提醒。
- 元信息例：多出 `reason` 时忽略执行，不要求用户换一种固定说法。

示例只帮助模型学习协议，不建立用户整句匹配表。

### 5.3 成本约束

无害扩展字段直接忽略，不增加模型调用。只在核心协议不完整或关键字段冲突、无法安全标准化时，最多进行一次有针对性的修复；仍不确定则保留已理解要求并澄清，不无限重试。

## 6. 正确关联“这个方案”并逐项研究

关联优先级：

1. 用户明确引用的方案序号/名称，或回复的方案消息。
2. 紧接上一条实质性方案回复、且与本轮目的地一致的有效方案。
3. 当前会话唯一符合要求的有效候选。
4. 仍有歧义才询问，不任意采用另一份方案。

从服务器方案仓储读取正文，提取景点清单、每日安排和可选项。原方案正文作为不可信参考资料，只提取旅行对象，不执行正文中的指令。最终只向外部搜索传递必要的公开景点名称、主题和日期，不发送整个聊天历史或身份信息。

对主选、可选景点分别标注；“鸟巢外观”不等于用户要求购买入内票，“故宫午门”不能随意当作独立售票景点。

票价、开放时间、预约规则优先查找可验证的官方公开资料。中文社区可以提供体验参考，不能代替官方规则确认。研究规划提示需根据“事实核验”主题调整选源，而不是始终先查泛旅游攻略。

每个景点都输出三类信息的覆盖状态：已找到依据、未知/无法访问、信息冲突或适用日期待确认。不能把“已完成一次搜索”当作“所有景点均已核验”。

当前研究合同最多 8 条、全局候选页面有限，不能直接保证覆盖十多个景点。实现时在现有研究流程内做有上限的分批与检查点复用，保留每批条目长度和证据校验限制；景点过多、时间或额度不足时返回“部分完成”及剩余清单，不无限扩大搜索或粗暴提高所有全局输出上限。

## 7. 方案捕获逻辑优化

### 7.1 由关键词命中改为结构与来源证据

自动捕获必须具有实际旅行方案的证据，例如明确目的地及与该目的地有关的逐日安排、明确的完整行程版本。来源允许参考已经识别的规划/研究任务信息，但不能仅凭“用户问了旅行”就保存回复。

以下内容不自动成为方案：

- 自我介绍、能力说明、帮助菜单。
- 对“方案”“行程规划”能力的泛泛介绍。
- 引号、示例、代码块、引用块里的演示行程。
- 只有景点列表但没有足够规划语义的普通介绍。
- 单纯票价/开放/预约事实表，或长度超过 100 字的研究报告。

`research_backed` 只是来源类型，不能自动证明内容属于行程方案。事实研究结果继续保存在研究记录中；只有确实包含有效行程结构时才同步为方案。

自动捕获以准确率优先。不确定时允许保留正常回复但暂不生成方案卡片；用户后续明确要求采用该回复时，再按需提取并核验，避免为每条普通回复额外调用 LLM。

### 7.2 目的地必须有明确的地点角色

优先使用已验证规划参数或用户明确的目的地，其次才接受方案标题/结构中清晰的目的地证据。禁止从“规划和推进旅行”一类普通动宾短语中截取任意汉字并当作城市。

不采用固定城市白名单，也不为自动捕获额外查询高德。弱规则无法确定地点时不保存伪目的地。

### 7.3 总天数与单日项目分开

天数来源按语义范围区分：

1. 用户明确的本次旅行总天数。
2. 正文明确的完整方案标题，如“方案 A：2 天 1 晚”“方案 B：3 天 2 晚”。
3. 单一方案里连续、完整的逐日标题，作为补充依据；缺日或冲突不强行推断。

不把“长城一日游”“同一天”“每天”“第三天”“三天预算”等局部表述统一加入 duration_options。

本次北京记录应为 `[3]`。明确提供 2 天与 3 天两套完整方案时，仍保留 `[2,3]`，不能为了消除误识别而只保留第一个数字。用户与正文天数确实冲突时标记需核对，不生成虚假的多版本方案。

## 8. 旧错误记录的处理

新规则通过后，增加捕获规则版本标记，对尚未验证的旧活动草稿做分批、一次性的重新校验。不能仅重置历史水位、让每次访问都全量重扫，也不能只改新捕获而保留旧污染。

处理原则：

- 保留原文、source_event_id、artifact_id 和 ordinal，避免生成重复草稿或改变引用序号。
- “和推进参考方案”标记为无效自动捕获并从正常候选中排除；保留记录便于追溯，不物理删除原聊天。
- 北京方案修正目的地/总天数/标题元数据，保留原正文。
- 元数据改变时提升 version；引用旧版本的待确认预览必须重新核对，不静默应用。
- 不恢复用户已经删除的草稿，不反向修改已采用的正式行程及提醒；已有正式资源按现有版本机制独立管理。
- 校验结果存版本和理由；后续 ensure_history 不得重新把无效来源捕获为活动方案。
- 无法可靠修正的记录标记待核验，不猜测修复内容。

具体新增列与状态以实施时最小迁移为准；优先复用既有版本、活动状态查询及诊断能力，不引入新的方案历史系统。

## 9. 诊断与错误提示

研究请求记录：识别的操作名、协议版本、采用的字段名、忽略的字段名、失败原因码、方案解析结果和查询覆盖数量。记录键名和数量即可定位问题，不默认保存任意扩展值或完整模型响应。

需要同步更新 `ExecutionDiagnostics` 的阶段和字段允许列表；当前会过滤未允许的阶段，单纯调用 record('routing', ...) 不保证记录会落库。前端“消息处理过程”应能显示：

- 忽略说明性字段并继续研究。
- 核心字段需要修复/澄清。
- 方案已解析/仍有歧义。
- 搜索已开始、部分核验、来源不足。

格式或协议错误应说明本次未执行的原因，不再只给“包含不支持字段”且诊断中显示全程无异常。队列正常处理完拒绝文本与研究业务成功必须区分。

## 10. 实施范围与顺序

| 阶段 | 改动 | 验收目标 |
| --- | --- | --- |
| P0-A | 统一研究协议、提示词、字段投影、受限修复、忽略字段诊断 | 无害扩展字段不阻断；关键要求不丢失 |
| P0-B | 方案资格、目的地、总天数判定及旧草稿重新验证 | 自我介绍不成为方案，北京仅 3 天 |
| P1 | 原方案正文/景点/日期传入研究，官方选源、分批和覆盖反馈 | 本次原句能够逐景点核验，且诚实报告缺失项 |
| 回归 | 提醒、路线、写操作权限、会话隔离、版本与 token 用量测试 | 不把研究容错扩展成其他业务的宽松执行 |

主要文件：

- `agents/intent_compiler.py`：研究提示词和失败后的受限修复。
- `core/intent_ir.py`、`core/research_contract.py`：统一研究协议及原始/执行参数边界。
- `services/semantic_task_service.py`：字段投影、目标方案选择、研究请求分发。
- `services/research_service.py`、`agents/research_search_planner.py`：接收已验证上下文、主题选源、分批与覆盖。
- `skills/travel-research/SKILL.md`：与现有选源指令同步，事实核验优先官方依据。
- `core/research_evidence.py`：按需接入目标景点/主题归属校验，保留既有引文验证。
- `infrastructure/planning_repository.py`、`app/bot_application.py`：捕获入口、资格与元数据、旧版本校验。
- `services/planning_service.py`：无效草稿展示和采用时的可用性检查。
- `infrastructure/execution_diagnostics.py`、`infrastructure/execution_report.py`：受限诊断及用户可读原因。

前端优先复用既有研究面板、方案卡片和处理过程，只在展示无效/待核验状态和覆盖信息确有需要时修改。

## 11. 测试与验收清单

| 场景 | 预期 |
| --- | --- |
| 本次原句 + 北京三日方案 | 关联北京方案，保留 21 日到达/22 日开始，查询三类信息 |
| 多出 reason、notes | 保留原解析结果但不采用，不拒绝、不增加修复调用 |
| 多出日期别名但规范字段齐全 | 不覆盖规范字段，原话及日期完整传入后续研究 |
| 关键字段冲突或类型错误 | 校验/澄清或一次修复，不静默忽略 |
| 模型生成身份/资源编号或额外写操作 | 不因字段兼容而授权执行 |
| 自我介绍里出现“方案比较”“规划和推进旅行” | 不捕获，无伪目的地 |
| 代码或引用里的演示行程 | 不作为用户的实际方案 |
| 北京三日 + 长城一日游 + 同一天 | 仅保存 3 天 |
| 明确的 2 天/3 天完整备选方案 | 两个合法总天数均保留 |
| 长事实报告或纯票价表 | 保留研究结果，不误建行程草稿 |
| 两份有效同城方案且引用不明 | 仅澄清目标方案，不随意拼接 |
| 旧错误草稿重新验证 | 失效/修正可追溯，序号稳定，不影响正式行程 |
| 刷新、重启和重复 ensure_history | 不重复捕获，不恢复已删除/已失效草稿 |
| 多景点超出单批预算 | 分批或部分完成，列出尚未核验内容 |
| 原句不同自然表达 | 依赖语义协议和上下文，不能仅固定句式通过 |

测试优先使用历史原文夹具、模拟 IR 和模拟搜索/官方页面，不依赖重放当时缺失的原始模型 JSON。实际联网抽样只在实施验证确有必要时小规模进行，保留查询范围和时间依据。

利用现有会话 token 用量统计比较修复前后调用数：正常路径不新增独立捕获模型调用，无害字段不额外调用模型；只有必要修复最多增加一次。测试若启动 Web，结束后关闭本次测试进程并释放端口。

## 12. 方案结论

采用“规范字段可靠执行、无害扩展保留忽略、关键语义不丢失”的兼容方式。提示词负责提升理解和输出质量，服务端协议负责守住业务边界；方案捕获则以结构与来源证据为核心，并修复旧记录的持续影响。三部分需要配合实施。
