# Web 会话及关联数据删除方案

日期：2026-09-18  
状态：2026-09-19 已审核并实施。结果见[交付记录](conversation-deletion-acceptance-2026-09-19.md)。本文保留原设计依据。

## 1. 结论与删除语义

可以实现。前端改动较小，后端影响中等偏高：需要协调会话数据、正在运行的同步线程、调度器、消息投递和文件系统，不能只删除会话列表记录。

推荐语义：用户确认删除后，服务端先在一个短事务中封禁该会话、撤销任务执行权、停止提醒与监测；随后清理数据库内容和附件文件。第一步成功后，该会话不能再收发消息、读取资料或新增业务结果。只有清理完成后才显示“删除完成”。

“立即停止使用”和“所有文件已经物理清理完毕”是两个不同状态。Windows 文件占用或进程崩溃可能延迟文件清理，界面必须如实显示“清理中／清理失败”，不能提前声称已经彻底删除。

本轮为永久删除功能，不设置保留原内容的回收站，不自动创建聊天备份；界面在提交前明确确认不可恢复。

## 2. 删除范围

| 对象 | 删除或停止内容 |
| --- | --- |
| 会话 | 标题、列表入口、会话元信息 |
| 聊天与记忆 | 用户消息、助手回复、对话记忆、待补充字段、待确认操作 |
| 资料 | 上传原件、已上传未发送附件、附件缓存、文档正文／摘要／切片／全文检索索引、图片识别结果与该会话专有副本 |
| 行程 | 当前行程、历史版本、关联修改预览 |
| 提醒 | 普通提醒、图片预约计划、预约项目及提醒实例；包括未到期、已排队和历史记录 |
| 定时能力 | 定时查询、规则监测、未来执行安排和已经入队的执行任务 |
| 后台任务 | 排队、执行、重试、附件处理、任务结果及事件状态 |
| 投递与通知 | 待投递消息、失败重试、该会话站内通知和已读状态 |
| 执行附属记录 | 可明确归属此会话的工具结果、幂等记录、消息引用、模型调用明细 |
| 浏览器状态 | 该会话草稿、当前选择、界面缓存和未提交的附件引用 |

保留：其他 Web 会话、QQ 数据、应用配置与密钥、本地登录会话、数据库结构和全局公共资源。`booking_policy_evidence` 当前按规则指纹共享，没有会话归属；不会整表删除。会话中的规则引用、行程快照及监测记录随会话删除，共享公共规则缓存独立管理。

相同图片可能被两个会话共用物理文件：删除本会话的引用及识别记录，但保留另一会话仍引用的文件。只有没有其他有效引用时才清理共享文件。

删除不撤回用户已另存的文件、既有备份、其他离线浏览器已经拿到的副本，或已发送给外部模型服务的请求。这也不等同于 SQLite、WAL 和磁盘介质的取证级安全擦除。

## 3. 当前代码中确认的影响点

1. `WebRepository.conversation()` 目前只检查记录存在；发送、上传、投递常在写事务之前检查，因此存在“检查通过后，会话被另一请求删除”的时间窗口。
2. `ExecutionScope` 与 `FencedConnection` 已有任务撤销保护，可以阻止失去租约的后台数据库写入，是可复用的基础。
3. `asyncio.to_thread` 中已启动的同步模型或文件操作，不会因取消 asyncio 等待就立即停止。
4. `ReservationImageService` 将图片写到 `images/<hash前缀>/<hash>.<扩展名>`，不同会话可以引用同一个物理文件；普通图片问答另有 `media/<scope哈希>/` 副本。
5. 文件写入与数据库记录不是同一事务。如果先删记录、稍后旧线程再写文件，会留下无法从会话查询的残留文件。
6. 单任务 `cancel` 会拒绝部分已准备回复或投递中的状态；会话删除不能简单循环调用现有“取消单任务”接口。
7. 数据有多种作用域表示：原始会话 ID、`web:<会话ID>`、job ID、事件 ID、提醒／监测 ID。仅按一个字段或事件字符串前缀删除会漏数据。
8. 部分外键没有级联删除，文档还有 FTS 触发器，预约数据也有触发器；必须按关联顺序清理并保持外键校验开启。

## 4. 推荐流程

### 4.1 前端确认

会话列表每项增加“更多 → 删除会话”，当前会话标题菜单也可删除。弹窗说明：

> 删除此会话及全部关联数据？
>
> 聊天记录、资料、行程和通知将被删除；正在执行的任务、未到期提醒、定时查询和规则监测将停止。此操作不可恢复。

可显示消息、附件、进行中任务与未到期提醒数量。数量只是当前预览；实际删除范围是提交时该会话的全部关联数据，不是固定数量的清单。

取消按钮默认可见，删除按钮明确标注“删除并停止关联任务”。不提供仅删除标题、却继续运行提醒的隐式行为。

### 4.2 第一阶段：建立不可恢复的删除边界

新增一个 Web 删除作业表，例如 `web_conversation_deletions`。以会话 ID 唯一记录状态、时间、清理清单和失败原因；成功后清除清理路径等细节，只留下最少的删除标记，避免重复请求和迟到任务将会话复活。

在 `BEGIN IMMEDIATE` 事务中：

1. 校验 Web 会话存在及本地访问权限；若已有删除作业，返回同一个作业。
2. 写入删除标记。该事务提交时刻是停止接收新业务的明确边界。
3. 撤销本会话执行、附件捕获和事件租约，取消尚未完成的任务。
4. 停用本会话普通提醒、预约提醒、定时查询、规则监测，终止其后续调度。
5. 将未完成的 Web Outbox 投递置为终止态并撤销投递权；不能仅跳过 future reminder 而漏掉已经排队的消息。
6. 保存关联主键、事件集合及文件候选清单，供后续清理与重启恢复使用。

事务成功后返回“删除已受理，清理中”。若这个事务失败，则不宣称删除成功，保持原状态。

所有会话读写入口都需要识别删除标记，包括消息、附件下载、上传登记、确认操作、任务查询、通知、上下文构建及重命名。已删除或正在删除的会话返回明确的终止状态，推荐使用 HTTP 410。

### 4.3 第二阶段：阻止迟到结果和文件发布

以下保护必须同时实现，不能只使用前端禁用按钮：

- 普通业务写入继续受原 `ExecutionScope` 约束；被撤销或删除的 job 不再具有写入权。
- Web 接收、上传登记和投递必须在实际写事务内重新检查会话是否可用，消除事务前检查的竞态。
- 调度器在生成 Inbox／Outbox 记录的写事务中检查会话状态和最新业务状态，不能使用删除前缓存的 active 记录重新排队。
- Worker 将“会话已删除”视为正常终止，不重新生成错误通知、重新插入处理事件，或因此重启整组后台任务而影响其他会话。
- 文件发布增加统一的生命周期保护：最终创建目录、落盘／重命名、登记引用必须与删除边界协调。现有图片与上传路径都接入，不能只有新上传接口受到保护。
- 可使用会话级的短临界区保护文件发布，配合持久化删除标记；模型和网络请求不在锁内执行。共享文件引用检查与删除使用一致的路径锁顺序，防止误删和死锁。

已发出的模型／高德请求可能仍返回，也可能已经计费。取消的可靠保证是它的迟到结果不能再写回会话、创建行程／提醒或投递通知；不能承诺撤回远端请求或立即结束底层同步线程。

### 4.4 第三阶段：清理业务内容与文件

删除协调器从已收集的关联集合出发，按外键顺序清理。主要覆盖：

- `web_requests`、`web_deliveries`、`web_uploads`；
- `conversation_turns`、`chat_messages`、`documents`、`document_chunks` 及对应 FTS；
- `travel_tasks`、`task_event_results`、`outbound_message_links`；
- `trips`、`trip_versions`；
- `personal_reminders`、`reminder_occurrences`；
- `reservation_workflows`、`reservation_images`、`reservation_plans`、`reservation_items`、`reservation_reminders`；
- `scheduled_queries`、`policy_watches`、`media_observations`；
- `inbox_jobs`、`inbox_assets`、`outbox_messages`、`event_tool_results`、`processed_events`；
- 存在时，按 job／事件归属清理 `model_calls`。

这是待实现的覆盖清单，不是可直接执行的 SQL 删除顺序。实施时依据外键图确认子表、引用与触发器顺序。删除旧 job 前保留必要关联集合，防止级联删除后无法找到附件或事件。

普通消息和定时任务的事件格式不同。清理应基于精确作用域、主键、来源事件与投递关联集合；不依赖宽泛的 `LIKE '%会话ID%'` 或按文本内容模糊匹配。

文件清理要求：

1. 候选路径只来自服务端已登记的附件、缓存与识别记录，不接受客户端提交路径。
2. 路径解析后必须位于当前 Web 数据根目录内；拒绝通过符号链接／Windows junction 越界。
3. 每次清理共享文件前检查剩余引用，并协调其他会话的并发发布。仍有其他引用则只释放本会话引用，不把它算作清理失败。
4. 清理该会话的临时 `.part` 文件与失败落盘副本，不能递归删除整个 `data/web`、全局 `images` 或其他共享目录。
5. 文件占用等失败写入删除作业，稍后重试；会话始终保持禁用，不能恢复可用后让旧任务继续。

数据库内容清除与文件删除无法形成跨系统原子事务，所以使用持久化清理作业实现可恢复的完成过程。文件已不存在视为成功；重复运行不能影响其他会话。

### 4.5 完成与前端同步

清理成功后删除会话实体，删除作业保留最少的 ID、完成状态与时间，不保留正文、附件路径或标题。重复删除返回已完成，不复活任何内容。

当前网页立即停止相关轮询、放弃迟到请求响应、清理草稿和界面数据。删除当前会话后切换到已有会话或空白欢迎页；删除其他会话时保留当前正在编辑的会话。

通过 BroadcastChannel 或 storage 事件同步同源标签页。其他浏览器实例在下一次服务器同步收到 410 后清理界面。离线标签页已经拿到的文字无法远程抹除，但不能继续向已删除会话提交请求。

## 5. API 与改动范围

建议接口：

| 接口 | 行为 |
| --- | --- |
| `GET /api/conversations/{id}/deletion-summary` | 获取确认弹窗的影响数量，不执行删除 |
| `DELETE /api/conversations/{id}` | 同现有 Cookie／CSRF／Origin 校验；建立删除边界，返回 202 和删除作业 ID |
| `GET /api/conversation-deletions/{id}` | 返回清理中、清理失败或完成；受本地访问保护 |
| `POST /api/conversation-deletions/{id}/retry` | 仅重试已有清理作业，不扩大删除范围 |

删除由用户点击直接调用 API，不通过 LLM 判断是否应删，也不通过自然语言猜测会话目标。

| 模块 | 影响 |
| --- | --- |
| 前端 App／API／样式 | 删除入口、确认弹窗、清理状态、跨标签页同步、草稿与轮询清理 |
| Web API／WebRepository | 删除状态、读写检查、摘要／删除／重试接口、增量表结构 |
| 新增删除协调服务／存储方法 | 关联图枚举、短事务撤销、内容清理、持久化文件清单、恢复 |
| Inbox／Outbox 与调度仓库 | 删除后正常终止，拒绝迟到写入、重新调度和结果投递 |
| 文件上传／图片服务／缓存 | 文件发布与删除协调，共享引用保护和临时文件清理 |
| 维护与启动生命周期 | 恢复未完成清理，统一文件删除保护，显示清理异常 |
| 测试 | 增加并发删除、故障恢复与隔离验证；原 QQ 路径回归 |

沿用 React、TypeScript、FastAPI、SQLite 和现有后台机制，不新增 Redis、Celery 或 Docker。业务模型的提示词和工具选择无需因会话删除而重写。

## 6. 风险评级与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 删除后任务又保存结果 | 高：数据复活、重新创建提醒 | 持久删除标记、执行权撤销、事务内复查、迟到结果丢弃 |
| 共享图片误删 | 高：损坏其他会话资料 | 精确引用统计、路径锁与统一发布协议 |
| 提醒刚好进入投递 | 高：删除后仍出现通知 | 同事务停用，Web 投递事务检查；删除前已经写入的通知也随会话清除 |
| 上传／识别在删除后落盘 | 高：残留文件 | 覆盖所有文件写入口的生命周期保护和恢复清理 |
| 外键或关联遗漏 | 中高：事务失败或留存敏感内容 | 关联清单、正确顺序、FTS 同步、foreign_key_check 与残留检查 |
| Windows 文件占用／进程崩溃 | 中：清理无法一次完成 | 持久化清理状态、幂等重试、重启恢复、不提前宣称完成 |
| 删除锁持有过久 | 中：其他请求卡顿 | 网络与大块文件操作不放数据库写事务，按会话协调、固定锁顺序 |
| 多标签页旧响应覆盖界面 | 中：已删除会话看似复活 | 失效标记、响应代次检查、取消轮询及广播同步 |
| 用户误点 | 高：永久丢失 | 显式确认影响、取消按钮、双击幂等；不在菜单点击一次后直接删除 |

综合判断：风险可控，但这是后端生命周期功能，不能作为只改界面的轻量按钮上线。主要风险来自并发和数据归属，而不是删除 API 本身。

## 7. 实施与验收顺序

1. 先建立 Web 会话关联清单和删除标记，验证删除边界及跨会话隔离。
2. 接入任务撤销、调度与投递阻断，验证进行中任务不能继续产生业务结果。
3. 接入文件发布保护、共享文件引用检查和可恢复清理。
4. 完成前端确认、清理状态及多标签页行为。
5. 在临时数据库和测试文件中运行全链路删除与故障注入；通过后才提供真实会话删除入口。

核心验收用例：

- 删除空会话、只有聊天的会话，以及带行程／附件／提醒／监测的完整会话。
- 删除 A 后，A 的上下文、附件、业务数据、通知、任务与可归属执行记录不再可读；B 完全可用，QQ 数据不变。
- 同一图片被 A、B 引用，删除 A 不破坏 B；删除最后引用后才清理物理文件。
- 模型请求处理中、结果待提交、附件上传／识别落盘中分别触发删除，迟到结果不复活数据。
- 普通提醒、预约提醒、定时查询、规则监测正好到期或已进入发送阶段时删除，不再出现后续 Web 投递。
- 连续双击、两个标签页同时删除、删除后重放旧请求，均幂等并拒绝重新写入。
- 数据库清理后模拟文件被占用：显示清理失败，数据仍不可访问；解除占用后重试完成。
- 在建立删除标记、清理数据库、删除部分文件等阶段分别模拟进程退出，重启后恢复到完成状态。
- 文件路径越界或 junction 被拒绝；全程不开启关闭外键约束的捷径。
- 删除当前会话时其他标签页及时清空旧界面；迟到 GET 响应、草稿和 localStorage 不把它重新选中。
- 其他会话的模型查询和定时任务不因本次删除被全局取消或重启。
- 完成状态下外键检查通过，目标关联记录与应删除文件均不存在；必要的删除标记不含内容。

## 8. 审核建议

建议采用上述完整删除语义：**确认后立即封禁并停止关联能力，后台完成数据及文件清理；成功后不可恢复，失败明确提示并可重试。**

不建议仅隐藏会话、删除一张表，或只取消未到期提醒而忽略已经排队和正在执行的任务。当前实施和验收状态以本方案开头链接的交付记录为准。
