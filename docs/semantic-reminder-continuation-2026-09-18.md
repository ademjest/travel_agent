# 提醒语义解析与多轮接续修正

日期：2026-09-18

## 问题与上次修复的局限

“10点吧”未匹配到时间回答，只是表面症状。增加“吧／呀”等字符只能补几个表达，无法使原有 LLM 语义解析真正参与后续对话。根本原因是：

1. `semantic_candidate` 以关键词决定是否调用语义编译器，许多补充回答在调用模型之前就被跳过。
2. `SemanticTaskService._pending` 只识别 `semantic` 类型任务，实际提醒由 `PersonalReminderService` 保存为 `reminder` 类型，二者没有接通。
3. 模型没有收到已经收集的事项、日期、钟点、缺失字段和上一轮追问。
4. `_reminder` 要求事项和时间都在当前消息中，并把解析结果改写成另一句话重新走规则；无法正确继承跨轮字段。
5. 原 Intent IR 校验禁止 `clarify` 携带已知操作。真实联调还暴露了操作对象格式不够明确的问题，部分输出被校验拒绝后退回旧路径。
6. 通用 Agent 的提示词混淆了“当前模型工具白名单”和“应用整体提醒能力”。已区分普通个人提醒的上层服务与图片预约工具，禁止仅因本轮工具缺项就声称系统没有提醒功能；也不允许未经执行就宣称创建成功。

## 当前链路

```text
当前用户消息
  + 同一平台／会话／使用者的有效待完成提醒
  + 已收集字段、缺失字段、上一轮追问
        ↓
IntentCompiler：判断新建、补充、澄清、取消设置或切换话题
        ↓
Intent IR：reminder/create 或 reminder/continue_pending
        ↓
服务端绑定真实任务，校验来源、归属、版本、歧义与时间有效性
        ↓
PersonalReminderService.handle_intent：合并字段或继续追问
        ↓
原事务、提醒存储、调度和消息投递链路
```

明确的固定指令继续走快速路径；其余自然语言不再要求包含“提醒我”等关键词才进入语义编译器。QQ群是否接收一条未 @ 的消息仍受群消息触发策略约束；属于本人有效提醒任务的后续回答不再受时间词汇表限制。

## 结构化接续

服务端为模型提供上下文中的任务序号，不把模型生成的数据库 ID 当作权限。例：前两轮已经收集“明天”“预约陕西历史博物馆”“10点”，当前回答说明白天，模型可以输出：

```json
{
  "schema_version": 1,
  "action": "update",
  "operations": [{
    "domain": "reminder",
    "operation": "continue_pending",
    "task_index": 1,
    "disposition": "answer",
    "trigger": {
      "text": "上午",
      "source_text": "天亮以后那个时间"
    }
  }],
  "source_spans": ["天亮以后那个时间"],
  "missing_fields": [],
  "requires_confirmation": false
}
```

日期和事项由服务端从原任务继承，模型不需要在当前消息中重新找到它们。新建提醒也支持有原话依据的时间标准化，而不是要求标准化表达恰好连续出现在用户输入里。

`handle_intent` 直接接收校验后的字段，不再将接续结果拼成句子、重新碰一次关键词门槛。普通时间解析规则保留为时间合法性校验及模型不可用时的有限回退，不承担自然语言是否属于提醒的主要判断。

## 执行约束

- 模型不能生成 owner_id、scope_id、reminder_id 等权限和资源字段。
- 接续只允许绑定模型调用前提供的有效任务，并在执行前重新检查归属与版本；写入时仍受原事务与租约约束。
- 多项提醒可能匹配时要求明确事项，不任意选一条。
- “10点”不能默认为上午。改变日期但没有解决上午／晚上的歧义时，也不能自动完成提醒。
- `clarify` 可以带部分已知字段，但不表示可以直接写入一条完整提醒。
- 取消设置只结束待收集任务，不连带取消已经存在的提醒。
- 无关话题交回其他业务路径，不修改待完成提醒。
- 模型不可用或输出不合规时保留原任务并说明尚未理解，不再由这一错误路径声称系统没有提醒工具。

LLM 提供语义判断，代码负责执行边界；来源校验和时间校验不能证明模型理解了所有可能的自然语言，信息含糊时仍然需要追问。

## 验证

新增 `tests/test_semantic_reminder_continuation.py`，覆盖不匹配原规则的自然回答、没有触发关键词的新建表达、跨轮字段继承、规范化时间、上午／晚上歧义、取消、话题切换、多任务选择、其他用户与过期任务隔离、模型失败、伪造身份以及模型调用期间的任务版本变化。

Web API 测试额外验证前端提交的非规则表达确实进入上下文 LLM 解析，并且不调用普通聊天兜底。

完整回归 560 项通过；提示词能力边界调整后另运行 Agent 相关 19 项测试，通过。完整日志为 `E:\Agent\travel-semantic-resume-full.log`，真实模型日志为 `E:\Agent\travel-semantic-reminder-live.log`。

`scripts/smoke_semantic_reminder.py` 使用真实模型与临时 Web 数据，通过以下流程：

- “明天提醒我预约陕西历史博物馆”→“我想选十点整”→“我说的是天亮以后那个时间，别放到晚上”。
- “明天上午十点，买车票这件事到时候喊我一声”。
- “后天提醒我收拾行李”→“我改主意了，这个安排先作罢”。

脚本不接入 QQ，不修改正式提醒，测试数据在退出后清理。可加 `--show-ir` 查看这些合成测试消息对应的原始 IR；生产日志不默认打印完整原始模型输出。

## 范围与成本

本次接通提醒新建和待完成提醒的语义接续，沿用既有其他领域服务，不代表所有旅行业务都已重新实现为同一套完整语义状态机。

移除自然语言关键词门槛后，部分消息会比原来多一次前置 LLM 解析调用，因此有额外时延与接口费用。明确指令仍走快速路径；后续优化应合并或复用解析结果，而不是重新用关键词挡住自然表达。
