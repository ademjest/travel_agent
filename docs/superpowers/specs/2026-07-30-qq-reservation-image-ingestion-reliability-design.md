# QQ 预约图片接收兼容与私聊回退设计

## 背景

当前预约制定流程设计为：

```text
群内发送“制定预约”
→ 进入 30 分钟预约制定模式
→ 用户在群内发送一张攻略图片
→ Bot 识图并结合群共享行程生成预约草稿
```

实际测试中，用户在群内正确发送了 `@旅游bot 制定预约`，Bot 也成功回复已进入预约制定模式；随后用户在同一群中发送了包含 `@旅游bot` 的图片消息，但没有收到预约草稿。

运行日志显示：

```text
群消息：attachments=0
私聊图片：attachments=1
ping：可以正常回复 pong
```

由此可以确认：

- Bot 登录、群消息接收和群回复链路正常。
- `制定预约` 命令和预约会话创建正常。
- 群图片没有进入 `ReservationImageService`，失败发生在消息附件接收或 SDK 解析阶段。
- 私聊可以稳定收到图片附件。
- 本问题与 Excel 行程解析、LLM 图片识别和预约日期计算无关。

## 目标

1. 确认群图片附件是在 QQ 原始事件中缺失，还是被 `qq-botpy` 解析丢失。
2. 原始事件存在附件时，在项目内实现兼容解析，不修改本机 `site-packages`。
3. 原始事件不提供附件时，提供“群内申请、私聊上传、关联回原群”的可靠回退流程。
4. 任何失败都必须留下可定位日志，不能继续静默无回复。
5. 普通图片与预约攻略图片继续保持明确入口，不恢复“任意图片自动创建预约”的旧行为。

## 非目标

- 不读取群历史消息。
- 不自动预约或购买门票。
- 不绕过 QQ 官方权限获取图片。
- 不在日志中保存图片 URL、访问令牌、完整消息正文或原始图片数据。
- 不为了兼容当前问题修改第三方安装目录中的 `qq-botpy` 源码。
- 不让私聊图片脱离目标群直接使用任意群的行程资料。

## 根因边界

当前 `bot.py` 只从以下字段归一化附件：

```python
message.attachments
```

预约图片入口只存在于群消息处理分支。私聊消息统一进入现有文档上传绑定流程，不会解析 `制定预约`，也不会调用预约图片服务。

因此当前实际状态是：

```text
群内预约会话有效
        +
GroupMessage.attachments 为空
        ↓
预约图片处理不会启动
```

## 总体方案

采用“诊断优先、群聊直传优先、私聊绑定兜底”的两阶段方案：

```text
群图片事件
    ↓
记录安全的原始事件结构
    ↓
┌──────────────────────────────┐
│ 原始 payload 是否包含附件？ │
└──────────────────────────────┘
       │是                         │否
       ↓                           ↓
项目内兼容解析                私聊绑定上传
       │                           │
       └───────────┬───────────────┘
                   ↓
          ReservationImageService
                   ↓
        群共享行程匹配与预约草稿
```

最终产品同时保留两条入口：

- 群图片附件可以正常取得时，继续支持 `@Bot + 图片`。
- 群图片附件不可取得时，明确提示用户使用一次性绑定码私聊上传，不再无回复。

## 第一阶段：安全诊断与可观测性

### 原始事件探针

在 `qq-botpy` 创建 `GroupMessage` 之前，对 `GROUP_AT_MESSAGE_CREATE` 原始 payload 做安全摘要。

只允许记录：

- 事件类型。
- `payload.d` 的顶层字段名。
- 原始附件数量。
- 原始附件元素的字段名。
- SDK 解析后的附件数量。
- 消息正文长度，不记录正文内容。
- 是否包含引用、提及等布尔信息。

禁止记录：

- 图片 URL。
- Access Token、App Secret 和 Authorization Header。
- 完整 OpenID、消息正文和原始 payload。
- 图片二进制或 Base64。

示例日志：

```text
Group event media probe: event=GROUP_AT_MESSAGE_CREATE \
raw_keys=author,content,group_openid,id,attachments \
raw_attachments=1 parsed_attachments=0 content_length=8
```

### 图片处理阶段日志

增加以下结构化节点：

```text
Reservation workflow active
Reservation image received
Reservation image download started/completed
Reservation image extraction started/completed/failed
Reservation draft created: plan_code, item_count
```

日志只使用事件 ID 的短哈希、图片 SHA-256 前 12 位和数量信息。

### Outbox 失败日志

当前 `OutboxWorker` 会把发送异常写入 SQLite，但不会输出日志。应增加：

```text
Outbox delivery failed: outbox_id channel attempt error_type retry_at
Outbox moved to dead letter: outbox_id attempts error_type
```

异常文本需要截断并清理潜在 URL、Token 和请求体。

## 第二阶段 A：原始事件存在附件

如果诊断确认原始 `payload.d.attachments` 有数据，而 `GroupMessage.attachments` 为空，则问题属于 SDK 兼容。

### 实现原则

- 在仓库内增加独立兼容模块，例如 `qq_gateway_compat.py`。
- 在 `TravelRiskBot` 初始化连接前安装兼容解析器。
- 使用原始 payload 构造项目自己的 `ChatAttachment`。
- 保留 SDK 原有事件分发和消息对象行为。
- 兼容层必须可以在 SDK 修复后安全关闭或移除。

### 支持字段

兼容层至少归一化：

- `filename`
- `url`
- `content_type`
- `size`
- `width`
- `height`

如果原始事件只提供 URL 而没有文件名或 Content-Type，应根据可信响应头确定图片类型，不能仅根据 URL 文本猜测。

### 用户流程

```text
@旅游bot 制定预约
→ Bot 回复已进入预约模式
→ 用户发送 @旅游bot + 单张图片
→ 原始事件兼容层提取附件
→ 直接生成预约草稿
```

## 第二阶段 B：原始事件不提供附件

如果 QQ 原始事件中也没有图片 URL，则群聊代码无法恢复图片，必须使用私聊上传。

### 推荐交互

1. 用户在目标群发送 `@旅游bot 制定预约`。
2. Bot 创建一次性预约图片绑定码，例如 `QR-ABC234`，有效期 10 分钟。
3. Bot 回复：

   ```text
   已开始制定预约。QQ 当前未向群机器人下发图片附件。
   请私聊机器人发送绑定码 QR-ABC234，绑定成功后再发送一张攻略图片。
   ```

4. 用户私聊发送绑定码。
5. Bot 将该私聊用户临时绑定到目标群，并提示发送一张 JPEG、PNG 或 WebP 图片。
6. 用户私聊发送图片；私聊日志应出现 `attachments=1`。
7. Bot 使用绑定记录中的目标群读取 Excel 和长期行程文档。
8. Bot 创建属于原群的预约草稿，并在私聊返回完整草稿。
9. 用户回到原群执行补充、刷新或确认命令。
10. 一次图片处理后绑定立即失效，无论成功或失败。

### 为什么不能直接在私聊制定预约

群消息中的 `member_openid` 与私聊中的 `user_openid` 不是同一标识，不能直接推断私聊用户对应哪个群成员，也不能确定应读取哪个群的 Excel。

一次性绑定码同时解决：

- 目标群选择。
- 群行程资料隔离。
- 私聊身份与群操作权限之间的关联。
- 多群同时使用时的歧义。

### 计划创建者归属

绑定记录必须同时保存：

- `group_openid`：预约计划所属群。
- `issuer_openid`：在群内发起 `制定预约` 的成员。
- `redeemed_user_openid`：兑换绑定码的私聊用户。
- `purpose`：`reservation_image`。

预约图片虽然由私聊用户上传，但草稿的 `creator_id` 必须使用群内 `issuer_openid`。否则私聊 `user_openid` 与群 `member_openid` 不一致，会导致创建者回到群里无法确认或修改计划。

绑定码本身视为短期授权能力。获得绑定码的私聊用户可以代发图片，但不能改变计划所属群和计划创建者。

## 持久化设计

优先复用现有 `upload_bindings`，增加用途字段：

```text
purpose = document | reservation_image
```

预约图片绑定还需要保存或关联：

- 目标群。
- 群内签发成员。
- 私聊兑换用户。
- 创建、过期、兑换和消费时间。
- 源群事件幂等键。

如果复用现有表会显著增加条件分支，可以建立职责更单一的 `reservation_upload_bindings`。实现时选择改动更少、约束更清晰的方案，不为未来用途预先抽象通用上传框架。

## 失败处理

| 场景 | 用户结果 |
|---|---|
| 群图片原始事件无附件 | 明确提示改用私聊绑定，不静默等待 |
| 绑定码错误或过期 | 提示回到群里重新申请 |
| 私聊直接发图片但没有绑定 | 提示先获取预约绑定码 |
| 一次发送多张图片 | 拒绝并要求逐张处理 |
| 图片格式或大小不支持 | 消费当前绑定并要求重新申请 |
| 图片下载失败 | 提示失败原因，是否保留绑定由实现测试确定 |
| LLM 识图失败 | 创建全手动草稿或明确提示重试 |
| 草稿创建成功但回复发送失败 | Outbox 重试并输出安全错误日志 |
| 事件重放 | 复用原草稿和原回复，不重复创建计划 |

## 安全与隐私

- 绑定码使用 `secrets` 生成，只保存 SHA-256 哈希。
- 绑定码只能兑换一次，并在 10 分钟后过期。
- 图片继续执行 HTTPS、DNS、大小和 Content-Type 校验。
- 图片和草稿按目标群存储隔离。
- 原始事件诊断不得记录图片临时 URL。
- 日志不得记录完整 OpenID；只保留短哈希或必要的截断标识。
- 普通私聊图片不能自动成为预约图片，必须存在有效 `reservation_image` 绑定。

## 测试方案

### 原始事件兼容测试

- 原始 payload 有附件、SDK 附件为空时能够恢复 `ChatAttachment`。
- 原始 payload 和 SDK 都无附件时不伪造图片。
- 日志不包含 URL、Token 和完整消息正文。

### 群聊直接上传测试

- `制定预约` 后的单张群图片创建一个草稿并结束会话。
- 普通群图片不会创建预约草稿。
- 多张图片被拒绝。
- 事件重放不重复创建草稿。

### 私聊绑定测试

- 群命令生成用途为 `reservation_image` 的一次性码。
- 私聊兑换后只接受一张图片。
- 无绑定、错误、过期、已消费绑定均被拒绝。
- 私聊图片使用目标群的文档和 Excel。
- 草稿创建者是群内签发成员，而不是私聊用户标识。
- 同一私聊用户的新绑定使旧的未消费绑定失效。
- 同一事件重试时复用原绑定码、草稿和回复。

### 投递与日志测试

- QQ 发送失败会记录错误类型、重试次数和下次时间。
- 连续失败进入死信时有明确日志。
- 成功发送不会输出附件 URL 或敏感 payload。

## 验收标准

1. 截图所示的 `@Bot + 图片` 测试不再静默无回复。
2. 原始事件包含附件时，终端显示 `raw_attachments=1`，并成功创建草稿。
3. 原始事件不包含附件时，用户收到私聊绑定指引。
4. 私聊图片日志显示 `attachments=1`，并使用原群的 Excel 生成草稿。
5. 计划创建者可以在原群完成补日期、刷新、确认和取消。
6. 普通图片不会自动调用预约功能。
7. 图片处理或回复发送失败时，日志可以定位到具体阶段。
8. 全量测试通过，现有文档上传、OneBot、提醒调度和预约确认流程无回归。

## 实施顺序

1. 增加原始群事件安全探针和 Outbox 失败日志。
2. 用真实 QQ 群图片复测，确认原始 payload 是否包含附件。
3. 原始附件存在时实现项目内兼容解析。
4. 原始附件缺失时实现预约图片私聊绑定。
5. 更新群提示、帮助文本和 README，删除“随后直接发送图片即可”的误导描述。
6. 补齐单元测试、验收测试和真实 QQ 冒烟测试。

## 最终决策原则

- 能从群原始事件可靠取得图片时，优先保留群内直传的便捷体验。
- QQ 平台不提供群图片时，不尝试从截图文字、聊天记录或不可信链接猜测图片。
- 私聊绑定是平台能力不足时的正式回退路径，不是临时手工操作。
- 在取得原始 payload 证据前，不直接大范围重写预约业务逻辑。
