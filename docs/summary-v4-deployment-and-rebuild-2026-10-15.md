# 摘要 v4 部署、降级与单会话重建策略

日期：2026-10-15。对应已批准的摘要质量改进方案。本文件说明运维边界，不是新的模型提示词。

## 1. 本次落地范围

- 摘要 system 直接读取 `docs/prompt_design/abstract_design_prompts.md`；没有重写用户原文。
- 契约：12项、正文总计1800字符、每项1—4引用、每引用1—500字符、四种kind；共享常量和本地schema位于 `core/summary_contract.py`。
- 保持现有模型、档位、JSON object模式和format_version=3，不假设兼容网关支持严格schema。
- 新输入使用整数message_id，严格按输入顺序提供；校验器只为旧响应回放兼容id。previous_items只传正文和来源ID/片段，不发送内部source_hash。
- saved_business_states当前省略。省略表示没有提供已保存事实覆盖证据，不能自行推断某类约束已被其他模块记录。
- 原有摘要启用开关、8轮且9000字符触发、用途排除、隐私/遗忘过滤、租约、发布时来源与所属复核继续有效。
- 分批同时限制24000字符和完整请求的保守字节估计；给system和消息结构预留空间，不扩大模型预算。

## 2. 失败策略

整份校验失败仍不发布。不直接裁掉第5条不同来源，不发布“部分成功”来抬高成功率，不让一个无效版本覆盖有效旧版本。

默认没有额外模型修复调用。`ConversationSummaryService(..., repair_permit=...)`是显式接入点：调用方必须在返回true前预留本次物理调用与Token预算；仅判断“还有钱”不是物理调用配额管理。生产runtime未传该许可，所以本次部署不会暗中增加调用。

只有JSON解析和结构/容量错误可申请一次修复，输入是同一system、允许来源、原始输出、错误类别/路径。出处、排除来源及语义错误不进入修复。修复结果重新进行全部校验，失败后不再循环；网关原有事件/日/月限额仍适用。截断/内容过滤不视为可发布结果。

失败优先复用仓库复核后仍有效的旧摘要；否则不注入摘要，由其余合法上下文继续回答。保持原失败冷却机制。后台日志只记状态、版本、错误类别/字段路径及是否复用；诊断回调另可取得提示词版本、哈希和批次信息，不默认记正文。

`inspect_conversation_summary.py`仍是只读工具，新增prompt_matches_current，用于区分“来源有效”与“已用当前提示生成”。旧版本不会因为换提示词就自动变成来源无效，也不会被冒充成v4。

## 4. 单会话重建：后续执行约束

新提示不能凭空找回旧摘要和引用均遗漏的事实。若以后某个会话确实存在有效但质量不足的旧摘要，采用以下流程，不全站清空：

1. 明确目标platform/scope/owner、旧版本、用途和新的物理调用/Token预算；只重建该会话。
2. 留存原消息和受控旧摘要快照，记录版本、来源/依赖哈希。快照同样含个人数据，纳入对应删除和访问策略，不能成为恢复已遗忘事实的旁路。
3. 从仍存在的原始用户历史读取，先应用summary_excluded_events及原过滤；助手内容不是事实来源。不可仅用旧摘要反推丢失事实。
4. 使用原租约与网关预算分批构建候选；旧有效版本在候选完成前继续作为明确标记的旧版降级参考。不能将重建到一半的早期批次当作最新完整摘要发布。
5. 发布前再次检查来源、依赖、所属、租约/版本及累计覆盖；删除/遗忘或并发更改导致失效时放弃候选，不能覆盖新状态。
6. 发布新的内容版本和v4提示哈希；离线检查与真实质量评估分别记录。失败不删旧快照、不把未通过候选注入回答。

本次交付的是上述重建策略，**未提供绕过预算或删除旧摘要触发重建的管理接口，也未执行正式重建**。原方案本身要求重建执行前另行确认范围与费用；当前默认库没有active旧摘要，无需冒险引入全量重建器。

## 5. 回滚

回滚应只恢复本次涉及的代码与提示词版本，保留用户的其他未提交改动。新增prompt_hash是可保留的加法字段，不必删除列；不要回滚整个正式数据库来覆盖升级后的新聊天。

prompt_version与prompt_hash用于辨别实际生成版本。回滚提示词不等于恢复曾经遗漏的事实；仍须保留来源有效性和遗忘检查。不要用全仓库reset或删除data目录来回滚。
