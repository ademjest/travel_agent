## QQ 人工测试步骤

1. 保持 NapCat 已登录。在原 Python 服务终端停止旧服务，然后使用原启动参数重启。默认示例为 `python -m uvicorn adapters.onebot_app:create_runtime_app --factory --host 127.0.0.1 --port 8000`；必须保持与 NapCat 上报地址一致的端口，不能启动两个重复回复的服务。
2. 在白名单测试群 @ 彼岸发送“现在天气怎么样”，看到追问后直接发“武汉”，应查询天气；由另一名成员回复“武汉”不应补你的任务。
3. 发“明天提醒我抢高铁票”，再直接发“上午十点”；应显示完整年月日时刻及“本群 @ 你”。用“查看我的提醒”检查。
4. 发“9月20号提醒我预约湖北省博物馆”，再发“早上九点”；应按提醒日期创建，不要求上传行程或图片。
5. 发“两分钟后提醒我这是升级投递测试”。等待原定时间及最多一个扫描周期（当前默认 60 秒），应在本群收到 @ 自己的一条提醒；再次查看列表应显示已发送。测试结束后取消其他测试提醒。
6. 连续发“明天提醒我抢高铁票”“后天提醒我带身份证”。直接发“上午十点”应要求指定任务；回复第一条机器人的设置问题再发“上午十点”，应只完成第一条。
7. 发“查看任务”“取消当前任务”，确认只是结束待补信息流程；已经创建的提醒仍可查到，并可说“抢高铁票那条不用提醒了”单独取消。

代码热更新不一定作用于现有 Python 进程，必须重启才能人工验证。新表会由 MemoryStore 初始化增量创建；正式数据上线前应通过 SQLite backup API 做可恢复备份，避免只复制正在使用的 WAL 数据库主文件。

## 第二批：规则证据与旅行查询（2026-09-09，继续实施）

已通过旧站主页的实际链接找到官方 HTTPS 入口 `https://www.hbww.org.cn/fuwu/index.html`，修正了前一批候选域名不可访问的问题。该页面当次读取的个人入馆段落包含“预约最多可提前5天”“每日0点开始放最新可预约日的门票”，同时包含暑期、周一闭馆与节假日说明。这是运行时抓取的页面事实，不是写死在代码里的政策，也不能据此保证未来国庆规则不变。

新增 `BookingPolicyResolver` 和 `BookingReminderService`：

- 运行时读取 HTTPS 页面、排除脚本和样式，区分个人入馆与团队/讲解规则。程序解析提前自然天数、每日时刻，不能明确解析则不推断。
- 保存来源、原文节选、核查时间和全文指纹到 `booking_policy_evidence`；派生通用提醒通过 `source_json` 保留参观日期及规则证据。
- 普通明确规则可按用户初始授权创建；涉及季节/节假日或未独立核实的用户来源，先展示计算结果并要求核对。确认前再次抓取，规则指纹变化必须重新展示，不能沿用旧确认。
- 已过开放时刻、明确常规闭馆日、暂停预约、规则冲突、含当天/工作日等无法明确计算的规则，不会生成猜测的提醒。
- 支持补场馆、补参观日期、提供 HTTPS 说明链接及“重新查询预约规则”；普通查询规则不会要求参观日期，也不会创建提醒。
- 用户修改派生提醒时保留原政策证据并标记人工时间覆盖。旧预约图片流程继续保留。

新增高德地点、步行及公交/地铁工具，均已用当前配置的 Key 只读实测通过。Agent 新增结构化 `request_missing_input`，把缺失城市和起终点存入任务状态；已测试地点和交通的未 @ 续问。新工具接入时曾发现系统提示词允许列表遗漏了追问工具，真实模型测试因此失败；修复允许列表后复测通过。查询“我们住哪里”且存在行程文档时仍优先读取已有资料，不强制变成酒店推荐。

## 第三批：结构化行程、资料来源与关联提醒

新增 `TripPlanner`、`TripService`、`TripRepository`，保存 `trips` 和不可覆盖的 `trip_versions` 快照。行程按当前平台、群和创建者隔离；模型输出中的地点 ID 必须出自实际高德 POI 查询，日期和天数由程序校验。

当前功能：

- 1–14 天城市行程；补城市、天数和具体开始日期。“国庆”不会自动当成 10 月 1 日；可先保存无日期草案，预约提醒等明确日期后再安排。
- 保存用户预算目标、偏好、必去地点和字段来源。轻松/老人场景默认减少每日活动；用户明确指定的每日活动数另行校验。限制未知 POI、重复地点、夜间禁忌、室内/室外日和未要求修改的其他日期。
- 支持“第二天改为室内/室外”、移动完整景点名称到某一天、去掉某天的景点、修改开始日期、查看/选择/取消行程。去掉当天最后一处景点可以留下用户明确选择的休整日。
- 用户要求住宿或餐饮时，给出对应 POI 类型的候选；不虚构实时价格、房态、营业状态或预约成功。
- 用户明确交通方式时，使用已选 POI 坐标查询公交/地铁、步行或驾车段。未查到的段落标记“暂未核实”；用户可“刷新行程交通”。无交通方式时先问，不默认自驾。查询是当前路网参考，不能当成未来日期的班次保证。
- 用户明确要求“并提醒预约”时，从必去场馆/相关地点与日期派生预约提醒。规则不明或需要核对时先保存行程，保留待处理的提醒；可补充“场馆名 HTTPS 链接”继续。仅从资料中读到的动作指令不会授权创建提醒。
- 修改影响已有关联提醒时，先保存预览；确认时再次核对行程版本、提醒集合/版本和政策指纹。行程与提醒在同一 SQLite 事务更新，任一冲突会整体回滚。已发送提醒不重新发送；用户取消的提醒不被重建；人工时间覆盖会保留并明确提示。
- 新修改会令同一行程的旧待确认预览失效。过长、无法完整展示的确认预览不会被截断后继续等待授权。
- “根据文档规划”只使用选定的群内文档版本，保存文档 ID 与需求快照。同群多份资料先选，不拼接不同旅行的数据。通用检索的低相关回退已明确标记，并给片段加上文档 ID。

真实测试过程中发现高德 `10021` QPS 限流。已为地点查询与行程交通段加入节流和最多三次有限重试；错误不是限流时不盲目重试。TripPlanner 复用五分钟内同城市/关键词的 POI 结果，保留原查询时间。仍不可用时明确说明未保存变更。

## 第四批：持久接收、恢复、图片资料和定时查询

OneBot 正式 HTTP 入口现在默认使用 Inbox。验签和字段校验后只保存必要的结构化输入，返回 `accepted` 与请求编号；无关 notice/meta 仍忽略。保留 Adapter 作为 Worker 的处理入口。原有 Adapter 集成测试使用显式的同步测试替身，新 `test_inbox.py` 单独验证正式的异步接收路径，不能用同步替身来证明生产入口速度。

### 接收与恢复机制

- `inbox_jobs` 保存最小可恢复输入、状态、租约、截止时间、重试次数和结果；不保存额外的原始 OneBot 字段。HTTP 请求体上限 128 KiB，普通积压最多 1000 条，控制命令仍可用于处理队列。
- 默认两个普通处理 Worker，同一用户消息按顺序处理；独立的定时只读通道避免被同用户长模型任务堵住。另一个循环优先保存附件，每个附件成功后就写缓存检查点。
- `inbox_assets` 记录本地路径、大小、类型和 SHA-256。缓存读取检查目录范围和哈希；HTTP 输入不能注入本地路径。链接失效或重启后优先使用已保存字节。文件/图片仍有 5 MB 限制。
- 业务执行默认 300 秒截止、最多三次失败尝试；附件保存阶段也有总时限和有限重试。失去租约、取消或超时后，SQLite 写入在同一写事务内验证租约，旧同步线程不能在返回后继续提交业务结果。
- 正常停止释放租约，硬退出后在租约过期时重新领取。已提交的回复直接恢复入 Outbox，不重复生成；已取消的控制请求绑定原目标，重放时不选择后来出现的其他请求。
- “查看任务进度”“取消请求”等控制命令也先持久化，以较高优先级执行，不等待同用户的长请求。取消只影响尚未完成的处理，已经提交的操作不会回滚。
- 白名单变更后，旧输入在下载与执行前重新校验；已进入 Outbox 的群消息也会检查当前允许范围。
- 输入缓存按事件保留策略清理；图片识别资料按图片保留策略清理。不会对目录边界之外的路径执行删除。

### 通用图片资料

新增 `ImageContextService` 和 `media_observations`。普通票据、截图可以直接提问，不再被要求先上传预约攻略。只识别当前附件，不接受模型自选文件或 URL；结果里的媒体编号由程序分配。识别文本按平台、群、发送者隔离，在后续图片问题中作为非可信参考。

用户明确要求根据图片规划时，才把事实快照交给 TripPlanner；不清晰的关键字段阻止据此建立行程或提醒。图片中的“提醒预约”等文字本身不会成为用户授权。模型输出原文需要核对，不能把 OCR 当成可靠性认证；测试中用的是合成票面，无真实个人信息。

### 模型预算与观察

运行时各服务共用 `ModelGateway`：客户端模型调用并发最多 2；每个输入事件最多 12 次网关调用；每次输出最多 8192 tokens。输入按 UTF-8 文本字节保守估算，图片另预留估计量，单次输入估计上限 64000、事件累计预留上限 256000。图片估计不是精确 tokenizer 结果，这些限制不能被表述成精确计费上限。

`model_calls` 记录 event/job/call 标识、模型、耗时、估计量和接口实际返回的 prompt/completion tokens，不记录提示词正文或密钥。接口未提供 usage 时明确为空，不补造实际用量。SDK 自身最多一次重试，因此网关次数也不等于底层 HTTP 请求次数。取消后的真实接口用量仍可记账，但不会让业务写入重新获得权限。

### 一次性定时查询

新增 `scheduled_queries` 与 `ScheduledQueryService`。用户可以安排到时查询当前天气、预报或路况；到期后产生只读类型的 Inbox 任务，不把参数拼成任意自然语言交给通用业务路由。注册表只有三个允许的查询工具，模型不能注入取消、修改、身份等参数。

结果通过 Outbox 在原群 @ 创建者，保留原定和实际查询时间；结果也能作为该用户后续只读问题的上下文。恢复任务时，地点字符串只作为数据，不能被重新解析为预约写操作授权。定时查询可查看、分页和取消；“提醒我查天气”不会被误解释成自动查天气。

到期扫描默认 60 秒，实际还可能有队列和接口延迟，不承诺到秒准确。测试脚本为了更快观察采用 0.5 秒轮询，但没有提前推进时钟：真实等到一分钟后的触发时刻才调用高德。重复查询、政策监测仍属于下一步工作，不能将一次性定时查询当作任意 cron 调度。

- `policy_watches` 保存已授权的监测对象、来源、间隔、截止时间、规则基线和轮次；通过 Inbox 独立只读通道执行。比较预约提前天数、放票时刻、闭馆星期、节假日例外和适用说明，忽略页面其他文字变化。相同失败保持安静，恢复后通知；停止可撤销待执行轮次和待投递通知，旧线程不能继续写入。
