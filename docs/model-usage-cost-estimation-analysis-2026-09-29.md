# 模型 Token 费用“部分未知”问题分析与修复方案

日期：2026-09-29  
状态：已完成诊断并实施修复；交付结果见 `model-usage-cost-estimation-delivery-2026-09-29.md`  
范围：Web 服务配置、模型调用用量记录、费用报表与前端展示。本轮未改写历史费用数据。

## 1. 结论

本次“部分未知”主要不是供应商没有返回 token usage，也不是用户填写的费率数值无效，而是费用模块只在每次模型调用结束时计算费用，没有在后来配置费率后回算历史记录。

当前数据库有 60 次调用：

- 57 次 `estimated_cost` 为 `NULL`；
- 3 次已经成功计算费用；
- 60 次都有输入和输出 token，可用于估算；
- 没有一条是因为输入或输出 token 缺失而无法计算；
- 41 条早期记录没有缓存 token 明细，但可以按“全部输入使用普通输入费率”进行保守估算；
- 16 条较新记录有完整 usage，却因为调用完成时费率尚未在运行进程中生效而没有费用。

前端只要发现一个分组中 `cost_unknown > 0`，就把整个分组显示成“部分未知”，并隐藏已经计算出的费用小计。因此截图中所有用途都显示“部分未知”。

按当前读取到的输入 2、缓存输入 0.2、输出 10 的每百万 token 费率回算，60 次调用的参考费用约为 0.711588，具体币种应以当前生效配置为准。该数值包含对 41 条旧记录按普通输入费率处理缓存明细缺失的保守估算。

## 2. 当前数据证据

| 用途 | 调用 | 空费用 | token usage 缺失 | 按当前费率可回算 |
| --- | ---: | ---: | ---: | ---: |
| unspecified | 41 | 41 | 0 | 41 |
| intent_parse | 8 | 7 | 0 | 7 |
| trip_plan | 7 | 6 | 0 | 6 |
| trip_requirement_extract | 3 | 2 | 0 | 2 |
| trip_plan_repair | 1 | 1 | 0 | 1 |

已经保存费用的 3 次调用发生在 2026-09-29，说明费率后来已经开始参与新调用计算。其余历史调用不会因为配置费率或重启而自动更新。

41 条 `unspecified` 记录产生于旧版用途分类和 usage 元数据结构。它们的 `prompt_tokens`、`completion_tokens` 有值，但后加的 `usage_complete` 字段因数据库迁移默认值为 0，不能据此认定供应商没有返回 usage。

## 3. 具体原因

### 3.1 费用只在调用完成时计算

`infrastructure/model_gateway.py::_finish` 在模型请求结束时读取：

```text
LLM_INPUT_PRICE_PER_M
LLM_CACHED_INPUT_PRICE_PER_M
LLM_OUTPUT_PRICE_PER_M
LLM_PRICE_CURRENCY
```

只有该时刻输入和输出费率均存在，才写入 `model_calls.estimated_cost`。费率后来保存后，历史行仍保持 `NULL`。

### 3.2 保存配置后需要重启

`EnvSettingsStore.save` 只更新项目 `.env`。运行中的 `ModelGateway` 通过 `os.getenv` 读取启动时环境，不会热加载保存后的费率。

前端虽然显示“配置已保存，当前运行服务仍使用启动时配置，待重启”，但这个提示和费用报表距离较远，用户容易理解成费率已经立即参与估算。

当前配置状态已经显示费率在运行环境中生效，因此后续新调用能够计算；这不影响此前 57 条空费用记录。

### 3.3 报表把所有空费用都视为同一种未知

`usage_report` 使用以下规则：

```sql
CASE WHEN estimated_cost IS NULL THEN 1 ELSE 0 END
```

它没有区分：

- token 齐全，但调用当时没有配置费率；
- 历史迁移记录，可以保守回算；
- 供应商确实没有返回 usage；
- 模型请求失败且没有可计费 token；
- 费率或币种配置无效。

因此可以回算的 57 次调用也被标成未知。

### 3.4 前端隐藏了已知费用小计

`frontend/src/SettingsPanel.tsx` 当前逻辑为：

```text
cost_unknown > 0 → “部分未知”
否则 → 显示 estimated_cost
```

即使一个分组中已经有部分调用成功计费，只要还存在一条空费用，前端也不会显示已知小计。例如 `intent_parse` 已有一次费用 0.008842，但界面只显示“部分未知”。

### 3.5 默认币种与运行时读取不完全一致

原设置层会把空币种显示为默认 `CNY`，但 `_finish` 直接读取 `os.getenv('LLM_PRICE_CURRENCY', '')`。如果用户没有把默认值显式写入环境，费用可能已经计算，但 `cost_currency` 仍为空。本次实施将统一默认值改为 `USD`。

当前数据库中已经计费的 3 条记录币种为空，证明历史上发生过“有费用、无币种”的情况。当前项目配置可能已经修改，不能用现在的币种无条件覆盖所有历史费用。

### 3.6 汇总表不会随历史回算自动修正

`model_usage_periods` 在调用结束时增量累加 `estimated_cost` 和 `cost_unknown`。即使未来更新 `model_calls` 历史费用，如果不重建或同步更新周期表，日/月统计仍会保留旧的未知数量。

## 4. 推荐修复方案

### P0：报表按当前费率回算可计算的历史记录

在 `usage_report` 中区分三类费用：

1. `persisted`：调用完成时已经保存费用和费率依据；
2. `recalculated`：历史费用为空，但输入/输出 token 齐全，按当前生效费率回算；
3. `unknown`：token 缺失或当前费率仍不完整，确实无法计算。

建议不要在 GET 报表接口中修改数据库。读取时动态计算即可，避免一次查看报表就改写历史数据。

对于 `cached_input_tokens IS NULL` 的旧记录：

- 将缓存 token 按 0 处理；
- 即全部输入按普通输入费率估算；
- 标记 `cache_detail_missing=true`；
- 报表说明这是保守估算，不能声称等于供应商账单。

报表返回值建议增加：

```json
{
  "estimated_cost": 0.711588,
  "cost_unknown": 0,
  "cost_recalculated": 57,
  "cache_detail_missing": 41,
  "unknown_usage": 0,
  "unknown_pricing": 0,
  "currency": "USD"
}
```

### P0：修正前端显示

建议显示规则：

- 全部可计算：`0.076842 USD`；
- 包含历史回算：`0.076842 USD（含 7 次按当前费率回算）`；
- 仍有真正未知：`0.012000 USD + 2 次无法估算`；
- 没有任何可计算费用：`2 次无法估算`。

不要再用“部分未知”替代整个费用单元格。已知小计和未知数量应同时显示。

报表下方说明：

```text
历史调用按当前费率回算；旧记录缺少缓存拆分时，全部输入按普通输入费率保守估算。
费用仅供本地参考，不等同于供应商账单。
```

### P0：统一默认币种

费用计算应使用和设置页面一致的默认值：

```python
currency = os.getenv('LLM_PRICE_CURRENCY', '').strip().upper() or 'USD'
```

如果当前报告包含多种非空币种，不应直接合计并标成一个币种。应按币种分组，或明确显示“混合币种，不能合计”。

对于历史上“费用有值但币种为空”的记录：

- 不应直接永久写成当前币种；
- 动态报表可标记为 `currency_missing`；
- 如果只有一个当前币种，可以显示“币种按当前配置推定”，不能称为原始记录。

### P0：增强保存后的提示

保存费率后，费用区附近应显示：

```text
费率已保存，重启后用于新调用；历史调用将在报表中按当前费率回算。
```

如果 `restart_required=true`，费用表应显示明显提示，而不是只在配置表单上方或下方显示一次。

### P1：为未来调用保存费率快照

为 `model_calls` 增加：

- `input_price_per_m`
- `cached_input_price_per_m`
- `output_price_per_m`
- `price_currency`
- `pricing_version`
- `cost_estimation_version`

每次调用完成时保存当时使用的费率。之后用户修改费率时：

- 已经计费的历史调用保持原费率；
- 只有此前未计费且 token 完整的调用按当前费率回算；
- 报表可以区分原始估算与后补估算。

现有 `LLM_CONFIG_VERSION` 可以作为人工配置标签，但不能替代实际费率快照。

### P1：提供显式历史重算操作

如果需要将回算结果持久化，增加明确操作，例如“按当前费率补算历史费用”，并在执行前展示：

- 将补算多少次调用；
- 使用的输入/缓存/输出费率和币种；
- 缓存明细缺失的记录数量；
- 已经保存费用的记录不会被重算；
- 操作完成后重建 `model_usage_periods`。

该操作应在事务中：

1. 更新符合条件且 `estimated_cost IS NULL` 的 `model_calls`；
2. 保存费率快照和“历史回算”标记；
3. 从 `model_calls` 重新构建日/月汇总；
4. 校验调用总数和 token 总数前后一致。

不建议在保存费率时无提示地重写历史费用。

## 5. 推荐代码改动范围

| 文件 | 改动 |

| `infrastructure/model_gateway.py` | 统一费率解析、动态历史回算、未知原因分类、币种默认值、未来费率快照 |
| `frontend/src/SettingsPanel.tsx` | 同时显示费用小计、回算次数和真正未知次数；突出待重启提示 |
| `frontend/src/SettingsPanel.test.tsx` | 覆盖已知、回算、部分未知、币种缺失和混合币种展示 |

如果实施持久化重算，还需增加受确认保护的 API、数据库迁移和周期汇总重建测试。

## 6. 验收用例

1. 先产生 3 次有 usage、无费率调用，再配置费率并重启：报表应显示数值及“3 次按当前费率回算”，不能显示“部分未知”。
2. 旧记录缓存明细为空：费用按普通输入费率估算，并显示保守估算说明。
3. 一次调用没有供应商 usage：显示已知费用小计加“1 次无法估算”。
4. 一个用途已有 2 次计费、1 次未知：不得只显示“部分未知”。
5. 只配置输入费率、未配置输出费率：明确显示费率不完整，不能按零计算输出费用。
6. 未显式填写币种：新费用使用与界面一致的默认 USD。
7. 修改费率后：已有费率快照的历史调用不改变；未计费历史调用按当前费率回算并标记来源。
8. 多币种记录：按币种分别显示，不能错误合计。
9. 持久化回算后：`model_calls` 与 `model_usage_periods` 的调用数、token 和费用一致。
10. 配置待重启时：费用区域附近清楚显示当前进程尚未使用新费率。

## 7. 当前可得出的实际结论

当前 57 条空费用记录并非不可估算。它们全部具备输入和输出 token；使用当前费率可以计算参考费用。现有“部分未知”把“调用当时未配置费率”误当成“现在仍无法估算”，并且隐藏了已经计算出的费用，因此属于报表逻辑和展示逻辑共同造成的问题。
