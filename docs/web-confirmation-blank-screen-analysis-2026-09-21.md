# 待确认行程导致网页白屏：原因与修复方案

日期：2026-09-21

范围：只读核对当前业务数据库、检查前后端代码，并用虚拟 API 响应在独立 React 测试中复现。未修改业务代码、真实行程或会话。本轮临时诊断测试运行后已移除。

## 1. 结论

白屏来自确认卡片的空预览：后端把 `null` 当作字符串预览返回；前端调用 `null.startsWith(...)` 抛异常，页面又没有 Error Boundary，导致 React 根节点被清空。

“连锁酒店／华住会／如家”不是致崩溃的特殊关键词。这条消息成功生成了新的待确认行程，因此触发了有缺陷的确认卡片渲染路径。模型回答已保存，不是模型无响应，也不是前一轮 SQLite 写锁错误。

另有独立问题：新酒店要求基于已保存版本重新生成候选，没有继承上一份未确认草稿里的节奏、交通和预算。只修白屏还不能解决这个接续问题。

## 2. 实际数据证据

目标会话：`09b86847af174743a481d603c10aac37`。

数据库中的本轮原话为“酒店我偏好连锁酒店，比如华住会旗下和如家旗下的”，与用户描述语义一致。

| 检查项 | 观察结果 |
| --- | --- |
| 后端 `/health/ready` | 返回 `status=ok` |
| 最新请求 | 2026-09-21 12:59:19（北京时间）提交 |
| 最新回答 | 12:59:41 已持久化至 `web_deliveries`，长度 852 字符 |
| 回答类型 | 原行程版本 2 的修改预览，尚未确认 |
| 对应事件 | `status=completed`，`prepared_reply=null` |
| 对应行程任务 | `status=collecting`，缺少 `confirmation` |
| 预览对应的已保存版本 | 版本 1 |

回答已经成功生成、保存并送达，而“发送已完成”和“用户已确认行程”是两个不同状态：前者不应该销毁后者需要的预览内容。

## 3. 白屏故障链

### 3.1 把临时发送缓存当作持久预览

`infrastructure/web_repository.py` 的 `context()` 从任务关联的 `processed_events.prepared_reply` 读取确认卡片预览：

```python
'preview': row['prepared_reply'] if row else task.initial_request
```

这里只判断数据库行是否存在，没有判断该列是否为空。实际上行仍然存在，列已经是 `NULL`，所以任务有效期内组装出的预览会是 `null`。

`infrastructure/memory_store.py` 的 `mark_outbox_sent()` 在投递完成后会正常清空 `prepared_reply`。这个字段是投递重试的临时检查点，其清理本身是既有设计；错误在于网页把它当作待确认预览的长期来源。

### 3.2 前端类型声明没有验证真实数据

`frontend/src/api.ts` 声明 `Confirmation.preview: string`，但读取 JSON 后直接 `return value as T`，并没有运行时校验。因此实际的 `null` 能进入 React 状态。

`frontend/src/App.tsx` 将 `c.preview` 交给 `Markdown`，后者立即执行：

```tsx
text.startsWith("旅行行程：")
```

空值导致错误：

```text
TypeError: Cannot read properties of null (reading 'startsWith')
```

这发生在 React 渲染阶段；请求函数的 `try/catch` 无法捕获后续渲染异常。`frontend/src/main.tsx` 仅包裹 `StrictMode`，没有错误边界，异常会使整个应用根节点卸载。

### 3.3 刷新为何仍然失败

应用先以空消息状态显示欢迎页，再读取 `localStorage['travel-active']` 自动恢复上次会话，然后加载消息与 context。加载到空预览后再次崩溃，因此表现为“新建聊天画面闪一下，随后白屏”。

刷新会重复请求相同的持久化状态，不能修正这一数据契约错误。

确认任务默认有效期为 30 分钟，过期后 `TaskRepository.recent()` 不再返回它。因此某段时间后刷新可能暂时恢复，但新建有效确认预览还会再次触发。不能把过期后恢复误认为问题已修复。

## 4. 已完成的独立复现

使用真实 `App` 组件及虚拟 API 响应：会话有消息，确认项的 `preview` 为 `null`，浏览器存储标记该会话为上次会话。测试不连接真实网页、不写业务数据库。

结果：

```json
{"error":"Cannot read properties of null (reading 'startsWith')","root_empty":true}
```

诊断日志：`E:/Agent/travel-blank-preview-repro.log`。

浏览器直接打开受影响会话的诊断动作遭遇自动权限审批超时，因此没有把浏览器控制台错误当作已捕获的现场证据；以上异常由独立 React 渲染实际复现，并与数据库及代码相互印证。

## 5. 另一个已确认的问题：未确认草稿的要求丢失

数据库中存在两份候选：

| 要求 | 较早的酒店预算预览 | 最新连锁酒店预览 |
| --- | --- | --- |
| 轻松节奏 `gentle` | `true` | `false` |
| 优先步行／公共交通 | 已保存于候选 | 没有该结构化约束 |
| 尽量少打车 | 已保存于候选 | 没有该结构化约束 |
| 住宿预算 | 200–300，人民币／间／晚 | 缺失 |
| 住宿要求 | 舒适一点，不要太贵 | 偏好华住会／如家旗下连锁酒店 |

原因是 `TripService.update_constraints()` 读取已保存的 `current['spec']`，没有以最近正在讨论的候选为修改基础；新候选生成时，原候选又被标记为 `superseded`。

两条消息相隔超过 30 分钟，较早确认任务也已经超过其短期有效期。需要区分“需求草稿还可以接续”和“旧确认授权是否仍有效”，不能将需求记忆完全依赖于确认任务 TTL。

这不是用户必须先确认每一句才能继续聊天的合理限制；系统应支持继续编辑草稿，再对最终候选进行确认与版本校验。

## 6. 建议修复顺序

### P0：使确认预览具有正确生命周期

- 将完整预览与候选及任务版本一起持久化，不再只依赖 `processed_events.prepared_reply`。
- 兼容现有任务时，通过当前用户／会话及准确事件关联读取已送达的预览；不能任选“最近一条回复”，避免展示与确认对象不一致。
- 无法恢复完整预览时返回明确的不可确认状态，引导重新生成；不要仅以用户原始请求或空字符串冒充预览。
- 保持确认所绑定的候选版本、行程版本和提醒规则校验。

### P0：前端错误隔离与可恢复界面

- 对接口预览做运行时类型校验，Markdown 组件能够处理异常值。
- 无有效预览时禁用确认按钮，并显示恢复入口；仅 `preview ?? ''` 会留下空卡片和可点击确认按钮，不足以完整修复。
- 增加页面级与确认卡片级错误边界。单张卡片异常不应使导航、其他会话及整个页面消失。
- 自动恢复上次会话失败时，仍允许返回首页或切换会话。

### P1：接续待确认草稿

- 同一行程连续补充要求时，基于最新可关联草稿做增量合并，保留预算、交通和节奏。
- 过期草稿可作为需求参考，但必须重新核对保存版本、政策与关联提醒，生成新的有效预览；不能直接恢复过期确认授权。
- 存在多份草稿或基础版本已变化时，澄清目标或展示冲突。

### 必须补充的回归

1. 完整投递结束、`prepared_reply` 清空后，context 仍能提供与候选版本一致的预览。
2. 已有异常数据、`preview=null`、缺失预览、自动恢复会话，都不应清空 React 根节点。
3. 无有效预览时不可确认写操作。
4. “节奏＋交通＋住宿预算 → 补充连锁品牌 → 最终确认”保留所有未被修改的要求。
5. 覆盖过期任务、版本冲突、删除会话、多会话隔离与旧数据兼容。

## 7. 为什么之前的测试没有发现

既有前端测试把 context 模拟为 `emptyContext`，没有覆盖实际待确认卡片。后端确认测试主要在发送完成前读取临时预览；真实接口脚本检查聊天回复、候选数据和确认结果，但没有实际渲染网页的确认卡片。

因此“后端整链路通过”和“前端测试通过”之间仍有组合场景缺口。此前的验证没有覆盖这个关键路径，需要补充上述跨投递生命周期的回归，不能仅增加对酒店关键词的识别。

## 8. 临时恢复与数据状态

聊天回复、已保存行程和候选仍在数据库中，白屏本身没有删除这些记录。

临时回到首页可在浏览器开发者工具中只移除当前会话选择，再刷新：

```javascript
localStorage.removeItem('travel-active');
location.reload();
```

这只改变浏览器的会话选择，不删除服务器聊天数据；重新进入仍有异常确认卡片的会话会再次触发，仍需修复代码。对于最新连锁酒店候选，不宜在恢复页面后直接确认：其中缺少上一轮尚未保存的预算和交通要求，应先正确合并并重新生成预览。
