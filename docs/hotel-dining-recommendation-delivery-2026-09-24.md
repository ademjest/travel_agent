# 酒店与餐饮候选优化交付汇总

日期：2026-09-24  
状态：已实施并通过自动化回归

## 1. 本次完成内容

### 自然语言要求与上下文

- 首次创建行程和已有行程修改两套入口均支持结构化住宿、餐饮要求。
- 支持酒店品牌、连锁要求、评分、靠近全程景点；支持餐饮品牌、菜系、特色关键词、评分、日期/餐次、忌口和过敏信息。
- 用户补充品牌、评分、预算或位置要求时，合并已有草稿和正式行程约束，不重新询问已知城市、日期和景点。
- 只调整酒店或餐饮时，原每日景点保持不变。
- 同一条消息可同时保存住宿和餐饮预算，不再被单一 `budget` 字段覆盖。

### 默认评分规则

- 酒店：“好一点”“评分高”且没有明确分数时，服务端应用高德评分 4.7 分。
- 餐饮：“评分高”“评价好”且没有明确分数时，服务端应用高德评分 4.5 分。
- 用户明确指定分数时以用户值为准，后续泛化描述不会覆盖明确值。
- 未提出高评分要求时，不自动增加评分门槛。
- 评分缺失不按 0 分处理，也不视为满足评分要求。

### 高德候选检索

- 酒店品牌要求实际生成品牌搜索词，例如“汉庭酒店”“如家酒店”。
- 餐饮根据菜系、特色和品牌生成搜索词，不再只搜索“餐馆”。
- 酒店和餐饮使用有限分页，每页最多 20 条、默认两页，并设置关键词和候选上限。
- 查询缓存键包含城市、关键词、类别、页码、条数和扩展模式。
- 使用 `extensions=all` 解析高德评分、参考消费、参考最低价、行政区和商圈。
- 继续沿用高德请求间隔和 `10021` 有界重试。

### 确定性筛选和排序

- 新增纯数据筛选模块 `core/place_recommendations.py`。
- 酒店根据品牌/连锁、评分、预算证据、所有行程日的平均距离和最远一天距离排序。
- 默认推荐同一家酒店兼顾全部行程日；休整日不按零距离计算。
- 餐饮可关联具体日期和早餐/午餐/晚餐，并根据该餐前后景点的位置排序。
- 没有指定餐次且没有明确要求结合行程位置时，仍提供简短全局餐饮清单，不自动填满每天三餐。
- 推荐结果分为“满足已核验条件”“部分条件待核实”“需要放宽条件的备选”。
- 严格品牌、评分、菜系等条件不满足时，会标明具体差异，不将候选伪装成达标结果。

### 距离和路线证据

- 所有候选先根据高德坐标在本地计算直线距离，避免为大量候选调用路线接口。
- 对启用位置要求的头部酒店，按已有交通偏好核验酒店到每日首个景点、每日末个景点返回酒店的路线。
- 对按餐次推荐的主选餐厅，核验前一地点到餐厅、餐厅到后一地点以及直接通行路线；数据完整时显示额外绕行时间。
- 每轮附加路线查询最多 12 次；超出后使用坐标距离并标记路线未核验。
- 没有交通偏好时不擅自使用打车或驾车时间。

### 预算与事实边界

- 酒店候选分别展示高德 `cost` 对应的参考均价和 `lowest_price` 对应的参考最低价；字段为空时明确显示高德未返回。
- 餐饮候选将高德 `cost` 显示为参考人均消费金额，并标注元/人。
- 当前高德酒店详情实测没有房型列表和房型价格字段，因此明确提示当前接口不提供具体房型价格。
- 酒店高德最低价或消费字段只作为非实时参考，不能证明指定日期的房价和库存。
- 酒店预算存在但实时价格未知时，明确显示“指定日期房价待核验”。
- 餐厅参考消费只有在预算单位明确为“每人每餐/每顿”时才进行参考比较。
- 餐饮参考人均符合预算也会注明实际账单待核验。
- 预算单位不可比较时不强行换算；未知价格不会被判定为预算内。
- 忌口和过敏无法通过 POI 名称确认时，明确提示向商家核实；明显冲突项进入备选或被降级。

### QQ 与 Web 展示

- 共用服务端候选结果，两种入口得到相同筛选逻辑。
- 回复显示实际筛选标准、默认/明确评分来源、评分、距离、参考价格、推荐依据和待确认项。
- 餐饮候选可显示“第 N 天 · 午餐”等关联范围。
- 旧版只有 `hotel_ids` / `restaurant_ids` 的行程仍能正常读取和显示。

## 2. 主要代码改动

- `core/place_recommendations.py`：候选类型识别、距离计算、预算参考、酒店和餐饮确定性排名。
- `core/trip_updates.py`：结构化酒店/餐饮约束、默认评分、多项预算、继承与覆盖验证。
- `agents/intent_compiler.py`：已有行程的酒店和餐饮语义解析规则。
- `agents/trip_planner.py`：首次行程需求解析、品牌/菜系分页检索、候选筛选和有限路线核验。
- `infrastructure/amap_client.py`：可控分页、扩展字段、行政区/商圈、评分和参考消费解析。
- `services/semantic_task_service.py`：将住宿和餐饮草稿上下文提供给解析器，多项预算缺失单位检查。
- `services/trip_service.py`：匹配状态、距离、预算证据、餐次候选和旧数据兼容展示。
- `tests/test_place_recommendations.py`、`tests/test_travel_discovery.py`：新增候选规则和高德字段测试。

## 4. 建议的人工验收场景

建议新建一个独立测试会话，先生成包含明确景点坐标的三日行程，再依次测试。每一步先检查预览，确认后再进行下一步。

### 酒店

1. `酒店换成汉庭或如家，必须是这两个品牌。`
   - 应实际搜索品牌；候选不能用独立酒店冒充。
2. `酒店要好一点。`
   - 应显示默认高德评分至少 4.7。
3. `评分改成至少4.5分，离每天景点都不要太远。`
   - 应保留用户明确 4.5，不重新应用默认 4.7；显示全程平均及最远距离。
4. `住宿预算200到300元，人民币每间每晚。`
   - 应显示高德参考均价和参考最低价；字段为空时显示未返回，不能声称预算内。
5. 选择一个前两天近、第三天远的测试城市或候选。
   - 排序和说明应体现最远一天，不只看平均值。

### 餐饮

1. `推荐一些当地特色餐厅。`
   - 应按特色关键词检索并给简短候选，不自动填满全部三餐。
2. `第二天午餐安排当地菜，离上午和下午的景点近一点。`
   - 应只生成第二天午餐候选，其他景点和酒店保持不变。
3. `餐厅评价好一点。`
   - 应显示默认高德评分至少 4.5。
4. `餐厅至少4.7分，每人每餐不超过60元。`
   - 应使用用户明确 4.7；显示高德参考人均消费，但必须注明实际账单待核验。
5. `第二天午餐不要辣，我对花生过敏。`
   - 不应声称商家一定满足；应显示配料和忌口待商家确认。

### 多轮和边界

1. 同一句提出酒店每晚预算和餐饮每餐预算，确认两类预算均保留。
2. 先要求酒店 4.5，下一轮只说“再近一点”，确认评分仍为 4.5。
3. 修改第二天景点后，再查看酒店和第二天餐饮，确认距离重新计算。
4. 严格要求找不到时，检查是否显示“需要放宽条件的备选”及未满足原因。
5. 高德查询失败时，应显示查询未完成，不应断言当地没有候选。

## 6. 当前限制和后续建议

- 高德 POI 不是酒店实时预订接口；要可靠按入住日期、房型和库存筛选，需要另接合法的酒店价格数据源。
- 当前高德 Web 服务没有返回具体房型及房型价格；如需“大床房/双床房/家庭房”的实时价格，需要携程、同程、酒店集团等具备授权的预订接口。
- 高德参考消费不保证等于用户实际账单；菜单、排队、订座、过敏原和临时营业信息需要商家或相应平台核实。
- 当前先以关键词分页检索和坐标排序完成附近推荐，没有依赖高德 App 的完整商家列表，也不能宣称获取全城全部酒店或餐厅。
- 如未来接入价格/菜单来源，应复用现有证据状态字段，不改变“未知不算达标”的规则。
