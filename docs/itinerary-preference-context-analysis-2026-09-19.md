# 研究转行程后补充偏好失去上下文：原因与修正方案

日期：2026-09-19  
范围：依据交付记录、当前代码、截图原句的纯函数复现及指定行程的只读数据库核对。未修改应用代码，未执行模型调用，未修改业务数据。

## 1. 结论与实测证据

核心问题是：已经保存的行程没有成为后续偏好修改的明确目标。消息经过多个规则入口后，落入了交通查询分支；这不是行程数据库丢失城市、日期或天数。

截图对应行程 `TR-bb334b865ee3` 的实际保存状态：

| 字段 | 值 |
| --- | --- |
| 城市 | 武汉 |
| 开始日期 | 2026-10-01 |
| 天数 | 3 |
| 版本 | 1，未被这次偏好消息更新 |
| 交通方式 | 空 |
| 轻松模式 | false |
| 创建时采用的长期偏好 | 空，preference_version=0 |

对截图原句“我喜欢轻松一点的行程，然后不太喜欢打车，尽量步行或者公交地铁出行”的静态函数复现结果：

```text
preference_request → False
trip_request → False
completed itinerary 的 trip_continuation → None
decide_travel_action → intents=(transit,), needs_clarification=True
固定回复 → 请告诉我出行起点和终点，以及所在城市。
```

对应时间段数据库中，原 itinerary 任务为 completed，随后出现了一个 transit/collecting 任务，缺失字段为 origin、destination。实际 Web 投递内容与上面的固定回复一致。该轮有一次模型调用记录，但没有保存模型原始 IR，不能断言它具体输出了哪一种操作；可以确认最终进入了固定交通澄清路径。

截图最后实际追问的是“起点、终点和城市”；前一轮“计划玩几天”是另一个日期范围处理问题，需要分别修复。

## 2. 原因链

### 2.1 长期偏好与当前行程修改是两种不同操作

[PreferenceService](../services/preference_service.py) 主要识别“记住”“保存偏好”“我一般喜欢”等表达。截图中的“我喜欢轻松一点的行程……”不满足这个入口，因此这句话本身没有进入长期偏好保存流程。

即使通过偏好面板另外保存，交付记录也明确约定“更新偏好不自动修改已保存行程”。[TripService._apply_preferences](../services/trip_service.py) 仅在新建路径调用，且 spec 已有 preference_version 时不重复应用。这是保护旧行程的合理设计，不应简单删除这个保护来强行刷新所有行程。

当前真正缺少的是：把对话中的这句话理解为“调整刚生成的这份行程”，同时不要未经授权将它升级为永久偏好。

### 2.2 行程服务仍用特定句式判定是否进入

[TripService](../services/trip_service.py) 的 trip_request 要求“规划行程”“行程改为”“第二天改……”等表达；trip_continuation 主要接续 collecting 状态的 itinerary。

行程生成后对应任务已经 completed。截图句子没有命中“修改”表达，于是在读取并选择已存行程之前就返回 None。虽然代码有 `_select_trip`，这个选择器没有机会工作。

后续的 editing 判断也依赖“改／调整／换”等词，transport_change 仅匹配“改成／改为……公共交通／步行”等模式。因此，只放宽最外层入口还不够，下一层仍可能将请求当成新建，或无法生成正确的修改动作。

### 2.3 语义编译器接通了提醒，尚未接通这种行程变更

[SemanticTaskService](../services/semantic_task_service.py) 向模型提供的是待完成提醒上下文；普通情况下只编译当前消息，没有提供当前行程的城市、日期、版本、日程和约束摘要。

它支持的 trip 操作主要是删除活动、查看行程和确认待执行变更，没有 `update_constraints` 一类针对节奏、交通和兴趣的更新操作。即使模型理解了用户希望“更轻松”，缺少可执行操作时仍会退回旧路径。

所以，“已有 LLM 解析”与“LLM 有正确上下文并能调用对应更新操作”是两件事。

### 2.4 通用交通规则提前返回，历史还没交给回答模型

[travel_decision.py](../agents/travel_decision.py) 发现“公交／地铁／公共交通”就标记 transit，没有先区分“交通偏好”与“查询一条交通路线”。

[TravelAgent._run](../agents/travel_agent.py) 在构造包含历史的模型 messages 之前，发现缺少路线端点便返回固定追问。这一轮即使 ContextBuilder 已取出历史，也无法靠增加上下文长度改变这个提前返回。

只读检查中，研究回复约 1401 字、行程回复约 712 字。没有证据表明本次是上下文窗口不足；代码中的提前返回及错误 transit 状态足以解释现象。

### 2.5 后续更新还存在字段覆盖风险

[TripPlanner.extract](../agents/trip_planner.py) 虽从 previous 复制旧状态，但随后使用 `value.get(key, previous.get(key, ''))` 写回字段。模型若返回显式空字符串，旧城市、日期等仍可能被覆盖；空数组也可能清掉旧约束或必去地点。

因此，修好路由之后，还应把“只更新本轮明确变化字段”作为执行契约，而不是让模型每次重新输出一份完整需求。

## 3. 日期范围为何又问三天

当前抽取结构主要包含 destination、duration_text、start_date_text，没有 end_date。day_count 依赖 duration_text 中“三天／3日”等表达计算；没有对“10月1日到10月三日”建立日期区间并计算天数的确定性流程。

网页攻略里提到三日游，并不等于用户这次一定要求三天；但用户明确给出的起止日期可以成为更强依据。建议增加带来源的起止日期字段，在日期与年份消歧后，由代码按包含首尾两天的旅行口径计算：

```text
2026-10-01 至 2026-10-03 → 3 个日历天
```

仅在起止日期、天数或年份确实矛盾时追问，而不是已经知道区间却再次机械询问天数。这个结论来自当前 schema 和计算路径；没有读取到该轮模型原始字段，不能把某个具体空字段输出当作已观察事实。

## 4. 推荐修正结构

```text
用户本轮消息
  + 当前会话正在讨论的行程摘要与版本
  + 当前研究摘要／引用标识
  + 尚未完成的任务
  + 已确认的长期偏好（默认值）
        ↓
LLM 识别目标与动作
  当前行程更新／新建行程／保存长期偏好／独立路线查询／澄清
        ↓
服务端绑定实际资源，并校验权限与原始依据
        ↓
对旧行程应用增量约束 → 重规划受影响部分 → 变更预览与确认
```

### 4.1 显式选择当前对象

优先使用用户明确指向的行程、引用的行程消息或界面所选行程；没有明确选择时，可以使用同一会话中唯一且明确正在讨论的行程。存在多份候选且无法消歧时，仅询问选哪份行程，不重新询问已知城市和日期。

不要依赖 LLM 从长篇聊天里重新猜数据库 ID。复用 `_select_trip`、消息关联及 owned trip 查询，并把候选摘要交给模型；由服务端解析目标引用和版本。

已完成的计划仍然是可以修改的业务对象，不能因为生成任务 completed 或任务上下文过期，就丢失行程关联。持久行程与短期任务应分开管理。

对于已经误建的 transit 待办，只有确认它就是本次误分流产物时，才将其标记为被替代，避免它继续把下一句拉回“起点／终点”追问。不能因此批量取消用户其他尚未完成的真实查询。

### 4.2 增加受约束的行程更新操作

新增类似 `trip/update_constraints` 的结构化操作，表达本轮变更，而不是再次生成“请规划……”的字符串并送入旧正则入口。

截图请求应被解释为以下含义，字段名仅为方案示意：

```json
{
  "domain": "trip",
  "operation": "update_constraints",
  "target_ref": "current_trip",
  "changes": {
    "pace": "relaxed",
    "transport_preferences": {
      "preferred": ["walking", "public_transit"],
      "discouraged": ["taxi"]
    }
  },
  "memory_scope": "current_trip"
}
```

日期、目的地、天数、研究引用、未被修改的必去地点均从原行程继承。本轮没说的字段不是空值；只有明确的清除动作才能移除已有值。服务端绑定 `TR-bb334b865ee3` 及其当前版本，模型不能任意指定其他用户或会话的资源。

### 4.3 临时要求与长期默认分别处理

“我喜欢轻松一点”出现在当前行程后，优先作为本次行程调整。只有“以后都这样”“帮我记住”或用户接受偏好建议，才保存到跨会话默认。

本轮明确约束优先于原行程约束与长期默认；不要把当前偏好全部覆盖到旧行程，也不要把本次变化自动写成永久画像。

若一句话同时要求“记住”和“调整当前行程”，应识别为两个明确动作，分别回执；不能由偏好服务提前 return 后吞掉行程修改。

### 4.4 交通偏好与交通查询分开

“尽量步行或公交”没有请求从 A 到 B 的路线；不要因此创建 transit 待办。更新行程后，每一段交通的起点终点来自已选 POI，通常无需让用户重复填写。

当前交通字段主要是单个 transport_text，长期默认也只能单选。原 add_route_evidence 还会优先选公交模式，并因字符串含“不／别”直接退出。因此应将正向偏好、弱避免和禁止分开建模，不能把整句否定表达直接塞进单个模式字段。

截图中的“不太喜欢／尽量”是偏好，不应擅自升级为绝对禁令。可优先安排近距离步行及公共交通，交通证据不足时说明缺口，不冒充已经核实。

### 4.5 复用已有变更与版本机制

先生成较轻松的日程候选，重查受影响的交通。涉及删除景点、调整日期或关联提醒时，沿用既有预览、版本校验和用户确认。

同一行程保留原 trip_id，确认后版本递增。不要新增一份无关联行程，也不要只在文字回复中说“改好了”而数据库保持版本 1。

## 5. 针对截图的预期行为

合理回执示例：

> 我会调整刚才的武汉三日行程，保留 2026 年 10 月 1—3 日的日期。安排会更轻松，优先步行和公共交通，尽量减少打车。下面是修改预览；这次先只应用到这份行程。

之后展示实际变更及交通依据；需要确认时让用户确认改动。不能重新追问已经保存的城市、天数，也不应把“轻松”简单等同于增加长距离步行。

## 6. 改动与验收优先级

| 优先级 | 改动 | 验收 |
| --- | --- | --- |
| P0 | 当前行程上下文进入语义解析；增加 update_constraints 分派 | 原截图最后一句进入行程更新，不能新建 transit 待办 |
| P0 | 行程字段增量合并、资源绑定、版本校验 | 原城市／日期／天数／来源保留，同 ID 更新或生成待确认预览 |
| P1 | 临时偏好与长期保存分流，避免前置服务吞掉复合请求 | 调整当前行程不自动更改长期 profile；明确保存才更新默认 |
| P1 | 混合交通与负向偏好结构化 | 不询问无意义的起终点，不丢失“尽量少打车”的约束 |
| P1 | 起止日期抽取及天数推导 | “10月1日到10月三日”得到三天；冲突才追问 |
| P1 | 调度决策可观测性 | 记录操作类型、上下文资源绑定、拒绝／回退原因，不默认记录完整私密对话 |

必须补充整条回归：研究武汉攻略 → 规划 10 月 1—3 日 → 成功保存行程 → 口语补充节奏与交通 → 原行程更新并保持日期和城市。再验证多行程消歧、切换成真正路线查询、无当前行程、上下文过期、重启恢复及并发版本冲突。

原升级中的偏好保存、跨会话读取、新行程采用默认偏好等测试有价值，但不等于已验证“已生成行程的自然语言偏好修改”。本次没有执行新的完整测试或真实模型调用，纯函数路由复现与只读数据核对结果见上文。

## 7. 不建议的修补

- 继续给 trip_request 或 preference_request 加“我喜欢”“不太喜欢”等字符串，只会覆盖有限句式。
- 仅扩大历史消息或换大模型，无法改变模型 messages 生成前的固定 return。
- 为这个问题先引入向量数据库，不能解决目标绑定、更新操作和字段合并缺失。
- 取消 preference_version 保护，导致更新长期默认后无提示改动已保存行程。
- 重新创建行程或要求用户重复城市日期，掩盖实际的接续失败。
