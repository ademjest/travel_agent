日期：2026-10-16。范围：当前本地工作区及已有验收记录。

状态：**已批准，分批实施中。** 10月16日已实现B0最小诊断及B1核心读取，两批各12次真实请求分别审计；第二批完成Q04新生成、v4.3有限校验修复、捕获摘要恢复后的Web末端验收及研究依据改进。摘要整体真实质量门槛尚未通过，当前变更未部署正式服务。见[首批交付](optimization-b0-b1-b2-delivery-2026-10-16.md)及[第二批交付](optimization-second-batch-delivery-2026-10-16.md)。以下设计与原基线保留供追溯，最新状态见第9节。

## 1. 总体判断与目标

项目已具备结构化意图、任务接续、行程预览确认、有限工具调用、执行租约、版本检查、Inbox/Outbox、用途级上下文及模型预算账本。摘要 v4 已补齐共享契约、有限语义保护、版本哈希、失败分类和完整条目渲染。下一阶段应围绕现有能力提升一致性与可验证性，不以新增框架、多 Agent 或扩大上下文作为默认方案。

主要目标：

1. 同一种外部查询，在即时问答、定时任务和行程规划中具有一致的错误含义、重试边界及结果状态。
2. 能区分“模型生成了”“通过校验并发布了”“实际注入了”“后续正确使用了”，验证摘要 v4 的真实收益。
3. 用户反馈错误时，能够沿意图、上下文、检索、工具、状态和投递路径定位问题。
4. 研究与行程建议的关键结论有可核验依据，证据不足时准确表达未知。
5. 先建立质量基线，再优化检索、模型分工和费用；持续保留权限、取消、遗忘和预算保障。

本方案中的优先级表示实施顺序，不代表已发现同等级的线上事故。代码观察、历史实验结果与待验证风险分别标记。新增数值门槛属于**建议验收标准**，不是现有成绩或真实调用授权；已有经确认的测试金标准继续优先使用。

## 4. 分项优化设计

### 4.1 O01：完成摘要 v4 的真实质量闭环

**保留成果。** 复用 [summary_contract](../core/summary_contract.py)、[摘要服务](../services/conversation_summary_service.py)、[有限语义校验](../core/summary_semantics.py)及现有 Q01—Q09 测试体系。用户确认的[提示原文](prompt_design/abstract_design_prompts.md)继续作为唯一来源，不在总体方案阶段改写。

**实施步骤。**

1. 固定语料、事实金标准、用途模型、档位、提示哈希和回答模型，登记本轮调用及费用预算。旧轮次已耗尽的 12 次授权不复用；本方案不发起新调用。
2. 第一轮优先覆盖旧失败的 Q01/Q02/Q03/Q06，以相同条件生成 v4 新响应。记录原始输出、发布与否、错误类别、版本、覆盖进度及实际渲染结果。预算不足时按预登记顺序缩小范围，不省略失败结果。
3. 对已发布摘要做完整用户原文、仅实际渲染摘要、无早期事实三个隔离条件的回答对照；再测约束应用和未知信息。金标准不进入模型输入，后续组不能继承前组回答。
4. 再进行真实 Web 路径验证：保留原触发阈值，使早期关键原文退出最近对话和群消息两条通道，检查实际注入版本/哈希，确认答案不是从原文泄漏获取。
5. 对核心用例做少量独立重复并加入未参与提示优化的改写留出集。报告每次结果与样本数，不把小样本重复写成统计显著。

**验收。** 沿用既有金标准；Q03 多主体和预算单位、Q02 人数房型、Q06 名称等针对性事实应在有效渲染摘要中完整保留。未知信息不编造，旧值不冒充当前值，删除/遗忘来源不恢复。分别报告生成事实覆盖、发布率、有效注入覆盖和下游正确率；来源引用中有信息但正文没有，不能算已注入保留。

**失败处理。** 区分模型遗漏、结构拒绝、语义误拒、发布竞争、渲染省略与回答误用。只有定位后才提出下一次小范围修改，不通过扩大窗口、提高条目数、截掉非法来源或硬编码答案通过测试。

**重建边界。** 10 月 15 日审计没有发现有效旧摘要需要批量升级；不因此开发全量重建器。仅在具体会话出现已确认的旧摘要遗漏时，按既有单会话重建策略评估来源、版本和费用。从仍有效的原始用户历史恢复，不从旧摘要猜测，也不发布覆盖尚不完整的重建中间版本。

### 4.2 O02：统一工具结果与有限重试

**当前问题。** [ToolResult.from_text](../core/tool_result.py)仍按前缀及关键词推断错误；[即时工具 Router](../tools/reservation_tools.py)有结构化回执和读取次数记录；[定时查询](../services/scheduled_query_service.py)仍调用 execute_tool 并检测错误前缀；[行程规划](../agents/trip_planner.py)存在直接调用高德客户端的路径。v4 修复的是定时意图的模型输出截断，不是这几条外部调用路径的统一。

[retry_read](../core/tool_execution.py)已有有限次数和期限检查，但没有抖动；高德临时错误常使用固定 5 秒等待提示。未来接入服务端 Retry-After 时，不能把超出本地上限的等待值简单截短后提前重试。

**最小实施范围。**

- 先覆盖天气/预报和路线，再覆盖地点搜索与研究；不先构建全用途插件系统。
- 在服务边界统一成功、缺项、业务不可用、权限、参数、限流、暂时故障和执行状态未知的含义。保留旧字符串适配供兼容，逐模块迁移调用者。
- 逐工具定义必要数据字段与单位；分开保存机器可读结果和用户展示文本。不要因为统一了外层 dataclass 就声称所有返回已校验。
- 只对明确可重试的读取失败实施有界退避与随机抖动；有效 Retry-After 作为最早重试时间。超过剩余期限时停止或调度下一次，不提前调用。
- 打通单次调用、任务恢复和 SDK 的尝试次数口径，避免嵌套重试相乘；继续关闭不受控的 SDK 隐式重试。取消后不开始下一次重试，成功回执复用不重新访问上游。
- 写操作保留现有业务幂等、归属和版本检查，不套用只读重试。结果未知先核对状态，保持部分成功回执。

**验收矩阵。** 在即时问答、定时查询、规划三条路径分别注入：超时、429、503、权限失败、错误 JSON、必要字段缺失、业务无结果、取消发生在退避中。检查物理请求数、错误分类、剩余期限、任务状态和用户文案。永久错误不自动重试；暂时错误不超预登记次数；无结果不伪造成功事实；已提交写操作不重复执行。

### 4.3 O03：将已有摘要诊断接入最小执行时间线

**当前问题。** 摘要服务和 ContextBuilder 已支持 diagnostics 回调，但 [build_runtime](../app/runtime_factory.py)当前装配没有传入统一诊断接收器。摘要已有分类日志和只读工具，缺的是跨层关联、检索/裁剪原因与便捷回放，不是“完全没有日志”。

**实施范围。**

- 使用已有 event_key/job_id/task_id/call_id 关联事件；增加阶段、时间、任务版本、提示版本/哈希、上下文策略、来源 ID、是否裁剪/回退、错误码、重试次数和最终状态。
- 第一版只落必要元数据到现有日志或轻量存储，提供按事件导出的命令；暂不引入独立监控平台或复杂页面。
- 将摘要 disabled、threshold_not_met、旧版复用、生成失败、发布拒绝、注入版本等状态与工具和模型记录串联。计量失败或诊断失败不得改变业务完成结果。
- 失败现场需要正文时，只保存受控的最小脱敏快照；定义访问范围、保留期，并纳入会话删除、遗忘和来源失效处理。非内容费用账本继续独立。
- 复用历史工具输出进行离线诊断回放；模型重新生成另列为付费实验。回放默认禁止真实消息投递和业务写操作。

**验收。** 为摘要缺失、地点歧义、预算阻断、上游超时、旧版本提交失败各保留一条可追踪链。任一失败样本应能区分发生阶段及是否已有副作用；日志不含密钥，诊断接收器异常不影响业务，删除会话后不能通过诊断快照恢复已删除内容。

### 4.4 O04：补充关键事实与约束的证据验证

**当前问题。** [研究汇总](../services/research_service.py)检查来源 ID 是否存在，但尚不能自动证明来源支持结论；[行程校验](../agents/trip_planner.py)能检查日期序号、POI、夜游、必去地点等，但不能仅凭 POI 存在证明目标日期开放、价格符合预算或适合行动受限者。

**实施范围。**

- 先选开放/预约日期、价格及单位、交通方式、用户明确禁止事项等少数关键字段，不尝试通用自然语言证明器。
- 对高风险事实保留原文片段、来源及适用时间；区分用户要求、来源陈述、程序检查结果和模型建议。抓取时间不能充当发布时间。
- 对确定性字段做程序校验；证据不支持或来源冲突时保留未知/冲突，并在用户实际需要决策的位置表达。
- 研究到行程的转换携带必要依据和约束，防止报告阶段标“未核实”，规划阶段却变成确定结论。
- 复用 v4 的预约语义修复；“需预约但无提前规则”不能生成假定的开约提醒，也不推断已预约。

**验收。** 使用旧政策与新政策冲突、其他城市同名景点、币种/计价单位缺失、只读到搜索摘要、禁止打车、行动时长受限等固定反例。目标是关键反例全部正确处理；来源编号真实但结论不受支持仍判失败。自动校验仅覆盖明确字段，其余依靠人工标注留出集评价。

### 4.5 O05：以真实失败类型改善 RAG

**当前问题。** [文档服务](../services/document_service.py)采用约 1800 字符切分和 200 字符重叠，主要按换行/句号寻找边界；复杂表格、条款与例外关联尚未充分利用。[词法/哈希融合报告](../evals/v3-retrieval-offline.json)在 100 个合成场景中 Recall@5 从 83.53% 到 89.41%，但无答案误召回从 0% 到 20%，结论为 No-go。它不是训练过的语义 embedding 的效果结论。

**实施顺序。**

1. 保留现有 FTS 基线，补充真实或公开授权旅行文档，按文档/主题划分开发与留出集，避免相邻 chunk 泄漏。
2. 将问题分为精确词、同义表达、跨段规则、表格、版本冲突和无答案；先记录正确证据的 chunk ID、范围及日期。
3. 优先尝试标题/段落/表格感知切分、必要元数据、父段补充与版本过滤，每次只改变一个主要因素。
4. 仅当同义类仍是主要失败来源时，再评估真正的语义索引及融合；登记模型来源、数据范围、资源成本和更新策略。

**验收。** 同时报 Recall@k、Hit@k、MRR/nDCG、无答案误召回、回答忠实度、延迟和成本。沿用既有上线门槛；缺少真实留出基线时不新编一个已经达成的数字。不以召回率单项上涨为上线依据，且必须保留权限过滤、删除同步和词法回退。

### 4.6 O06：优化上下文选择，检验未覆盖纠正与容量竞争

**当前问题。** [用途策略](../core/context_policy.py)仍主要采用固定字符额度；[上下文构建](../agents/context_builder.py)的部分相关性判断依赖关键词。v4 已避免切半条摘要，但 [render_summary](../core/conversation_summary.py)达到含引用的总长度限制后会停止添加后续条目，因此“全部发布条目”与“实际注入条目”仍可能不同，这是有界设计的取舍，需要测量而非直接认定为缺陷。

另一个待验证场景是：旧摘要仍通过来源检查，但新的纠正尚未进入已覆盖批次，且随后离开近期历史。来源仍有效不一定代表事实仍是最新；是否发生及造成什么影响，应通过用例确认。

**实施范围。**

- 在 O03 中记录条目级注入/省略原因、覆盖水位和关键来源，先判断问题是提取、选择还是容量。
- 增加多任务切换、多个候选方案、跨午夜、长工具结果、未覆盖纠正和偏好删除场景。
- 用户明确的当前任务约束进入已有业务状态；不要将所有临时事实自动升级成长期偏好，也不让摘要模型猜测哪些事实已入库。
- 如果回退旧值风险被复现，最小修复优先考虑保留未覆盖的明确纠正/待办作为有界上下文，或标明状态待确认；不因每条新消息废弃整个摘要。
- 只有证据表明分配不合理，才调整相关用途额度或条目优先级；保留完整结构与必要引用。

**验收。** 关键事实退出两条近期历史后，最新限制仍被正确使用；已遗忘偏好不重新出现；同一场景能解释条目为何被省略。涉及必要状态超限时明确停止/澄清，不静默丢失约束。不得靠统一扩大历史窗口通过测试。

### 4.7 O07：明确恢复、投递与停止语义

**保留成果。** 继续使用 Inbox、ExecutionScope、数据库事务与版本检查、成功回执和 Outbox。取消后拦截迟到写入，已经提交的操作不承诺自动回滚。

**当前边界。** [Outbox](../services/outbox_worker.py)为 Web 提供 delivery_key，QQ 没有相同保障。外部已发送但本地未确认时仍可能重复投递，这是确认丢失窗口，不等同于已经观测到线上重复事故。通用 Agent 的 4 步/6 工具限制可以止损，但是否过早停止复杂任务缺少分类统计。

**实施范围。**

- 在测试环境注入：业务提交后崩溃、发送成功后确认丢失、租约更换、取消与完成竞争、恢复时预算已耗尽。
- 将投递可确认失败与状态未知区分；检查平台是否支持查询或幂等能力。没有平台支持时，明确至少一次投递的限制及重复消息识别方式，不虚称跨平台 exactly-once。
- 记录终止原因和已完成/未完成事项，保留当前部分成功语义。先统计各任务触达步数上限的比例及有效进展，再决定是否仅为特定任务调整限制。
- 人工兜底先使用明确的状态说明和后续操作指引；当前没有客服团队或人工队列时，不声称已经“转人工”。

**验收。** 已提交本地业务不因重放重复产生副作用，取消后无迟到业务写入，未知外部结果不被标为确定失败/成功；Web 幂等投递回归继续通过。QQ 不可消除的窗口作为残余限制记录。不要仅为“成功率”延长所有任务或无限重试。

### 4.8 O08：从费用记账推进到成功任务成本优化

**当前问题。** [模型网关](../infrastructure/model_gateway.py)和独立账本已覆盖用途、预算、费率快照、未知 usage 与迟到结算，不能重复作为待实现项。剩余缺口是真实摘要净收益、用途模型选择、缓存收益，以及搜索/地图等外部调用对完整任务成本的影响。

**实施范围。**

- 先按业务 run 汇总模型调用、真实 usage、失败/修复/重建成本和外部请求次数。无费率或无 usage 的部分标未知，不按零计算。
- 摘要对照计入生成、增量更新、失败和必要重建，再计算后续调用节省；短会话可能不节费，应如实报告。
- 候选用途模型、缓存和上下文档位分开实验，固定其他条件。缓存冷/热组交错运行，区分供应商缓存用量与应用结果缓存。
- 复用 service_probe 计量；连通测试本身有消耗，但通过不意味着已证明工具调用或复杂 JSON 能力。

**验收。** 在质量门槛达标的同类任务上，比较总成本/成功任务数、P50/P95 延迟、失败与修复率，并同时报告样本量和费用未知比例。供应商账单与本地估算分开。当前不预设“必须节费20%”等没有基线的结论，不通过删除明细重置已消费预算。

### 4.9 O09：按模块治理提示与契约，控制维护成本

**当前问题。** [意图编译](../agents/intent_compiler.py)、[语义任务服务](../services/semantic_task_service.py)与行程模块包含多个领域及接续规则；快速路径、语义路径和传统入口需要保持一致。摘要 v4 只在少数领域完成共享契约迁移，不意味着全项目已统一。

**实施范围。**

- 以现有[提示词清单](prompt_design/project-prompt-inventory-2026-10-14.md)登记用途、唯一来源、版本/哈希、输入输出契约和测试集，避免再建重复台账。
- 选择住宿/餐饮预算或接续输入一个高频模块试点，共用子契约；区分未提及、追加、替换、明确清除。
- 拆分 current_message、confirmed_state 与有来源的历史补充，保持既有字段验证，不让历史文本变成新授权。
- 如需按领域装配提示，复合意图必须装入所有相关规则，不能只保留首个意图；先验证与现有完整提示的行为等价。
- 大文件按本轮功能边界逐步迁移职责，不进行全仓库格式化或重写。框架替换、微服务、多 Agent 不作为本阶段目标。

**验收。** 固定旧行为回归通过；新增改写、否定、指代、预算单位、同句多需求用例不退化。必须测错分流风险，不能只用提示长度下降作为成功。每次变更具备独立回滚范围。

### 4.10 O10：建立真实端到端留出集与交付证据

**当前问题。** 875 项后端测试、120 个脚本模型装配场景、历史真实模型固定工具测试和部分真实地图验证，分别覆盖不同边界；不能合并成一个“线上成功率”。

**实施范围。**

- 保留三层独立报告：L0 确定性故障与契约测试；L1 真实模型配固定工具，观察语义波动；L2 真实模型和真实读取服务的完整用户流程。
- L2 首批建议 20 个独立场景，覆盖查询接续、研究到规划、约束修改、长会话摘要、失败恢复，每类4个；该数量是计划，不替代已有完整用例，也不足以估计长期可靠性。真实提醒/投递在隔离目标中验证，不发送给无关用户。
- 预先定义每个场景的完成条件、硬约束、可接受澄清与未知回答。失败重跑不能覆盖首次结果，环境故障与模型/代码失败分别统计。
- 记录代码清单、提示哈希、语料哈希、档位、用途模型、时间、物理调用数、Token、费用及未知项。留出答案不进入模型输入。

**建议准入。** L0 相关回归全通过；L1/L2 测试中越权、重复业务副作用、已取消后迟到写入、把未执行说成已完成等关键反例零失败。首批 L2 总体至少18/20符合预定完成条件，任一关键错误仍不准入；随后扩大和重复观察。该门槛只用于首批筛选，不宣称系统已达到90%长期成功率。已有更严格门槛优先。

## 6. 统一指标与防止误判的规则

| 指标 | 计算/解释 | 常见误判 |
| --- | --- | --- |
| 摘要生成事实覆盖 | 新生成输出中正确表达的目标事实/目标事实数 | 未发布输出不能算系统已记住 |
| 摘要发布率 | 校验并发布成功的逻辑生成任务/逻辑生成任务总数，另列物理调用数 | 一次结构修复不能隐藏首次失败和成本 |
| 有效注入事实覆盖 | 实际发送给回答模型的摘要正文中正确表达的事实/目标事实数 | 仅存于sources引用中不等于注入 |
| 下游约束满足率 | 正确应用的适用约束/全部适用约束 | 只会复述事实，不等于能应用限制 |
| 工具恢复率 | 可恢复故障注入后在预算内完成的任务/该类任务数 | 权限错误不应靠重试变成成功 |
| 错误完成率 | 未完成却向用户宣称完成的任务/已评估任务数 | 返回200或生成自然语言不等于业务成功 |
| RAG质量 | 召回、排序、无答案误召回和答案支持度分别报告 | 引用ID有效不等于事实成立 |
| 成功任务平均成本 | 同类全部尝试的可计价总成本/满足质量条件的成功任务数 | 缺失usage不等于零；失败成本不能剔除 |
| P95端到端耗时 | 同类任务从接收至可见结果的耗时，注明排队和重试 | 只测模型耗时忽略队列和投递 |

## 7. 发布、回退与本阶段不做事项

- 每批只修改对应功能及必要测试，保留现有未提交工作；不使用整仓reset清理用户改动。
- 数据库变更优先采用兼容的加法迁移，先做副本演练；正式备份使用SQLite一致性备份。代码回退不直接覆盖已有新业务数据的整库。
- 默认不扩大历史窗口、摘要条目数、Agent步数或全局输出预算；任何调整都需要相关任务的质量/成本对照。
- 不重复实现摘要v4已完成的契约与语义反例；不自动接入repair_permit，不全站重建或删除旧摘要。
- 不把外部文件、研究网页或摘要中的文字当成操作授权；不让优化绕过权限、版本、取消、遗忘和费用控制。
- 不以本地单用户应用的现状要求立即迁移数据库、建设多租户、微服务或独立监控集群。多人公网部署属于单独需求，应另评鉴权、隔离、并发与运维。
- 真实API实验、单会话重建及正式发布按后续明确的范围与额度执行；本文交付不触发这些操作，也不需要为编写方案本身另行审批。

## 8. 方案维护方式

后续每完成一批，新增对应交付报告，并在问题总表旁登记“已实现/离线通过/真实质量通过/正式生效”四种独立状态及证据链接。已完成条目不因后续总体分析再次变成待实现；只验证了机制的条目不提前标为真实质量通过。

本方案核心取舍是：**保留现有工程保障，先补一致性、诊断与真实质量证据，再依据可复现失败优化记忆、检索和费用。**
