## 本轮改动

| 问题 | 实施结果 | 验证 |
| --- | --- | --- |
| R1 图片内容复用导致所有权错误 | 创建入口显式传入当前发送者；共享图片的首次上传者不变 | 同群 A/B 同图各自拥有草稿、事件重放复用、跨群隔离 |
| R2 调用工具不等于完成动作 | 工具结果增加结构化状态、动作、对象、数据、错误码等字段；登记完成前检查成功状态和动作/对象；校验 schema；预约查询只开放读工具，排除常见否定指令中的写动作；完成摘要使用执行回执 | 无效 JSON、失败、错误动作、错误编号均不能放行成功；预览需要人工确认时立即结束 Agent 回合 |

| R4 误触发与澄清 | 日期词需结合天气语义；非 @ 文本需明确请求信号；常见无地点天气问题直接返回 `needs_input`；最近一次天气澄清可在 30 分钟内由同群同用户的短地点回答恢复 | 普通聊天不触发、成员隔离、过期澄清、地点续问、真实模型与高德查询 |
| R5 查询缓存过期 | Agent 不缓存预约工具；预约执行器不持久缓存 list/refresh；写操作继续保留原有幂等记录；失败的外部查询不缓存 | 同事件读—写—读读取新日期；失败查询可以再试；原有写操作幂等测试 |
| R6 行程版本混合与确认内容变化 | 保存日期来源文档 ID、文件名、证据片段和人工/推断来源；检测新选中文档与已确定日期的冲突，暂停自动合并；用户显式填写日期可确认自己的选择；确认前刷新产生新日期时先返回草稿，下一次确认才落提醒 | V1/V2 冲突、人工保留原日期、来源可追溯、预览后再次确认、Agent 不得自行重试绕过预览 |

`date_source_json` 与 `plan_version` 在打开数据库时自动迁移；没有来源的旧数据保留为“历史记录/来源未知”，不会伪造文档来源。日期来源变更沿用项目的 `updated_at`。`state_version` 是结果协议的可选字段，目前旧文本执行器适配结果可以为空；确认一致性由数据库版本检查保障，不依赖模型回传版本。

工具调用仍顺序执行。`list_reservation_plans` 仍保留刷新草稿的既有行为，因此不能作为纯读操作并发执行。文档仍按覆盖目标景点数优先、同分按新文档优先选择；不是无条件采用最新上传文件。跨旅行的显式文档选择、人工日期与新文档的提示式比较、完整审阅版本令牌仍是后续工作。

自然语言权限收窄采用确定性信号，不能视作完整语义授权解析。复杂的多对象、多动作指令建议用逗号分开并分别写编号；歧义指令会要求澄清。用户只问查询时不开放确认/取消工具，数据库仍绑定当前群和创建者权限。

## QQ 测试群验收

1. 保留当前 NapCat 登录状态。在承载 Python OneBot 服务的终端停止旧服务后，在 `(agent)` 中重启 Python 服务以加载新代码。使用原启动命令；默认本地入口示例：`python -m uvicorn adapters.onebot_app:create_runtime_app --factory --host 127.0.0.1 --port 8000`。如果当前上报端口不是 8000，保持原端口和绑定地址。
2. 在白名单测试群中发送“明天一起吃饭”“这份文件我晚点发”：应不回复。然后 @ 机器人发送“现在天气怎么样？”：应只追问一次城市；直接回复“西宁”：应查询真实天气。
3. 由两个群成员分别发送“制定预约”，再上传同一张攻略图。各自查看预约提醒：只显示各自计划；A 不得确认 B 的计划。
4. 上传带明确年份的行程 V1（如 2030-08-20 青海湖）；创建包含青海湖、莫高窟的草稿。再传 V2（2030-08-25 青海湖、2030-08-26 莫高窟），执行“刷新预约 编号”：应显示日期冲突，不能静默组成旧青海湖日期加新莫高窟日期。
5. 用“补充预约 编号 项目序号 YYYY-MM-DD”明确选定冲突日期（保留原日期也明确填写），再刷新、查看、确认。确认时若刚补出新日期，应先显示草稿；再次发送确认后才生成提醒。
6. 用测试计划验证“查看预约提醒”“取消预约 编号”。测试完成后取消测试计划。真实 QQ 引用、群文件双事件和消息投递故障需在测试群继续人工观察。

若不重启 Python 服务，当前运行进程仍可能使用升级前代码。无需退出或重新登录 NapCat。
