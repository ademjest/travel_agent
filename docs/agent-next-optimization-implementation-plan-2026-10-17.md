1. 开始每批前读取适用AGENTS.md、检查工作区差异和相关验收记录。保留用户既有未提交工作，不整仓reset、清理或格式化。

3. 尽量复用现有仓库、服务、工具契约和诊断。只在当前边界确实不足时新增小模块，不引入通用插件平台、多Agent框架、微服务或独立向量数据库。
4. 不通过扩大上下文、放宽引用校验、增加隐式重试或删除失败记录来让测试“通过”。
5. 普通状态读取必须只读；不能因为打开设置、诊断或就绪页面而下载模型、调用模型、重建索引或重放业务。

8. 保留原始失败和每次修复后的独立报告。离线脚本、捕获回放、真实新生成、真实外部读取、正式生效分别计分。
9. 不主动重写摘要提示。实验候选和原提示分开保存；任何获批修改记录实际文本差异、用途版本和哈希。
10. 只完成已获批范围；若某项受预算或发布条件限制，继续不依赖该条件的工作，准确记录待办，不把未执行项标为完成。

## 6. R1：就绪状态和更易理解的诊断

### 问题依据

当前模型在首次编码时加载，后台索引异常主要写日志；空索引查询返回空候选。配置存在、文件存在、工作线程运行，均不证明模型和索引已就绪。当前诊断也主要保留事件过程，恢复后的结果还可更直观。

### 实现范围

主要涉及：`infrastructure/local_embedding.py`、`infrastructure/semantic_index.py`、`infrastructure/execution_diagnostics.py`、`infrastructure/execution_report.py`、`app/runtime_factory.py`、`adapters/web_app.py`、`frontend/src/SettingsPanel.tsx`、`frontend/src/DiagnosticsPanel.tsx`。需要新增模块时先确认现有服务无法承担该职责。

1. **分开表示状态。**
   - 功能：关闭/开启；配置：缺少/有效/无效。
   - 编码器：未加载/加载中/可用/失败，记录固定模型版本与安全错误类别。
   - 当前会话索引：无资料/待构建/构建中/部分就绪/就绪/失败。
   - 一次检索：正常命中、没有相关候选、门槛过滤、索引未覆盖、故障回退。
   不用一个布尔ready掩盖这些差异。
2. **后台维护可观察。** 保存或维护本轮索引版本、已完成/待处理数量、最后成功时间和失败原因。先复用现有索引表和进程状态；确有跨重启需求才增加兼容元数据表。
3. **状态查询轻量化。** Web GET只返回状态快照及其更新时间，不触发加载/推理，也不每次重新编码或全量计算内容哈希。进程刚重启、尚未检查时明确标“待检查”。
4. **失败可恢复。** 初始化或索引失败不阻止关键词路径；避免每30秒重复昂贵加载或刷同一错误。以配置/模型版本变化或显式本地重试触发恢复，保持次数与退避可解释。
5. **诊断结果汇总。** 在保留完整时间线的基础上区分“已恢复”“仍在降级”“最终失败”“结果未知”。只依据关联的调用/工具/投递记录，不因后面出现任意成功事件就抹掉前面的失败。
6. **版本可见。** 复用现有设置的待重启提示，增加后端实际运行版本、前端构建版本和支持能力。版本来自构建/启动时固化信息，不能读取磁盘最新文件来冒充旧进程已加载的代码。旧后端缺少能力接口时显示未知/需更新，不导致整页不可用。
7. 索引数量和错误详情按当前会话授权范围返回；不暴露其他会话正文、模型密钥或无关本地路径。

### 必测场景与完成条件

| 场景 | 期望 |
| --- | --- |
| 开关关闭、无资料、首次未加载 | 三种状态能够区分，不标成同一种故障 |
| 模型目录错误、清单损坏、依赖缺失、权重校验失败 | 应用继续可用，关键词可用，明确语义能力不可用 |
| 索引部分完成、文档更新/删除、进程重启 | 状态与当前命名空间一致；不得把旧索引标成完整就绪 |
| 暂时失败后成功、摘要回退、投递未知 | 页面准确表示恢复或降级，不把完成等同于内容正确 |
| 读取状态/诊断、切换会话、删除会话、迟到响应 | 无模型调用/下载/重建；不跨会话显示或恢复已删除信息 |
| 新前端配旧后端 | 显示能力缺失或版本提示，正常聊天页面不崩溃 |

专项覆盖现有`test_execution_report.py`、`test_local_embedding.py`、Web接口和两个前端面板测试；必要时拟新增就绪状态测试。真实本地模型冒烟在隔离库执行，不使用收费模型。

回退：关闭新的状态增强/语义能力仍可继续关键词检索；新增字段兼容旧客户端，不删除旧诊断记录。

## 7. R2：未覆盖纠正与旧摘要回退保护

### 先复现，再选择最小改动

真实实验已出现增量摘要失败后沿用旧版，但“纠正随后退出近期历史是否造成旧值误用”尚未完整验证。不得直接宣布已经发生线上错误。

主要涉及：`services/conversation_summary_service.py`、`infrastructure/conversation_summary_repository.py`、`agents/context_builder.py`、`core/context_policy.py`、`core/conversation_summary.py`及相应测试；拟新增`tests/test_summary_freshness.py`。

### 离线复现矩阵

1. 旧摘要为360元/间/晚；新消息改为320元；分别注入语义拒绝、模型失败、预算阻断和冷却未重试。
2. 同时包含19:30改19:00、轮椅未决改决定不借用，验证多个字段不互相覆盖。
3. 推进足够的中性对话，确认原始纠正退出最近对话和群消息两条通道。
4. 检查实际送给回答模型的请求，而不只检查数据库摘要或脚本回答。
5. 补充长消息分段尚未覆盖、更新成功、普通闲聊、多任务切换、来源删除/遗忘、会话删除和并发发布场景。

### 建议实现方向

- 先建立“摘要覆盖到哪里、还有哪些有效用户材料未覆盖、是否有分段进度”的明确状态；来源有效与内容已覆盖不能混为一谈。
- 在现有总上下文额度内，优先考虑补入**有来源、按存储顺序排列、完整保留的未覆盖用户材料**，并标明旧摘要待更新。避免重复当前消息或已经在近期上下文中的材料。
- 不依赖一个“更正”关键词判断所有新事实；不另用模型偷偷提取纠正，不把助手回答作为用户决定。
- 只有能完整容纳所需未覆盖材料时，才能据此支持当前值；若存在无法纳入的潜在关键材料，必须保留不确定状态。在涉及当前约束或业务提交的场景，采用现有澄清/缺信息路径，不能仅靠一句警告继续宣称全部要求满足。
- 默认先对摘要整体标记覆盖状态，不通过未经验证的正则猜测受影响条目并静默删除。需要条目级覆盖时，先提供反例和最小设计。
- 不扩大总窗口；必要时从非必要文档、群聊背景等已有预算中重新分配。必要任务状态仍超限时沿用明确的停止/澄清行为。
- 补充材料必须再次经过当前权限、来源删除/遗忘及摘要排除规则；删除后不能由新的补充缓存恢复。
- 未覆盖材料不等于已保存业务状态，不构成新授权；成功发布前不得推进摘要覆盖水位。

### 完成条件

- 所有离线反例的实际模型输入包含可验证的最新纠正，或进入明确不足/澄清状态；不能把旧值无条件当作最新值。
- 更新成功后补充材料退出，版本/覆盖进度一致；普通闲聊不导致每轮重建或抛弃全部长期信息。
- 总字符/输入预算、来源生命周期、取消和并发版本保护不退化。
- 离线通过只关闭机制缺口，模型是否正确使用仍由R3真实测试证明。

回退：保留旧存储结构和摘要；若补充机制出错，退回明确的信息不足状态，不能以恢复旧值静默回答作为回退成功。

## 8. R3：摘要引用质量与真实新生成验收

### 已知问题与范围

第二批5份新摘要输出中，生成时仅2份发布；v4.3原样重验接受3份。两份失败仍属于正文旧值/单位缺少对应引用。最后Web成功恢复了捕获输出，不能替代原始新生成流程的稳定验收。

先复用`evaluate_summary_quality.py`、`replay_summary_responses.py`、`smoke_summary_live.py`、`smoke_summary_web.py`和既有用例，保留原始失败。

### 提示候选的审核方式

默认不修改原提示。可先新增一个明确标为候选的文档，提供精确差异与反例。建议比较两个策略：

- A：当前v4提示，作为对照。
- B：更正条目优先只写当前有效信息；历史值仅在确有后续用途时保留，且同时引用支持历史值与新值的原文。

B的候选强调文本供审核：

> 更正条目优先记录当前有效值及完整单位、对象和条件，不为展示更正过程重复旧数字或旧时间。若确有必要写出旧值，sources必须同时支持新旧表述；不能只引用更正后的片段，却在正文中加入未被引用的旧值。

此文本不是自动替换指令。用户未批准提示实验时，Codex仅准备候选与离线反例，继续保持原提示哈希。即使批准隔离实验，也不能自动替换正式提示。

### 试验准备与执行

1. 固定旧回归、新改写和反例，明确人物、单位、当前值、未决事项及未知信息的评分标准；答案不进入模型输入。
2. 分别统计生成事实覆盖、首次发布率、引用错误、语义误拒、实际注入覆盖和最终回答正确率。
3. 完成原始Web路径：首版新生成、增量新生成、近期历史退出、实际版本/哈希注入、最终回答。固定历史材料可以用于机制测试，但报告必须标明其预置方式，不能称全部历史都由真实模型在线生成。
4. 捕获输出恢复和合并原文一次生成继续保留为诊断工具，单独标记，不能填补原始Web新生成的失败。
5. 驱动在失败后保留隔离库、阶段、水位、原始输出和同一预算审计，允许从已确认阶段恢复；不因临时库清理而丢失现场、另起文件重置额度。
6. 先用脚本模型干跑并核对预期调用路径，再提出具体真实批次。物理请求、Token及费用上限必须在执行前得到授权；SDK和传输隐式重试保持关闭，未知usage停止后续调用。
7. 用当前版本做独立新生成及改写验证；已用于修复的样本转为回归，不再称独立留出。不要为得到成功结果不断重跑同一题。

### 完成条件

- 既有关键事实金标准、引用依据和未知项要求通过；不能把缺少引用的事实算系统已记住。
- 至少有完整原始Web新生成路径及独立复测证据，并按预先登记的场景逐项报告；存在关键旧值误用或未执行却声称完成时不准入。
- 发布率等统计完整保留失败分母，不预设本轮已经达到某个长期成功率。
- 提示改动如有采用，更新唯一来源、版本、哈希和提示清单，保留可回退的上一版本。

## 9. R4：搜索与网页读取可靠性统一

主要涉及：`infrastructure/search_client.py`、`infrastructure/web_reader.py`、`infrastructure/public_http.py`、`core/tool_result.py`、`core/tool_execution.py`、`services/research_service.py`及读取测试。

### 实施步骤

1. 在现有安全HTTP边界保留状态码、可重试类别和合法Retry-After。不能为了重试绕过HTTPS、DNS/IP检查、重定向限制、内容类型和大小限制。
2. 搜索返回空结果是正常业务结果；参数、权限、登录/验证页、404、格式错误和暂时故障分别处理，不统一变成“服务不可用”。网页软404及只有导航没有正文的现有检查继续保留。
3. 只设置一层重试。默认同事件同逻辑读取最多3次物理HTTP请求，**重定向也计入物理上限**，并继续遵守现有最多2次重定向；额度耗尽即停止，不能把每一跳当成新额度。
4. 不产生HTTP请求的解析/校验失败也要有有限逻辑尝试，避免DNS或前置校验循环。永久失败不自动重试，安全限制拒绝不按暂时网络失败重试。
5. 尊重剩余期限、取消与Retry-After。超出本地等待期限时停止；已有持久化接续入口可记录最早重试时间，其他入口返回明确状态，不新建通用调度框架。
6. 复用现有事件检查点和恢复计数。Tavily虽使用POST，但它是可能按请求计费的读取，网络失败与重试都计数，不能称失败请求免费；成功结果仍需校验后才可复用。
7. 错误与恢复经过工具/检索诊断可见，避免HTTP层和业务层尝试次数重复相加；认证头、正文和私有参数不进入诊断。

### 必测矩阵

429、503、超时、长Retry-After、401/403、404/软404、登录验证页、错误JSON、缺字段、空结果、过大响应、重定向到禁止地址、退避期间取消、成功后恢复、预算耗尽。

完成条件：读取入口遵循同一错误含义和物理计数；失败不伪造成功研究结果；既有SSRF、权限、取消和删除测试继续通过。真实外部读取只在具体额度获批后执行。

## 10. R5：实际资料检索与回答质量

### 数据先行

- 优先使用公开允许访问的旅行资料，或用户明确授权的本地资料；保存来源、抓取时间、文档版本和许可/使用范围说明。
- 按文档、来源版本和近重复组拆分开发/留出，干扰文档也不能跨组复用后再宣称严格独立。
- 覆盖精确名称、同义改写、否定/例外、跨段规则、表格、版本冲突、同名地点和无答案；明确相关证据的段落/条款及“信息不足”的依据。
- 历史100题作为回归保留；新32题是小型实验，不能直接升级成实际资料效果。

### 分步实验

| 实验 | 主要变化 | 必须固定 |
| --- | --- | --- |
| A | 当前关键词基线 | 资料、查询、权限范围、Top-k、上下文预算 |
| B | 当前BGE与关键词混合 | 相同切分与上述条件 |
| C | 标题/段落/条款感知切分 | 先固定B的模型与融合，不同时换模型 |
| D | 父段或相邻条款补充 | 固定检索结果及总上下文预算，标明补充来源 |
| E（有证据再做） | 重排或BGE-M3候选 | 根据失败类型选一种，不同时改变多个因素 |

如果正确证据从未进入候选，先处理召回或切分；如果候选存在但排名过低，再评估重排。不要硬编码具体测试问句的同义词来通过留出题。

### 验收口径

- 同时报Recall@k、Hit@k、排序、无答案误召回、来源覆盖、实际注入和最终回答忠实度；召回正确不等于回答正确。
- 门槛、Top-k和融合参数只在开发集选；留出结果失败后转为回归，下一轮另准备未参与调优的留出。
- 保留历史合成指标门槛用于可比性，不把“100题合成指标通过”作为正式质量充分条件；真实资料的准入场景和判分标准在打开留出前冻结，不事后挑有利阈值。
- 预算、单位、适用日期、城市、否定与无答案等关键反例不得被错误升级为确定结论；不能靠给模型更多无关资料掩盖误召回。
- 答案生成若使用收费模型，单独登记预算。助手自行复核要标明复核方式，不能冒充独立人工盲评。

### 性能与索引升级

先测冷加载、热查询、索引更新、内存和会话规模。当前全范围扫描/窗口平均是否构成瓶颈尚未证明。只有测量支持时才引入变更驱动更新、缓存或窗口级候选；本阶段不默认部署向量数据库。

若切分或模型改变，使用新命名空间和版本；先在隔离库构建验证。正式重建须检查删除同步和可回退范围，不能覆盖旧索引后才发现新索引不可用。

## 11. R6：事实时效、实体范围与规划依据贯通

主要涉及：`core/research_evidence.py`、`core/research_contract.py`、`services/research_service.py`、`infrastructure/research_repository.py`、`infrastructure/planning_repository.py`、`services/planning_service.py`、`services/trip_service.py`、`agents/trip_planner.py`。

1. 对现有新报告、旧报告、研究转规划、探索草稿转行程逐条列出输入/输出契约，检查依据与不确定状态在哪里丢失。
2. 区分用户约束、来源陈述、程序已检查内容和模型建议。发布时间、抓取时间、适用起止时间分别保存；缺失即未知，不由抓取时间补成“最新政策”。
3. 对确有证据的实体/城市/场馆标识做关联；同名或范围无法确认时保留歧义。没有来源不能凭模型猜地理适用性。
4. 新旧来源冲突保留双方来源及适用范围，不能仅以抓取较晚自动裁定；无法确定时在计划中显示待核对。

6. 规划可以在明确未知条件下给出候选建议，但不能保证目标日期开放、已有票、已预约或预算一定满足。关键业务写入仍遵守原有明确授权和确认。

必测：新旧政策、同名异地、单位缺失、只有搜索摘要、抓取时间冒充生效时间、提前预约与无需预约的区别、禁止打车/行动限制、证据在草稿采用与计划修改中丢失。

完成条件：关键反例不产生无依据的确定断言，依据与未知状态在所有本批明确列出的入口中保留。未覆盖入口列入限制表，不宣称全项目事实校验完成。

## 12. R7：成本、性能与契约维护

### 费用与效率

- 按已有run/event关联汇总成功任务总成本，包含摘要生成、增量、失败、修复、重建和外部请求；无usage/无费率记未知，不记零。
- 分别比较摘要开/关、用途模型、档位和缓存，一次改变一个主要因素。缓存冷/热组交错，使用同类且质量已达标的任务。
- 本地embedding记录CPU、内存和耗时；没有远程Token费用不等于没有资源成本。
- 报告总成本/成功任务数、P50/P95、失败率及样本量，不预设必须节费某个百分比。

### 维护试点

只选一个已有高频领域，例如住宿预算的金额、币种、主体、周期及追加/替换/清除语义，统一相关入口的子契约。先对照当前行为，特别保留同句多需求、否定、指代和接续；不要借此拆分全部大文件或一次重写所有提示。

完成条件：行为回归通过，真实质量没有因低成本模型或短提示退化，收益可核算，改动可单独回退。没有收益时保留基线并记录负结果。

## 13. R8：恢复交错、综合验收及发布

### 综合与恢复

沿用原方案的20个场景种子，补足可执行判分与实际入口：查询接续、研究到规划、约束修改、长会话摘要、失败恢复各类覆盖。它们不是已通过的20次真实联网流程。

注入业务提交后崩溃、投递成功但确认丢失、租约更换、取消与完成竞争、恢复时预算耗尽。检查部分成功和外部结果未知，不承诺QQ恰好一次投递。

保留原首批综合筛选标准：20场景至少18项符合预定完成条件，越权、重复业务副作用、取消后迟到写入、未执行却声称完成等关键错误零失败；该结果不代表长期成功率。未具备真实执行条件的场景列未执行，不能补计成功。

### 发布前准备

1. 所有拟发布源码稳定后完成相关专项及必要全量；保存源码、提示、语料、依赖和前后端构建清单。
2. 前端先构建到独立暂存目录，不直接覆盖正在服务的dist造成新页面配旧后端；此项属于本次部署流程改进。
3. 准备具体发布范围：是否包含诊断、摘要保护、读取改进，embedding是否继续关闭；批准某批代码发布不等于自动开启所有实验开关。
4. 准备正式数据的一致性备份方案、兼容迁移演练、排队任务处理方式和回退步骤。备份保护凭据，不把配置原文或数据库正文放入报告。
5. 至此给出可审阅发布清单；若用户尚未授权正式切换，再请求具体发布授权。用户已明确批准相同范围时不重复询问。

### 获批后执行与验收

- 确认实际实例、解释器和数据目录；停止接收或等待活跃请求安全结束，不擅自终止正在提交的业务。
- 执行一致性备份和兼容迁移，受控切换前后端，保证唯一正式实例；不对不明进程批量停止。
- 检查健康、实际版本与能力、诊断入口、已有会话读取和本地无副作用流程；涉及收费验收必须仍在已批准额度内。
- 若开启embedding，核对正式解释器依赖、模型加载、范围内索引覆盖和词法回退；隔离目录可运行不替代正式就绪验证。
- 回退优先回退代码/静态资源和关闭新功能；不整库覆盖已有新业务数据，不删除新字段/表来制造旧版本兼容。
- 交付实际生效记录、残余限制和回退位置。仅有构建成功不能标正式发布完成。

## 14. 每批交付模板与停止条件

每批报告必须包含：

1. 原问题及本批范围；修改文件与核心行为变化。
2. 起始/最终源码清单和提示版本；本批未覆盖项。
3. 专项、全量、真实调用及运行验收的独立结果。
4. 原始失败、归因、修复以及修复后新证据，避免覆盖失败历史。
5. 本批请求/Token/费用或本地资源记录；未知项目明确列出。
6. 是否正式生效、回退方式、下一步。

出现越权/删除恢复、取消后写入、未知usage、物理预算耗尽、来源保护退化或无法确认真实写操作结果时，停止依赖该结果的实验/发布，保留现场并继续不受影响的本地工作。不能靠换输出文件、扩大额度或跳过反例继续。

建议沿用现有验证脚本生成报告。输出文件使用实施日期和批次唯一命名，不覆盖本轮历史审计；执行命令与环境记录在交付文档中。
