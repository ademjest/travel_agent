# travel_agent：事实状态、局部规划、可见差异与规则分流实施方案

日期：2026-10-18；版本：v1.0；状态：**用户已批准；2026-10-19完成本地实现、隔离模型对照与回归，未进行正式服务切换。**

实施结果见[四项重点升级实现报告](state-routing-incremental-delivery-2026-10-18.md)。本批新增100,000 Token授权已用31,721，剩余68,279；与本文设计时提及的上一批额度分开记账。实际验收范围、首次评测误判及当前边界以交付报告为准。

本方案依据[全面比对报告](agent-experience-comparison-and-opportunities-2026-10-18.md)，将用户选定的“关键事实状态＋局部规划修改＋可见变更差异”与新增的“固定规则减轻意图解析负担”合为一条实施主线。

## 1. 目标与范围

目标不是扩大关键词命中率，而是在不遗漏需求、不降低确认与来源要求的前提下，减少重复意图解析和重复规划，并让用户明确看到当前要求和实际变化。

本轮包含：

1. 有严格适用范围的固定规则；完全覆盖且可执行的请求跳过意图模型。
2. 全请求操作检查与完成跟踪，防止复合请求只执行第一项。
3. 扩展现有行程/任务状态，保存关键事实的来源、状态及更正关系。
4. 按变更影响范围生成局部规划，并确定性合并校验。
5. 当前需求卡、结构化差异及与草稿版本绑定的确认。
6. 离线回归、完整任务成本对照和分阶段启用。

不纳入首版：泛化语义规则引擎、多 Agent、通用依赖图、任意跨业务事务、自动预订付款、向量模型替换、全面时间窗求解。原有摘要提示不改写，不自动保存长期偏好。正式服务切换沿用已有单独发布边界。

“规则直达”只表示省去意图解析模型。后续业务仍可能需要地图/天气工具、规划模型或回答模型，不能展示成整个请求零 Token。

## 2. 当前代码事实与必须处理的边界

| 位置 | 当前机制 | 本方案处理方式 |
| --- | --- | --- |
| `core/commands.py` | 已有命令解析；部分天气/路线命令接受前缀后的自由文本 | 保留有效命令，补充整句与复合请求边界，避免后半句被当作地点 |
| `services/semantic_task_service.py` | 多数自然语言进入模型；已有路线更正/接续；部分分支按某类操作存在即返回 | 在执行前审查全部操作形态，不能只增加前置正则 |
| `core/intent_ir.py` | 已有多操作 IR、来源校验，最多 8 个操作 | 规则与模型复用 IR，不另建业务动作体系 |
| `core/execution_outcome.py` | `TravelReadRequest` 支持不同领域的只读组合；同领域多地点暂不走该路径 | 先保留回退，再单独补按操作实例跟踪的只读批次 |
| `agents/travel_agent.py` | 有工具白名单、4 步/6 工具等边界及完整性检查 | 不盲目提高上限；超出可处理规模时明确分批 |
| `services/trip_service.py`、`core/trip_updates.py` | 已有 spec、草稿、版本和共享字段更新；纯交通等分支可跳过整体规划 | 扩展当前来源与影响范围，不另建事实主库 |
| `agents/trip_planner.py` | 现有完整计划生成、限定日期校验、POI 缓存和部分旧路线复用 | 增加有限类型的局部生成，完整校验继续保留 |
| Web confirmation API | 已有 confirmation id/version/client_request_id 校验与重复提交处理 | 复用并绑定新的差异预览，不重复建设确认接口 |

目前看到的分发顺序属于需要测试的风险位置，不把所有组合都直接定性为已复现缺陷。第一阶段须用完整应用入口证明哪些输入发生遗漏、哪些已有保护。

## 3. 整体流程

```text
用户消息 / 明确的界面操作
  → 原有鉴权、会话归属、Inbox、取消与确认检查
  → 请求解释入口
      ├─ 已验证的结构化界面操作：直接生成业务操作
      └─ 文本规则解析（仅识别，绝不执行）
           ├─ 全部覆盖、唯一解释、执行器支持：生成 Intent IR
           ├─ 整句意图明确但缺字段：保存全部需求并澄清
           └─ 无匹配 / 部分匹配 / 歧义：完整原文交给现有意图模型
  → 全请求检查：操作全集、依赖、冲突、目标版本、执行器能力
  → 只读查询 / 已支持的业务事务 / 行程需求增量
  → 影响范围计算 → 局部生成 → 合并及完整校验
  → 服务端生成需求卡和差异 → 用户确认 → 原有提交路径
  → 逐项结果：完成、待补充、待确认、失败、未执行
```

该入口在所有可能消费整条消息的宽松前缀/业务分支之前生效；不能只放在 `IntentCompiler` 前，而让 `semantic_candidate` 因旧命令匹配提前退出。具体接入点先由入口回归固定，保留附件和预约图片专用路径。

第一阶段规则对带附件、引用资料、多轮自由指代和多个待接续任务的文本不直达；已有确认和明确路线接续保留，但须验证整句不会附带未处理的第二需求。

## 4. 固定规则如何避免遗漏多个需求

### 4.1 采用“受限语法的整句覆盖”，不采用“命中一个关键词就返回”

规则可以有多个，但每条要声明：

- 固定编号和版本、适用业务、允许的完整句式。
- 可提取槽位及其原文位置，必要字段、来源要求。
- 允许的礼貌前后缀和连接形式。
- 不支持的条件、否定、更正、引用、时间含义等边界。
- 能与哪些规则组合，以及哪一种执行器能完整处理。

只进行有限的空白/标点标准化，保留与原文的偏移映射。数值、单位、否定、校区/校门和地点限定不得删除或缩写。原始消息始终保留给后续业务。

匹配返回轻量结果：`complete`、`needs_input`、`fallback`、`ambiguous`，以及规则版本、候选操作、已解释区间和未解释区间。它只是解析诊断，不拥有执行权限。

**直达条件必须同时成立：**

1. 除明确列出的礼貌词、标点和连接符外，整条消息均被受限语法解释。
2. 每个字段来自有效原文或服务端确定的当前任务；没有相互竞争的解释。
3. 不包含超出该规则定义的否定、条件、比较、指代或附加要求。
4. 全部操作组合在支持列表中，且所需执行资源未超过已有上限。
5. 通过现有 IR、参数、归属和版本检查。

字符都落入捕获组不等于语义完整。例如 `查询天气 (.+)` 不能算整句覆盖，因为“武汉，顺便提醒我买票”可能被全部吞成地点。地点槽位必须有保守边界和动作尾句排除；仍无法判断时回退。排除表只能补充受限语法，不能单独作为完整性证明。

### 4.2 多需求处理分为三种情况

**A. 每项都能识别且组合受支持。**

先收集全部操作，再一次分发。例如“查询天气 武汉；查询路线 武汉站 → 湖北省博物馆”，生成天气与路线两个操作。执行结果分别记录，不在第一项成功后提前返回。

**B. 只识别一部分。**

例如“查询天气 武汉，顺便帮我找带老人不累的玩法”。规则不调用天气，完整消息进入模型。首版不采用“规则执行前半句、模型只看剩余文本”，因为这会丢掉共享地点、条件和先后关系，并容易重复执行。

**C. 都识别了，但组合不支持或语义存在依赖。**

例如“下雨就把第二天改室内”“查天气并取消提醒”。保留全部候选需求，经完整模型解释和组合检查；只有已有执行器支持整体语义才执行。仍不支持时列出已理解事项并让用户选择先处理哪项，不默默只执行第一个。

这会牺牲一部分直达率，换取较低误分流率。不能保证任意自然语言都能被规则完整解析；应通过严格语法、回退和针对性测试控制范围。

### 4.3 切分原则

- 首版复合命令优先支持句号、分号或换行分隔的完整子命令。
- 不直接按所有“和、与、还有、然后”切分；它们可能属于地点、宾语、条件或顺序关系。
- 引号、括号、URL 内的分隔符不作为任务边界；含不支持的嵌套结构直接回退。
- 第二阶段才增加“同时/并且”两侧均为独立完整句式的组合。
- “武汉和长沙天气”先回退；显式双子句“查询天气 武汉；查询天气 长沙”在同领域批次执行完成后才直达。
- “明天”“那里”“同上”不靠邻近字符串补齐；只有规则明确支持的任务状态或完整语法才继承，且记录来源。

### 4.4 首批规则清单

| 类别 | 首版范围 | 路由与限制 |
| --- | --- | --- |
| 精确系统命令 | 帮助、状态、查看行程/提醒等已有命令 | 复用现有处理；带额外句子不能按单命令结束 |
| 单项当前天气 | `查询天气 地点`、`地点现在天气怎么样` 等少量完整句式 | 地点保守校验；不把指定小时/明天天气当作当前天气 |
| 明确路线 | `查询路线 起点 → 终点`、`从起点到终点怎么走` | 保留完整地点；需明确规则默认语义，交通/时间附加要求不被丢弃 |
| 独立只读复合 | 多条完整天气/路线命令 | 全部覆盖且支持时才执行；首版先支持异领域 |
| 明确行程字段修改 | `酒店预算改为320元/间/晚`、`不要夜游` 等 | 必须能唯一定位行程；统一转换到现有字段更新，生成草稿不直接提交 |
| 同一行程多字段修改 | 如完整预算子句＋不夜游子句 | 合并为一个约束变更及一个确认，不分开提交 |
| 明确界面操作 | 编辑字段、选择方案天数、已有确认 | 类型、归属、版本和幂等检查；沿用现有确认能力 |

预算规则只在币种可明确解释、数值/范围及计价单位满足现有契约时直达；不能凭单个“元”扩大到不支持的币种场景，具体人民币解释沿用项目规则。自由需求“酒店便宜点”“就按刚才的”仍走模型。

提醒创建、删除资源、永久偏好、研究搜索和读写混合请求不新增规则直达；已有可靠命令保持原行为。后续只有在负例与副作用测试齐备后逐类扩大。

### 4.5 冲突、否定与重复

- “不要查询天气，查路线”：普通肯定规则不可吃掉否定；首版回退完整解析。
- “预算改为320，不对，改成350”：首版回退；不根据正则顺序采用第一个数。
- “武汉天气如何；长沙天气如何”：保留两个操作，不能按 domain 去重。
- “查武汉天气；再查武汉天气”：仅对确认为同一时点、同一语义的重复只读请求合并；不能泛化合并“先查、稍后再查”。
- “查询天气武汉这句话是什么意思”：属于语言解释，不能触发天气调用。
- “如果下雨就取消预约”：条件不是立即取消的授权。
- “明天十点从武汉站出发，查路线”：出发时间不是创建提醒的授权；当前读取契约不承载的时间语义要回退并保留原文。

## 5. 全请求检查和执行：分流之外的必要工作

### 5.1 支持矩阵

不再仅以 `any(operation.domain == ...)` 决定全部请求去向。先根据完整操作集合判断执行形态：

| 操作集合 | 处理 |
| --- | --- |
| 单一支持业务 | 现有执行器 |
| 多个独立只读操作 | 受限只读批次；全部槽位确认后执行 |
| 同一行程的多字段更新 | 一次合并约束、一次草稿、一次确认 |
| 已有完整实现的行程/关联提醒联动 | 复用已有提交与版本检查，并加完整性回归 |
| 其他读写混合、跨资源写入、条件依赖 | 完整解释后转已有受支持路径；否则保存请求并明确澄清/分步，不执行子集 |

首版不为了支持所有组合而引入通用工作流平台。对明确不支持的组合，用现有任务 slots 保存原始请求、已识别事项和缺项，禁止无提示降级为单任务。进入下一轮时按目标事项和版本继续；自由指代仍可用模型解析。

### 5.2 按操作实例跟踪，不能只看领域

为受限只读批次提供稳定操作键：由请求身份、固定解析版本、操作序号及规范参数生成，恢复时使用已持久化的解析结果，不随新规则重新解释旧请求。不同城市天气属于不同实例。

每个实例都有 `pending / completed / needs_input / failed / not_executed` 状态及结果引用。一个请求只有全部必要项达到正确终态才结束；部分成功必须逐项说明，未执行不算成功。

优先复用现有工具成功检查点、执行回执和事件结果存储，在需要时补操作键维度。禁止直接循环调用会自行提交根事件的 `service.handle`，避免一次请求多次提交或复用错回执。批次由单个协调入口提交根结果。

首版只读批次最多 3 个操作，顺序执行，仍受现有物理请求、时限与总预算限制；超出时回退或明确要求分批。三个不是新工具调用预算。天气/路线清晰查询可用固定格式汇总；比较与建议仍走模型，不能输出未经推理的建议。

### 5.3 模型回退不能成为遗漏的盲点

回退携带完整原文和必要当前任务状态。无歧义、独立完整子句的规则候选可作为辅助检查项；有冲突的候选不当作确定事实强加给模型。

若模型漏掉可独立确认的完整子句，发起至多一次有预算的解释修复；仍不完整则澄清且不执行。修复不是额外业务重试，也不能绕过已有模型请求上限。不能给所有回退请求默认增加第二次模型调用。

解析前不得执行规则子集。业务执行后出现工具失败，由原有恢复机制处理，不能重新进入“全句模型解析并重做所有业务”。

## 6. 关键事实状态：扩展已有数据，不建第二份主库

### 6.1 首版事实范围

优先覆盖当前结构已支持的酒店/餐饮预算及单位、节奏、交通、夜游和住宿偏好。同行照护、是否借轮椅等额外事实，只在下一批有明确字段契约后扩展；不在首版试图结构化所有对话。

日期沿用现有行程字段和解析；展示来源，但跨日期的完整局部修复延后。用户明确的地点、币种和单位不靠摘要补猜。

### 6.2 表达与真值来源

当前值继续保存在 `trip.spec` 或候选草稿中。给字段增加来源元数据及字段修订标识；变更前后值使用现有版本记录/草稿差异，不再复制一份独立值表。

元数据至少能表达：字段路径、原消息/事件引用及必要原文区间、来源类别、修订标识、确认状态。未知、明确清除、布尔否定分开处理；`false` 不表示缺失，未提及不表示清除。

权威边界：

- 已确认行程是已保存业务状态。
- 待确认草稿表达用户最新调整要求，规划接续可以使用，但明确标“尚未保存”。
- 询问“已保存的行程”只能读取已确认版本；询问“我刚才想改成什么”可读取草稿。
- 长期偏好是缺少本次要求时的默认，不覆盖显式当前约束。
- 摘要、模型建议和外部文档不能自动覆盖用户已确认决定。

原始历史保留来源，模型上下文使用有效当前字段，避免将旧自由文本偏好与新字段当作两个同等有效要求同时注入。不删除历史来掩盖冲突。

### 6.3 生命周期

收集需求 → 校验增量 → 更新草稿 → 生成/更新预览 → 确认时以预期版本提交；取消草稿不改变已确认行程。后续更正覆盖同一字段的草稿值，并令旧预览过期。

旧行程缺少新来源元数据时标记为历史来源未完整记录，不伪造引用，也不强迫用户重新输入全部字段。读时兼容，后续真实修改再补来源。

无正式行程时使用现有任务 slots；不自动建立长期事实记录。来源删除、会话遗忘和行程删除沿现有策略级联处理新元数据，避免留下可恢复的聊天引用。

## 7. 局部规划修改

### 7.1 首版三个影响范围

| 修改类型 | 可修改范围 | 必须保留 | 注意事项 |
| --- | --- | --- | --- |
| 住宿预算/品牌 | 住宿候选、相关通勤证据 | 景点与活动安排 | 无价格证据时仅记录目标，不能宣称新酒店符合预算 |
| 交通偏好 | 受影响路线、耗时/限制标记 | 原活动，除非发现需扩大修改的冲突 | 复用路线必须检查时效与模式 |
| 明确指定一天/时段的活动要求 | 指定范围活动、相邻路段、关联提醒 | 其他天/时段的业务内容 | 整体必去、不重复和节奏仍需通过 |

夜游、节奏等全局约束需要计算所有受影响时段；可能覆盖多天，不能为了叫“局部”而漏改。暂未支持的字段组合沿现有整体生成，但必须标明规划范围，不能伪装成局部优化。

### 7.2 实现路径

1. `apply_constraints` 先产生有效候选 spec 和字段 delta。
2. 纯函数依据变更类型和当前计划计算允许修改的路径；多个变化取影响范围并集，再检查互相冲突。
3. 仅获取影响范围所需候选和有效证据；范围外信息以必要的禁止重复地点、必去要求和边界约束供模型使用。
4. 可确定性完成的修改直接处理；需要生成时模型只输出有限 patch，如住宿候选或指定日活动。首版用固定 patch 类型，不提供任意 JSON 路径写入。
5. 服务端验证 patch 目标、候选 ID、基础版本和范围，合并进旧计划。
6. 继续执行完整 `validate_plan` 及相关推荐/提醒检查，并额外验证不受影响的业务字段保持一致。
7. 生成确定性差异，保存草稿，等待确认。

稳定比较忽略纯检查时间等非业务元数据，但不得忽略地点、活动、预算、日期或提醒变化。

### 7.3 失败及范围扩大

局部生成不合法最多使用现有有限修复预算；不能无限局部修复后再无限整体重规划。达到上限保留已有计划，指出无法满足的限制。

确需改动范围外的已确认活动时，展示原因和拟扩大的范围，请用户决定是否扩大；不能以内部“优化”名义改变其他天。已经包含在用户新全局要求中的影响不重复请求许可，但仍要展示完整差异并走原有最终确认。

研究证据和原文来源继续随局部候选传递；不以旧候选缓存绕过来源时效要求。

## 8. 可见需求和变更差异

### 8.1 当前需求卡

在现有“本次旅行”面板显示预算及完整单位、交通、节奏、住宿偏好、未定项，支持查看来源。已确认值与草稿修改分开标记，例如：

```text
住宿预算：420 元/间/晚
待确认修改：320 元/间/晚
价格核实：尚无实时房价依据
```

编辑字段通过带资源/草稿版本及请求 ID 的结构化入口，复用同一更新服务。不能从前端直接信任 owner、确认状态或来源；界面提交本身作为新的用户输入来源记录。文字输入入口继续保留。

### 8.2 差异预览

差异必须由服务端比较已确认基线与候选计算，不交给模型自由总结。核心字段包括基础行程版本、草稿修订版本、需求变化、活动变化、路线变化、提醒影响和待核实项。

默认展示从已保存版本到当前完整草稿的累计差异；可附本轮新增变化。避免用户多轮调整后只看到最后一轮，遗漏前面仍待确认的改变。

示例：

```text
本次待确认修改
• 住宿预算：420 → 320 元/间/晚
• 酒店候选：A → B（实际房价尚未核实）
• 关联通勤：已重新查询
• 第1—3天景点安排：保持不变
• 提醒：无变更
[展开完整预览] [确认这次变更] [继续调整]
```

“保持不变”和“无变更”只在服务端实际比较成立时显示。数据不全、预览缺失或版本不一致时禁用确认，沿用已有重生成入口。

已有 confirmation id/version/client_request_id 接口继续使用，绑定到实际候选版本；两个标签页中的旧预览不能确认新草稿。重复点击返回同一结果，后端重启不丢失预览身份。

QQ 使用同一差异数据渲染文本，不把 Web 组件当作唯一实现。文字确认仍需关联唯一有效预览，不能把任意“好的”当作提交。

## 9. 诊断与最小实现划分

沿用现有诊断，只增加允许列表内的元数据：规则/版本、路由来源、回退原因、操作数量及逐项状态、修改范围、规划模式、实际调用用途。默认不记录完整句子、原始槽位值和资料正文。

用户摘要显示：“已识别 2 项需求，均已处理”“已处理天气；路线缺少起点”“本次只更新住宿候选，行程尚未确认”等。规则编号和内部键放技术详情。

建议边界如下，实施时可合并小模块，避免为了形式拆分：

| 位置 | 修改责任 |
| --- | --- |
| 新增 `core/rule_intent.py` | 纯解析、覆盖区间、组合与回退原因；不调用工具/模型/数据库 |
| `core/commands.py`、`app/bot_application.py` | 旧命令边界及统一入口，防止前缀抢占 |
| `services/semantic_task_service.py` | 规则/模型选择、全操作支持矩阵；复用现有业务分发 |
| `core/execution_outcome.py` 及现有执行存储 | 只读批次的操作实例、回执与恢复；按需扩展现有结构 |
| `core/trip_updates.py`、`services/trip_service.py` | 来源增量、草稿权威状态、影响范围接入 |
| `agents/trip_planner.py` | 有限 patch、合并校验、证据复用 |
| 按需新增 `core/trip_diff.py` | 纯函数生成服务端可见差异，不调用模型 |
| `infrastructure/trip_repository.py` 及 Web context 层 | 兼容元数据、草稿版本和差异读取 |
| `frontend/src/App.tsx` 及小组件 | 需求卡、差异预览、结构化字段操作 |

不为本轮构建插件式规则平台，不将所有历史领域解析器整体重写。

## 10. 分阶段实施与开启条件

| 阶段 | 交付 | 验证后才能开启 |
| --- | --- | --- |
| S0：基线和遗漏复现 | 固定当前源码/提示/账本；完整入口负例；任务级指标 | 区分已复现遗漏和仅有风险的分支 |
| S1：规则解析与分发保护 | 纯解析器、整句覆盖、全操作支持矩阵；旧前缀保护 | 只观察/离线验证，不先执行新规则 |
| S2：有限直达 | 单项读、异领域只读组合；再补同领域多实例批次 | 槽位、全部需求、恢复与物理尝试上限通过 |
| S3：状态来源及需求卡 | 扩展已有 spec/草稿元数据；只读需求展示；旧数据兼容 | 草稿/已保存/未知/清除边界通过 |
| S4：局部规划和差异 | 住宿、交通、指定日试点；差异与确认绑定 | 范围外保持、完整校验、旧预览拒绝通过 |
| S5：规则到修改贯通 | 有单位预算等明确规则、同一行程多字段合并、结构化编辑 | 不绕过确认、不遗漏复合更正，端到端通过 |
| S6：真实对照和发布准备 | 效果/成本报告、失败清单、兼容和回退演练 | 不满足质量门槛则保留开关关闭；正式切换单独执行 |

S2 与 S3 可按依赖交错推进，但不代表自动启用多 Agent 或并行编辑。先让分发完整，再让规则省调用；先有正确状态，再让局部修改省计算。

使用少量服务端开关控制规则直达与局部规划。观察模式只在原有请求本就经过模型时比较，不为了观察给原来的零模型命令额外调用模型。无需再增加面向普通用户的复杂设置。

回退时新草稿不能静默当成旧完整计划处理：候选始终保留兼容的完整计划，并验证旧版本读取能力。不能保证旧程序兼容时，发布前明确限制回退并准备可恢复制品；不靠哈希清单冒充备份。

## 11. 验收设计

### 11.1 规则与组合用例

至少建立 200 条人工标注的离线语句：建议 80 条可直达正例、120 条边界/回退/复合负例；按句式家族划分开发和留出，避免只替换城市名造成虚高。

| 输入类型 | 必须验证 |
| --- | --- |
| 单项天气/路线 | 规则路径 0 次意图模型调用，字段正确且无多余操作 |
| 天气＋路线 | 两项均有回执；任一失败不隐藏另一项 |
| 武汉天气＋长沙天气 | 不按领域去重；未启用批次前完整回退 |
| 已知命令＋未知附加需求 | 规则不先调用任何工具；完整原文进入模型 |
| 天气＋提醒/删除/研究 | 无部分提前执行、无擅自写入；不支持则明确说明全部事项 |
| 条件、否定、更正、引用 | 不误触发肯定规则，不取第一个旧值 |
| 地点含连接词/校区/校门 | 不误切分，不截短地点 |
| 缺少字段或多个待办 | 保留全部已知需求，追问目标字段/事项，不重复创建任务 |
| 重试/重启/重复消息 | 不重复成功操作；逐项状态可恢复 |
| 旧命令前缀＋第二需求 | 不能绕过新检查从旧路径抢先执行 |

固定回归集中要求错误直达、漏操作和未授权副作用为 0；这表示测试门槛，不是对任意自然语言作零错误保证。规则覆盖率只作收益指标，不能以提高覆盖率为由放宽安全边界。

### 11.2 状态与局部修改

至少建立 40 个离线端到端场景，包含：多轮同字段更正、币种/单位、清除与否定、草稿取消、旧摘要冲突、来源删除、重启、两个标签页、并发版本变化、局部候选缺失和局部修复失败。

核心门槛：

- 关键当前值与单位正确，未知不补猜；草稿不冒充已确认。
- 范围外业务内容在固定场景中 100% 保持，完整计划约束仍通过。
- 多轮草稿累计差异与实际提交完全一致。
- 旧版本确认和重复消息不会改变错误资源或重复提交。
- 价格无依据时只记录预算目标，不声称实际达标。

### 11.3 Token 和体验对照

固定使用当前 `gpt-5.6-sol` 及档位，至少比较：原路径、仅规则优化、仅局部规划、两者组合。首先使用固定模型输出与工具快照完成全部离线场景；真实模型只选择有代表性的小子集。

统计完整任务的模型请求、各用途实际 Token、外部物理请求、估算费用、P50/P95 延迟、澄清轮数及完整完成率。包含解析回退、摘要维护、失败和修复；分开冷/暖缓存，避免以请求拒绝或漏任务换取成本下降。

建议性能目标（待基线确认）：规则适用集的意图解析调用降为 0；局部修改集的总 Token 中位数较基线降低至少 20%，且完成质量不下降。20% 是试验目标，不是已测收益；若未达到，应定位开销或收窄方案，不能篡改验收口径。回退路径不应普遍增加一次模型调用。

真实测试须先根据待测输入/输出上限登记计划，再消耗已有余额。此前授权账本为累计 100,000 Token、已用 59,688、余额 40,312；执行时重新核对，不重新记成新额度。本次设计不调用模型、不消耗该额度。若余额无法覆盖全部真实验证，交付已完成证据与未测项，不以离线结果冒充实测。

## 12. 审核建议与最终交付

建议审核后按 S0—S6 分批实施，首批只开启低歧义单项读和受支持的完整只读组合；明确预算等写前草稿规则在 S5 再开启。复合需求只要部分未被理解，就保持整句模型回退，不先执行命中的部分。

最终应交付：版本化规则清单与负例集、来源状态兼容说明、局部修改影响表、需求/差异界面、完整任务验收与成本报告、未通过事项和发布回退检查记录。

用户可据本方案审核范围；本文不是新增功能上线完成报告，也不因选择了重点方向就自动扩大原有正式发布授权。
