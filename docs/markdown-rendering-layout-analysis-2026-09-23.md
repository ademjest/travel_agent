# Agent 回复 Markdown 布局问题分析与修正方案

日期：2026-09-23

范围：依据两张截图、对应 Web 数据库中的原始回复、ReactMarkdown 实际生成的 HTML，以及当前前端 CSS 和行程格式化代码进行只读分析。本轮未修改业务代码或正式数据。

## 1. 结论

两个截图不是同一个原因：

1. 菜品编号列表的超大行距，主要由 `.markdown li { white-space: pre-line; }` 引起。它将列表 DOM 标签之间的格式化换行也保留成可见空白行。
2. 行程中“第 1 天／第 2 天／第 3 天”缩进不一致，是行程纯文本缺少明确 Markdown 分隔，同时前端只转换以“旅行行程：”开头且日期已确定的回复。创建预览没有进入转换逻辑，导致后续日标题被 CommonMark 解析进上一条 `<li>`。

模型输出格式存在一定差异，但截图中的严重异常是前端渲染契约和样式共同造成的，不能只靠提示模型“排版好看一点”解决。

## 2. 截图一：编号、标题和正文间距过大

数据库中的原始回复结构是合法且常见的 Markdown：

```markdown
**开封特色菜推荐**
1. **开封灌汤包**
   - 代表性很强，皮薄汤多，吃的时候先开小口喝汤。
   - 适合早餐或正餐点一笼尝鲜。

2. **鲤鱼焙面**
   - 河南传统名菜……
```

ReactMarkdown 生成的结构为：

```html
<ol>
  <li>
    <p><strong>开封灌汤包</strong></p>
    <ul>
      <li>代表性很强……</li>
      <li>适合早餐……</li>
    </ul>
  </li>
</ol>
```

当前 CSS 同时存在：

```css
.markdown p { white-space: pre-line; }
.markdown li { white-space: pre-line; }
```

`white-space` 会继承。React 生成的 `<li>` 中，`<p>` 和 `<ul>` 之间存在源码格式化换行文本节点。在 `pre-line` 下，这些换行不再完全折叠，因此产生以下视觉结果：

- `1.` 标记单独占据一行；
- 菜名出现在下一行；
- 菜名与子列表之间出现很大空白；
- 子列表项目之间也被额外拉开。

基础 `.markdown p { margin-bottom: 12px }` 和列表 `margin: 8px 0 14px` 会进一步叠加距离，但不是截图中数十像素空洞的主要原因。

## 3. 截图二：同级“第 N 天”缩进不一致

行程服务输出的是逐行纯文本：

```text
行程创建预览（尚未保存）：开封3日行程……
你的要求：要加上酒店推荐
住宿要求：酒店推荐……
第 1 天（日期待定）
- 下午：开封府……
- 晚上：大宋武侠城……
第 2 天（日期待定）
- 上午：清明上河园……
```

缺少空行和 Markdown 标题标记时，CommonMark 的解析结果会接近：

```html
<p>
  行程创建预览……
  第 1 天（日期待定）
</p>
<ul>
  <li>下午：开封府……</li>
  <li>
    晚上：大宋武侠城……
    第 2 天（日期待定）
  </li>
  <li>上午：清明上河园……</li>
</ul>
```

因此：

- 第 1 天仍处在普通段落中，靠左显示；
- 第 2 天附着在“晚上”列表项后面，与列表正文同级缩进；
- 第 3 天同样可能附着在前一日最后一个活动列表项里；
- 三个看似相同的日标题实际属于不同 DOM 层级，CSS 无法仅凭文字让它们对齐。

## 4. 前端行程转换为何没有生效

`frontend/src/App.tsx` 当前只在满足以下条件时转换日标题：

```tsx
text.startsWith("旅行行程：")
```

并且只匹配：

```regex
第 \d+ 天 · 日期
```

截图中的回复以：

```text
已采用方案草稿：……
```

开头，日标题格式又是：

```text
第 1 天（日期待定）
```

因此开头条件和正则条件都不满足。类似以下回复也存在相同风险：

- 行程创建预览；
- 行程修改预览；
- 先输出说明，再输出旅行行程；
- 日期待定的行程；
- 规则重新核对后的行程预览。

## 5. 推荐修正方案

### P0：修复列表空白行

移除 `.markdown li { white-space: pre-line; }`。需要保留普通工具回复的逐行显示时，只在段落或明确的纯文本组件上保留，而不要应用到列表容器。

建议增加列表内专用间距：

```css
.markdown li {
  white-space: normal;
}

.markdown li > p {
  margin: 0 0 4px;
}

.markdown li > ul,
.markdown li > ol {
  margin: 4px 0 8px;
}

.markdown li + li {
  margin-top: 8px;
}
```

外层正文行高可以从 `1.85` 调整到约 `1.7–1.75`，但应在移除列表 `pre-line` 后再根据视觉检查决定，避免把真正的结构错误掩盖成字体问题。

### P0：统一所有行程日标题

不要再以整条回复必须 `startsWith("旅行行程：")` 作为转换条件。应对回复中的任意行程区块识别：

```regex
^第\s*\d+\s*天(?:\s*·\s*[^\n]+|（日期待定）)$
```

将所有匹配行统一转换为：

```markdown
### 第 1 天（日期待定）
```

同时确保标题前后有空行，使前一日列表可靠结束。住宿／餐饮等同级区块也应转为固定标题：

```markdown
### 住宿候选
### 餐饮候选
```

这样普通行程、创建预览、修改预览和日期待定行程会产生相同 DOM 层级。

### P1：后端输出稳定的显示结构

前端正则可以兼容历史消息，但新消息不应继续依赖前端猜测。建议 `TripService.format_trip()` 输出明确的 Markdown 结构，或输出结构化内容块供不同平台渲染。

较小改动可以给 Web 渲染器增加结构化转换：

```text
行程标题

### 第 1 天（日期待定）

- 下午：开封府……
- 晚上：大宋武侠城……

### 第 2 天（日期待定）

- 上午：清明上河园……
```

更稳定的长期方案是让行程回复包含 `kind=itinerary` 和结构化 `days`，Web 使用 React 组件渲染，QQ 仍使用纯文本。这能避免同一份纯文本同时承担聊天、Markdown 和平台适配三种职责。

### P1：规范一般回答的标题层级

普通 Agent 应优先输出真正的 Markdown 标题：

```markdown
## 开封特色菜推荐

1. **开封灌汤包**
```

而不是仅用独立粗体段落模拟标题。可以在 Agent 输出提示中说明：

- 主要区块使用 `##`；
- 子区块使用 `###`；
- 编号和项目标题保持在同一行；
- 不输出只有 `1.` 的空列表项；
- 列表之间只保留一个空行。

提示词只能提高一致性，前端仍需防御合法但风格不同的 Markdown。

## 6. 建议的前端规范

| 元素 | 建议间距 |
| --- | --- |
| 普通段落 | 下边距 8–10px |
| `h2` | 上边距 18px，下边距 8px |
| `h3` | 上边距 14px，下边距 6px |
| 外层列表 | 上下 6–10px |
| 同级列表项 | 6–8px |
| 列表标题到子列表 | 3–5px |
| 行程日标题到第一项活动 | 6px |

同一级别标题必须使用相同元素与相同容器宽度，不能靠空格或文本缩进对齐。

## 7. 必须补充的测试

1. 使用截图一对应的原始 Markdown，断言编号和菜名处于同一个列表项首行，嵌套列表无空白文本行。
2. 使用“旅行行程：”开头的已保存行程，所有日期标题渲染为 `h3`。
3. 使用“已采用方案草稿：”开头的创建预览，日期待定的三个日标题也全部渲染为同级 `h3`。
4. 使用“行程修改预览”及前置说明文本，转换不能依赖 `startsWith()`。
5. 确认“第 2 天”不出现在上一日最后一个 `<li>` 的 `textContent` 中。
6. 对手机、普通桌面和高分辨率宽屏分别检查嵌套列表、标题和长地址换行。
7. 保留普通逐行工具回复的换行效果，避免移除 `pre-line` 后将必要状态行合并。

## 8. 推荐实施顺序

1. 先移除列表上的 `white-space: pre-line`，增加列表内部间距规则。
2. 将行程标准化逻辑改为识别任意位置、已确定或待定日期的日标题。
3. 给行程输出增加明确空行或结构化 Web 渲染。
4. 增加截图对应的 DOM 和视觉回归。
5. 最后微调整体行高与标题 margin，避免在结构仍错误时只调像素。

本轮只进行了分析并保存方案，没有修改前端代码或启动 `run_web.py`。
