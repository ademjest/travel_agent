# travel_agent 与 Agent 工程经验的全面比对及高收益方向

日期：2026-10-18。性质：现状评估与后续建议，不替代已批准实施方案，不表示下列新增方向已经实现或批准。

## 1. 结论与评估范围

当前项目已经具备较完整的 Agent 工程骨架：模型解释意图，确定性代码检查权限和业务约束；有工具契约、有限重试、上下文控制、记忆、检索、执行状态、版本确认与诊断。已经超过“会调用工具、接了 RAG”的演示阶段。

但“机制存在”与“复杂旅行任务稳定成功、总成本降低、正式用户已经用到”是不同结论。目前后两类证据仍不充分。下一阶段最大的收益在于打通已有能力：**维护明确的旅行事实和决策状态 → 按变化局部计算 → 用证据核验可执行性 → 让用户直接核对和操作。**

| 节点失败、恢复与回滚 | Inbox/Outbox、租约、幂等、成功检查点、乐观版本、修改预览 | 不等于任意外部操作都能回滚，也不保证 QQ 端到端恰好一次 | 核心机制满足，需补真实交错验收 |
| 数据清洗、切分、检索 | 文档导入、字符窗口与换行/句号边界切分、重叠、FTS5；可选本地 BGE 混合检索 | 标题、表格行、条件与例外可能跨块；真实资料证据充分性和规模性能待测 | 有基础，属于高收益升级区 |
| 日志、复盘、bad case | 元数据诊断、中文处理过程、导出、离线捕获输出回放、专项和回归测试 | 离线回放不等于业务恢复重放；还需把真实失败转成固定场景集并衡量任务完成 | 已显著超过只看控制台日志 |
| 内容与执行安全 | 不可信资料隔离、来源检查、归属、写操作权限/确认、删除遗忘、公开 HTTP 访问限制 | 这些不等同于覆盖所有内容风险的独立审核体系；应按实际开放场景决定补充范围 | 执行安全有基础，不能声称全覆盖 |
| 成本与上线效果 | 用途模型配置、账本、价格快照、缓存用量记录、就绪状态代码 | 尚未证明摘要长期净节省；正式切换、备份回退与完整真实 L2 仍待完成 | 可测量基础已具备，收益结论尚不成立 |

旅行场景的合理降级是保留已确认结果，明确缺少的数据，并给出可操作的下一步。不能把天气、房价、开放时间等失败结果换成看似合理的默认值；项目没有人工客服团队，也不宜虚构“转人工”。

## 3. 目前最有价值的优点与主要短板

### 优点

1. **业务边界明确。** 模型不能仅凭生成内容获得写权限，行程和提醒变更有版本与确认，适合有副作用的 Agent。
2. **对事实来源较认真。** 摘要引用、数字/单位/否定保护、研究原文证据与规划传递，能防止一部分“看起来顺畅但事实改变”的错误。
3. **可追踪性已经落到用户入口。** Web 消息旁有“查看处理过程”，不再只依赖手工找到事件键并执行 PowerShell。
4. **可选检索和模型能力有退路。** BGE 默认关闭、失败保留词法检索；预算、有限重试和降级使失败可收敛。
5. **业务面较完整。** 研究、方案、行程、住宿餐饮、预约、提醒和资料已贯通，下一步可以优化完整任务，而不必继续堆基础组件。

### 短板

主要矛盾已经从“缺机制”转向四件事：**重复理解和计算、事实/决策表达分散、证据相关但不一定够用、复杂任务的真实验证不足。**

目前不宜宣称成熟上线：最新模型测试有失败保留，新的正式运行能力尚未全部确认，真实资料完整导入到回答的链路也未全面过关。

## 4. 优先方向一：统一当前旅行事实与决策，减少摘要承担的责任

### 现有基础和问题

`TripPlanner.extract`、`apply_constraints`、任务 slots、行程 spec、约束覆盖和草稿版本已经保存结构化信息。不是重新造一个“长期记忆库”。问题在于会话中的事实、提议、当前决定、已确认执行结果，尚未都能通过同一套来源与版本规则供问答、规划和界面使用。

比如：“酒店原来 420，改成 320 元/间/晚；轮椅只是建议，目前决定不借；医院暂未确定。”如果关键结论仍反复经过自由文本摘要，数值限定、提议归属和未知状态都可能丢失。

### 建议

扩展已有行程/任务状态，按需记录字段值、币种/计价单位、状态、原始来源及版本。状态至少能区分提议、当前选择、已确认和未知；更正保留被替代关系。多个行程先消歧，不把一次旅行要求自动保存为永久偏好。

模型提取候选增量，现有验证与提交路径决定是否接受。问答和规划优先读取经校验的当前状态，摘要主要承担叙事背景。没有正式行程时先使用现有任务草稿，避免引入第二份相互竞争的事实主库。

**收益：** 减少重复从聊天中重建事实；减少摘要质量波动对关键约束的影响；为可视化需求和局部修改提供共同基础。这是较有项目特色的创新方向，但不是学术原创性声明。

**验收：** 20 轮以上的更正、撤回、未知、多人提议、摘要失败、重启和遗忘场景；对固定测试集要求关键单位/状态不丢失、旧值不复活、跨会话不泄露，并统计重复追问和总 Token。结构化数据仍需来源验证，不能因为结构化就当作正确。

## 5. 优先方向二：从“整体重规划”升级为确定性的局部修改

### 代码依据

`services/trip_service.py:update_constraints` 对纯交通等少数情况有跳过整体规划的分支，但多数约束变化仍调用 `collect_places` 和 `plan`。已有 POI 五分钟缓存、旧路线复用；`TripPlanner.plan` 提示只改受影响天，并对明确“第几天”的修改检查其他天是否变化。因此项目不是完全没有增量能力。

剩余机会是把“受影响范围”从提示要求变成代码约束，并减少发送给模型的候选及旧计划。

### 建议

先用一个简单的影响范围映射，不立即引入通用图引擎：

| 变化 | 优先重新核对 | 通常可复用 |
| --- | --- | --- |
| 酒店品牌/预算 | 住宿候选、相关通勤；若影响可行性再扩大范围 | 用户锁定景点、无关研究 |
| 第二天下午改室内 | 当天下午活动、前后路线、有关提醒 | 其他天及不受影响活动 |
| 出发日期变化 | 日期相关开放/预约规则、天气、提醒 | 仍有效的地点介绍与偏好 |
| 交通方式变化 | 受影响路段、耗时和可行性 | 不冲突的活动顺序 |

模型只生成局部 patch，服务端合并并验证完整行程；范围之外的变更拒绝或请求重新确认。复用必须检查来源版本、时间和使用目的，特别是已有路线复用不能把历史耗时当作当前实时路况。

**收益：** 同时降低上下文、模型输出和外部请求，减少“只改酒店却把整趟行程改了”的体验问题。

**验收：** 固定局部变更集比较完整重规划基线；记录未受影响部分保持率、模型/HTTP 物理请求数、总 Token、P50/P95 延迟，以及完整约束通过率。不预先承诺节省百分比。

## 6. 优先方向三：缩短重复意图解析与上下文组装

### 代码和实测依据

`semantic_candidate` 除明确命令、少量寒暄和特定接续外，大部分自然语言会进入语义编译器。`IntentCompiler.compile` 每次携带涵盖多个领域的较长 SYSTEM_PROMPT。与此同时，项目已按用途限制上下文，并按决策筛选工具，不能将这些已有功能重新包装为升级。

最新 24 次、59,688 Token 的测试中，意图解析 4 次共 15,786 Token，摘要 6 次共 17,724 Token。这个工作负载刻意测试摘要和问答，不代表日常流量比例；它只说明值得测量这两个阶段。

### 建议

1. UI 中具有明确资源和版本的“确认”“选择天数”“调整字段”走结构化业务请求，复用服务端归属和版本校验；减少按钮先变成自然语言、再被模型重新理解的路径。保留自由表达入口。
2. 在可靠的当前任务状态或显式操作信息下选择较短的领域契约；不确定、跨领域和复合请求仍走完整解析。避免粗糙关键词分流丢掉“查天气并规划地铁”等第二意图，也不默认额外加一次 LLM 分类调用。
3. 沿用现有 ContextPolicy，按当前任务取必要字段和证据，去掉状态、摘要、近期原文之间可确认的重复；完整保留数值单位、否定及来源。
4. 复用按资料版本和时效验证的结果；区分“同一事件恢复用的成功检查点”与“跨事件可复用的缓存”。当前交通与稳定文档采用不同有效期，不缓存用户授权结论。
5. 单独测量供应商报告的缓存命中、实际 Token 与费用。固定提示前缀可能降低费用，但不等于 Token 预算消耗归零。

网关的输入估算目前是保守字节上界，不是真正 tokenizer。可先对实际 usage 校准高估情况，再评估兼容的分词估计；不能为降低误拒绝直接放松硬预算。

**验收：** 相同完整任务、同一模型和档位、固定资料版本，分别统计冷/暖缓存，纳入解析、摘要维护、失败、修复与回答所有消耗。质量不退步后才比较每个成功任务的成本；不得以拒绝请求或遗漏子任务换取“省 Token”。

## 7. 优先方向四：把 RAG 从“找到相关段落”升级为“有足够证据回答”

### 现有证据

本地 BGE 已实现，在合成用例上有召回收益；默认关闭，不能说已全面生效。真实 NPS 资料小样本 16 题中，FTS 与 BGE 有答案题 Recall@5 都为 100%，但两者对 4 道无答案题都返回候选。返回候选本身正常，不能直接认定模型会幻觉；它表明相似度阈值不能代替答案支持判断。

目前导入按字符窗口、换行/句号及重叠切分。研究引用校验和来源适用性已存在，但有限数字/标签规则并不是通用语义证明。

### 建议

- 优先保留政策条款的完整条件、例外、主体、日期和表格行；检索较小片段，按需带回父段及标题，避免无限扩张上下文。
- 对价格、预约、过敏保证、开放时间等问题明确需要哪些字段。证据缺少计价单位、适用人群或日期时，只回答已知部分。
- 区分用户要求“仅依据资料”和允许联网补查的任务边界；确需最新资料时补查正确来源，仍无依据则说明未知。
- 将原文引用、实体适用性、有效期、冲突/缺失状态沿现有研究到规划链路传递；不要简单地多数来源投票。

**收益：** 比单纯扩大 embedding 更直接改善答案可信度，并减少将大量无关候选送给模型的开销。中文主场景应补中文真实资料；现有英文 NPS 样本不能代表中文模型的全部表现。

**验收：** 从实际文件导入开始，按来源隔离开发/测试集；同时测试有答案、无答案、过期、同名地点、冲突及跨块条件。评价最终回答支持率、合理拒答率、过度拒答率和成本，不只看 Recall@K。原先被测试护栏中止的资料问答保留为未通过/协议不充分，不能直接当作已证实的产品路由缺陷。

## 8. 优先方向五：增加旅行可行性检查，让规划真正能执行

这是在图片通用工程经验之外，最有旅行领域价值的方向之一。

目前 `validate_plan` 能检查天数、活动数、地点证据、时间段、必去地点和部分偏好；路线与耗时证据随后补入。已经有路线能力，但尚不能由这些检查推出“开放时间、预约时点、通勤、休息和总预算都可行”。

建议先做小范围确定性规则：已知开放窗口与日期是否冲突、已知路程是否挤占停留时间、预约是否晚于计划入场、休息与步行限制是否明显冲突。每个检查结果为“通过/冲突/资料不足”，带来源与影响项。估算停留时间要标明是假设；实时交通不能保证未来出行情况；POI 评分不能证明价格或无障碍条件。

先给冲突解释和两个局部备选，由用户选择；与方向二的局部修改结合。后续可复用已有天气/规则监测，在用户明确开启时提出行程变化建议，重要改动继续确认。

**收益：** 从生成合理文字，前进到能解释限制、发现问题并协助修复的旅行助手。创新和体验收益高，但数据成本与实现复杂度也高，建议从一个城市、一天行程开始。

**验收：** 人工标注的可行/冲突/未知三类日程；未知数据不能被判通过；比较冲突检出、误报、修复后约束满足、地图请求量和用户选择轮次。不直接承诺全局最优路线。

## 9. 优先方向六：在现有旅行面板上补全“需求—依据—差异—下一步”

现有 Web 已有行程/方案/提醒/资料面板、每日调整入口、完整变更确认与处理过程。无需重做一个聊天产品。

建议增加三个用户可直接理解的部分：

1. **当前需求卡。** 展示预算及单位、日期、同行限制、交通、未定事项；能查看来源并编辑。明确哪些是草稿、哪些已确认，保持与方向一同一状态来源。
2. **变更差异。** 默认显示本次具体变动、受影响日期/提醒、仍需核实的信息，并可展开完整预览。现有版本确认机制继续生效。
3. **可操作的失败恢复。** 在已有“查看处理过程”摘要中先回答：完成了什么、缺什么、下一步是什么；按实际失败提供补充地点、刷新过期依据或重新生成局部预览。按钮仍要检查当前资源版本，不能重放整次写操作。

不把 event key、检索 namespace 和内部重试次数作为用户必读内容；技术细节继续留在展开项。运行/索引状态沿用已有设置面板，不另建一套。

**验收：** 用户能在不看 PowerShell、不找事件键的情况下完成一次查询失败修复；已知字段不重复追问，过期确认不会提交，失败后的已成功部分不会重复执行。统计完成轮次、恢复成功率、误操作与首次可用结果时间。

## 10. 实施次序与投入取舍

| 次序 | 内容 | 收益重点 | 投入判断 |
| --- | --- | --- | --- |
| A | 补当前真实质量/发布证据，固定任务级基线 | 确认用户实际用到的版本及测量可信度 | 必要收尾；不代表暂停所有独立优化 |
| B | 明确按钮走结构化请求、意图上下文对照、需求卡首版 | 较快降低延迟和重复理解，提升可见性 | 中低到中；先做窄路径 |
| C | 关键事实/决策增量与局部规划首版 | 同时改善可靠性、Token 和使用体验 | 中到高；最值得作为主线 |
| D | 真实资料切分、证据充分性与来源适用性 | 避免“相关但答不出来/答错”，支撑规划 | 中到高；可与 C 分批交错 |
| E | 一日行程可行性检查与局部修复 | 明显的旅行领域差异化 | 高；建立在事实与证据基础上 |

A 包括摘要新生成稳定性、真实公开/地图读取、完整 L2、QQ 投递边界、发布数据目录/备份/旧制品/回退核验。最新后端和前端回归通过不替代这些工作。开发依赖审计尚有未解决项，应单列维护工作；不能直接推断成线上已被利用。

每个优化只改变一个主要因素：先事实和局部更新，再评估上下文压缩及摘要维护策略；避免同时换提示、模型、切分与阈值，最后无法解释收益来自哪里。

暂不优先：多 Agent 框架迁移、微服务拆分、独立向量数据库、未经规模测试就换更大 embedding、所有回答再套一轮 LLM 审核、继续盲目扩大上下文。它们可能增加延迟、Token 和维护面，当前证据尚未说明必要性。

## 11. 用什么证明“整个项目进步”

采用完整旅行任务作为计量单位：提出需求 → 补充信息 → 研究/规划 → 修改 → 确认 → 后续查询与提醒。以当前 `gpt-5.6-sol` 为基线，避免模型变化掩盖架构效果。

- 任务完整完成率与复合请求覆盖率；不能只计算收到一个回答。
- 关键约束保留、最新事实正确、资料结论有依据；分别统计过度拒答。
- 单个成功任务的总 Token、估算费用、模型/外部物理请求数；失败和修复也计入总消耗。
- P50/P95 延迟、澄清轮数、修改波及范围、失败恢复成功率。
- 删除/遗忘、权限、重复投递与版本冲突等既有边界不退步。

先建立基线，再确定节省幅度目标。当前两次摘要问答和两次原文对照的条件及缓存不充分一致，且未完整摊销摘要维护成本，不能据此承诺固定节省比例。本次未消耗新增测试额度；既有账本为已用 59,688 / 100,000 Token，余额 40,312，未来若沿用授权需累计扣除。
