# 普通规划、联网研究与已保存行程上下文断裂分析

日期：2026-09-22

范围：依据用户给出的三轮原话、当前代码的纯函数路由结果，以及 Web 数据库中的请求、回复、研究记录、任务、模型调用和行程记录进行只读核对。本轮未修改业务代码或正式数据。

## 1. 结论

本次不是模型简单“忘记了前文”，而是系统把相关内容存放在三个彼此不连通的层次：

1. 第一轮的详细安排只是普通聊天回答，没有形成联网研究，也没有形成可引用的规划草稿。
2. 第二轮形成了研究报告，但没有生成或保存行程；它与第一轮方案也没有建立引用关系。
3. 第三轮被理解为修改当前行程，而 `trip/update_constraints` 只能修改数据库中的已保存行程。当前会话没有 `trips` 记录，于是返回固定提示。

当前的 `travel-research` skill 只在 `ResearchService` 已经接管消息之后负责选源。第一轮没有进入 ResearchService，因此 skill 没有机会执行；skill 本身也不能替代业务路由、跨轮记忆或行程持久化。

## 2. 三轮实际发生了什么

会话：`8f9176b99476477686b0e0d13d9be6be`。

### 第一轮：请求网上攻略和小红书参考

用户原话：

> 我想去开封玩，但是还没确定时间，想先了解一下大概的攻略参考，最好可以参考一下网上的攻略比如小红书

静态路由结果：

```text
research_request = False
trip_request = False
travel_decision = general
```

`ResearchService.research_request()` 主要识别“搜索／搜一下／查……攻略／联网”等特定表达。该句使用“了解攻略参考、参考网上攻略、小红书”，没有命中入口。

这一轮出现了两次模型调用，没有创建任务、研究记录或行程。结合应用顺序和最终回复，可以确认消息最后进入普通 TravelAgent。原始语义 IR 没有保存，不能断言第一次模型调用具体输出了什么；可以确认当前 Intent IR 不支持 `research` 领域，因此无法生成可执行的研究操作。

普通 Agent 没有网页搜索工具，于是凭模型已有知识给出 2 天 1 晚和 3 天 2 晚两套参考方案，并告诉用户可以如何在小红书搜索。它没有实际读取小红书内容。

这份回复长 2456 字，本轮总字符数约 2504；内容保存在聊天记录里，但没有被标记为“规划方案”。

### 第二轮：明确搜索开封四日游

用户原话：

> 帮我搜索开封四日游攻略

静态路由结果：

```text
research_request = True
trip_request = False
```

这次进入 ResearchService，并形成 `research_runs` 记录。搜索计划正确判断为国内目的地：

- 第一批：`xiaohongshu.com`、`zhihu.com`
- 第二批：马蜂窝、携程、去哪儿、穷游
- 第三批：开封旅游、景点官方信息

本次 Tavily 没有返回小红书结果，返回了知乎、携程、去哪儿、Tripadvisor、Trip.com 等结果。多数只能取得搜索摘要，只有部分页面能读正文。因此“国内来源正文不足”的提示有依据，但这不等于没有执行国内站点优先策略。

第一轮明确提出的小红书偏好没有传到第二轮。搜索规划器只接收当前句“帮我搜索开封四日游攻略”，没有读取同一会话之前的研究来源偏好。默认策略仍尝试小红书和知乎，但没有把“小红书是用户特别希望参考的平台”作为对话状态保存。

第二轮回复虽然按 4 天结构给出研究建议，但 `ResearchRepository` 只保存报告和来源。代码仅在以下情况进入 TripService：

- 同一条消息明确说“根据研究结果规划……”；或
- 研究消息本身同时命中行程请求并包含“规划／制定／安排”。

“帮我搜索开封四日游攻略”只表示研究，没有授权保存行程。因此数据库中没有行程，这一行为本身合理；缺少的是“研究方案草稿”这一中间业务对象。

### 第三轮：恢复最开始方案并增加酒店

用户原话：

> 那还是按照最开始的规划安排吧，但是要加上酒店推荐

这一轮出现一次模型调用，没有创建任务。最终进入 `SemanticTaskService._update_trip()`，并返回：

> 当前会话还没有已保存行程，请先规划行程；本轮未创建交通查询。

语义编译器当前有 `trip/update_constraints`，但只描述“行程生成后”修改已保存行程；没有以下操作：

- 从聊天中的旧方案创建行程；
- 从研究报告创建行程；
- 选择“最开始／刚才／搜索结果里的”某一份方案；
- 将非正式方案升级为可确认行程草稿。

`SemanticTaskService` 给模型的上下文主要是已保存行程、提醒和长期偏好。当前没有已保存行程，也没有把最近聊天方案和研究候选放进语义上下文。模型只能把“按照原规划安排、加酒店”近似解释为修改行程；服务端发现 `trips` 为空后固定拒绝。

应用调度中 SemanticTaskService 位于普通 TravelAgent 之前。一旦它返回这条提示，普通 Agent 没有机会尝试结合历史解释“最开始的规划”。

## 3. 为什么仅增加聊天历史也不够

通用 Agent 的 ContextBuilder 会读取最近对话，但对话预算约 2400 字，并按完整轮次选择：某轮加入后超过预算时，整轮跳过。

第三轮处理前：

| 对话轮次 | 用户 + 助手字符数 | 是否适合当前预算 |
| --- | ---: | --- |
| 第一轮初始规划 | 2504 | 单轮已超过 2400，会被跳过 |
| 第二轮研究报告 | 1902 | 会被保留 |

因此即使第三轮回退给普通 Agent，它通常只能看到第二轮研究报告，看不到用户所说的“最开始”那份第一轮方案。扩大历史长度可以缓解个别场景，但不能可靠解决方案身份、来源选择、版本和执行授权。

## 4. 正确的业务语义

系统需要区分三种对象：

| 对象 | 含义 | 可否直接修改／确认 |
| --- | --- | --- |
| 探索性方案 | 聊天中提出的路线思路或多个备选 | 可以继续讨论，不能冒充已保存行程 |
| 研究方案 | 带来源的攻略总结或路线建议 | 可作为规划依据，不能自动执行 |
| 已保存行程 | 有 `trip_id`、版本、结构化日期／活动／来源 | 可通过版本校验修改和确认 |

第三轮的意图是：选择一份探索性方案作为基础，增加酒店要求，然后将其转为新的行程候选。它不是 `update_constraints(current_trip)`。

在当前具体会话中，“最开始的规划”可以指向第一轮回答，但第一轮里同时有 2 天 1 晚和 3 天 2 晚两种安排，仍然存在一个业务歧义。正确回复应类似：

> 我找到了最开始那份开封参考方案，其中有“2天1晚”和“3天2晚”两套。你想采用哪一套？我会同时加入酒店推荐，日期可以继续待定。

不能默认套用后来的 4 日研究，也不应直接选择第一轮中的某一种天数。

## 5. 推荐修正结构

```text
用户消息
  ↓
语义路由：研究 / 探索规划 / 从旧方案创建 / 修改已保存行程
  ↓
当前会话持久对象
  ├─ 研究来源偏好
  ├─ 探索性方案候选（按时间编号）
  ├─ 研究方案候选
  └─ 已保存行程及待确认草稿
  ↓
服务端选择对象、校验身份和来源
  ↓
必要时仅澄清方案或天数
  ↓
TripService 重新查询地点与酒店 → 预览 → 确认 → 保存
```

### 5.1 用语义操作触发自然语言研究

不建议继续只给 `research_request()` 增加“小红书／网上攻略／参考攻略”等字符匹配。应在 Intent IR 增加受约束的研究领域，例如：

```json
{
  "domain": "research",
  "operation": "search_travel_guides",
  "query_text": "开封攻略参考",
  "source_request": "网上的攻略比如小红书"
}
```

需要同步修改：

- `core.intent_ir.SUPPORTED_DOMAINS`：加入 `research`；
- `agents.intent_compiler`：识别“了解网上攻略、参考小红书游记”等真实研究意图；
- `SemanticTaskService`：服务端绑定当前会话并调用 ResearchService 的结构化入口；
- `ResearchService`：保留固定命令快速路径，同时接受已经校验的研究操作。

这样第一轮就会实际执行 `travel-research` skill 的选源计划，而不是由普通 Agent 教用户如何搜索。

### 5.2 保存会话级研究偏好

第一轮的“小红书”属于当前探索任务的来源偏好，不应自动变成全局长期偏好。建议在会话研究上下文保存：

```json
{
  "destination": "开封",
  "preferred_domains": ["xiaohongshu.com"],
  "strict_sources": false,
  "source_event": "..."
}
```

第二轮省略平台时，若仍是同一目的地和同一研究主题，则继承该偏好；用户明确改口或排除平台时再更新。不能让其他会话或其他用户继承。

### 5.3 增加持久的“规划方案”对象

聊天正文不能充当可靠业务状态。建议增加会话级 `planning_artifacts`（名称可调整），最少保存：

- artifact id／会话／用户／顺序／来源事件；
- 类型：`exploratory` 或 `research_backed`；
- 目的地；
- 天数候选；
- 每日纲要或主题；
- 住宿／交通／节奏等已明确要求；
- 未确定字段；
- 原回复或研究报告引用；
- 是否已转成行程、版本和创建时间。

该对象不是正式行程，不允许直接确认预订或提醒。它用于可靠理解“最开始那份”“刚才搜索出来的四日方案”“第二个方案”等引用，且不受最近对话字符预算影响。

探索性回答生成后，可以通过有原文依据的结构化 sidecar 保存方案摘要。研究报告也应生成对应 artifact，并保留来源标识。不要直接从长篇自由文本无校验地创建 `trip_id`。

### 5.4 增加从上下文方案创建行程的操作

新增类似：

```json
{
  "domain": "trip",
  "operation": "create_from_plan_artifact",
  "plan_index": 1,
  "changes": {
    "accommodation": {
      "requested": true,
      "value": "酒店推荐",
      "source": "要加上酒店推荐"
    }
  }
}
```

模型只引用服务端提供的序号和用户原话，不能生成数据库 ID。服务端解析“最开始／最新／搜索结果”并绑定实际 artifact。

如果 artifact 有多个天数方案，先保存已知修改并只问选择哪一个。选择后：

- 日期可保持待定；
- 使用 TripPlanner 重新查询开封 POI；
- `hotel_requested=true` 时查询酒店 POI；
- 原方案只是结构参考，地点、路线和来源仍重新校验；
- 生成新行程预览，确认后再保存正式行程。

`trip/update_constraints` 应继续只处理已保存行程或已绑定的行程草稿。没有 trip 时，不要用一句固定错误结束；若存在方案 artifact，应转入创建流程或给出针对性的选择问题。

### 5.5 将方案摘要接入语义上下文

`SemanticTaskService` 的 context 建议增加紧凑候选：

```json
{
  "planning_artifacts": [
    {"index": 1, "order": "earliest", "kind": "exploratory", "destination": "开封", "duration_options": [2, 3]},
    {"index": 2, "order": "latest", "kind": "research_backed", "destination": "开封", "duration_options": [4]}
  ],
  "research_context": {
    "destination": "开封",
    "preferred_domains": ["xiaohongshu.com"]
  }
}
```

模型据此解释相对指代；完整内容只在服务端选中后读取，避免把多篇长报告全部塞进模型窗口。

## 6. 最小修补与完整方案的区别

最小修补可以在“没有保存行程”时读取最近研究报告，并询问是否据此创建。但它无法满足本次“最开始的规划”：最近报告是第二轮四日游，用户明确想回到第一轮；而第一轮又有两种天数。

只扩大聊天历史也不够：长方案会继续竞争 token 预算，且没有稳定方案编号、权限和版本。

只修改 `travel-research` skill 也不够：skill 负责“搜什么来源”，不负责消息是否进入研究、旧方案选择和 TripService 状态转换。

完整方案需要同时处理：语义路由、持久方案 artifact、研究偏好接续、从方案创建行程，以及前端可见的方案选择。

## 7. 建议的用户体验

### 第一轮

识别为自然语言研究请求，实际优先搜索小红书和国内平台。若小红书只有摘要或不可读，明确说明，同时用其他国内来源补足。展示“开封初步参考方案”，并保存为方案 1。

### 第二轮

识别同一目的地的继续研究，继承“小红书优先但不严格限定”的会话偏好。搜索四日游并保存为方案 2，不覆盖方案 1。

### 第三轮

解析“最开始”为方案 1，解析“加酒店推荐”为新增住宿要求。发现方案 1 有 2 天和 3 天两个版本，只追问：

> 最开始的方案有 2 天 1 晚和 3 天 2 晚两套，你想采用哪套？酒店推荐会一起加入，日期可以先不定。

用户选择后生成行程预览，并显示地点与酒店来源。确认后才创建正式行程。

也应提供明确入口：

- “采用最开始的 3 天方案”；
- “采用刚才搜索到的四日方案”；
- “查看方案草稿”；
- “删除方案草稿”。

网页右栏可以把“研究结果／方案草稿／已保存行程”分开展示，降低自然语言引用歧义。

## 8. 验收清单

1. 原第一轮表述实际调用研究服务，小红书偏好进入搜索计划，而不是只返回搜索教程。
2. 第二轮同目的地研究继承来源偏好；新方案不覆盖旧方案。
3. 三轮原句完整回归：第三轮不能返回“没有已保存行程”，应定位方案 1 并仅澄清天数。
4. 用户选择后，生成日期待定的新行程预览，包含酒店候选；确认前 `trips` 仍为空或保持原版本。
5. “按刚才搜索的四日方案”应选择方案 2，而不是方案 1。
6. 长回复超过聊天预算、重启、超过 30 分钟后，方案引用仍可恢复。
7. 多会话、多用户严格隔离；删除会话同步删除方案 artifacts 和会话级研究偏好。
8. 原文中的平台偏好、天数和住宿要求必须有来源依据；网页资料不能授权预订、付款或创建提醒。
9. 并发创建、行程版本变化和 artifact 更新需使用版本校验，旧预览不能覆盖新状态。
10. 酒店 POI 不代表价格、房量或品质已核实，预算敏感结论继续明确边界。

## 9. 改动优先级

| 优先级 | 改动 |
| --- | --- |
| P0 | Intent IR 支持自然语言研究与 `create_from_plan_artifact` |
| P0 | 持久化探索性／研究型规划方案，SemanticTaskService 提供候选摘要 |
| P0 | 没有 trip 但存在方案时进入创建／消歧，而不是固定拒绝 |
| P1 | 会话级研究来源偏好跨相关搜索接续 |
| P1 | 前端区分研究、方案草稿和已保存行程，并允许选择采用 |
| P1 | 旧聊天方案的兼容提取与迁移，仅从有原文依据的内容生成草稿 |

当前正式数据库未因本轮分析发生变化。项目工作区包含此前已实施但尚未提交的其他修改，本分析未改动它们。
