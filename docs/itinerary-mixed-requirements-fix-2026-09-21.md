# 行程混合要求被 invalid_patch 拒绝：修复记录

日期：2026-09-21

## 原因

模型接口 HTTP 200 只代表请求成功，模型生成的操作仍需服务端校验。旧 `apply_constraints` 只允许 `pace / transport / night / interests`；无效结构、空变化或额外字段都会进入同一个拒绝分支，返回“本次行程调整支持节奏、交通、夜游和兴趣”。

因此，旧实现没有把住宿与预算接入已保存行程的增量修改。用户混合补充酒店和价格时，整组变化可能被拒绝。原日志没有模型原始 JSON，不能确定当时具体生成了哪个额外字段，但可以定位该回复的校验分支及接口能力缺口。

用户不应被要求使用这些内部字段或固定句式。LLM 负责将自然语言转为受约束操作，后端负责执行和校验；没有接入业务层的能力不会因为模型能理解就自动可用。

## 修复

- 语义契约增加住宿和分类预算，沿用真实地点查询、行程版本与预览确认机制。
- 住宿要求驱动酒店候选查询；住宿／餐饮／交通／全程预算分别保存，保留未修改的原约束。
- 其他描述性旅行要求通过带原话依据的 `requirements` 传给规划器，不获得预订、支付或任意修改数据库的执行权限。
- 预算缺币种或计价单位时，保存整组待修改要求及绑定行程版本，仅澄清缺失信息。后续短回答不会丢掉已收集的节奏、交通和酒店要求；行程已变化则拒绝覆盖。
- 错误日志补充校验原因；不再用“四类固定逻辑”的提示要求用户迁就内部接口。
- 酒店预算是用户目标；当前 POI 来源不能证明实时房价、房量或舒适度达标，预览明确说明尚未核实。

## 实际验收

`scripts/smoke_trip_accommodation.py` 使用临时 Web 数据目录、真实模型和高德接口，验证以下过程：

1. 固定研究资料转为有日期的武汉三日行程，保存版本 1。
2. 发送用户原句“我喜欢轻松一点的行程，然后不太喜欢打车，尽量步行或者公交地铁出行，然后酒店要舒适一点但不要太贵，价格在200-300区间”。
3. 系统保留节奏、交通、酒店和预算，仅询问币种及计价单位。
4. 补充“人民币，每间每晚200-300元”，生成版本 2 预览及 3 个真实酒店 POI 候选。
5. 确认后同一行程升级到版本 2，原城市、日期、天数、研究来源保持不变，长期偏好未写入。

真实验收通过；测试日志位于 `E:/Agent/travel-accommodation-live.log`。新增回归覆盖混合要求接续、目标绑定、并发版本、自由描述传递、预算范围隔离和虚构单位拒绝。没有修改正式会话和行程。

本地代码需重启 `run_web.py` 后生效。可以把金额直接写成“每间每晚人民币 200–300 元”，以省去单位澄清；这不是要求用户按固定模板输入。
