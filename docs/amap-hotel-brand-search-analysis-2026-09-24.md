# 连锁酒店要求未命中汉庭／如家：高德检索链路分析

日期：2026-09-24

范围：依据用户实际开封会话的只读数据库记录、当前 TripPlanner 和 AmapClient 代码，以及使用项目现有高德 Web 服务 Key 进行的只读关键词／分页查询。本轮未修改业务代码或正式行程。

## 1. 结论

本次主要不是高德没有汉庭、如家，而是当前 Agent 没有将品牌要求用于高德检索。

用户要求已经保存到：

```text
酒店要求汉庭酒店、如家酒店这些连锁酒店，要求酒店环境好，评分高
```

但地点收集阶段只执行：

```python
search_places('开封', '酒店')
```

没有执行：

```python
search_places('开封', '汉庭酒店')
search_places('开封', '如家酒店')
```

通用“酒店”查询当前只取第一页前 5 条，所以候选池只有双宇商务主题酒店、轩雅快捷酒店、站前宾馆等。模型被强制只能从有高德 POI 依据的候选 ID 中选择，不能凭用户原话编造汉庭或如家，因此最终只能推荐这些通用候选。

## 2. 代码路径

`agents/trip_planner.py` 的住宿候选收集逻辑为：

```python
extra = ['酒店'] if hotel_requested else []
keywords = [..., *extra, ..., '博物馆', '风景名胜', '公园']
```

`accommodation_text` 虽然保存了品牌、环境和评分要求，但没有参与搜索关键词生成。

`infrastructure/amap_client.py` 当前地点查询参数为：

```python
{
  'city': city,
  'keywords': keywords,
  'citylimit': 'true',
  'offset': 5,
  'page': 1,
  'extensions': 'base'
}
```

关键限制：

- 只有第 1 页；
- 每页只请求 5 条；
- 使用宽泛的“酒店”关键词；
- `extensions=base` 不读取酒店评分等扩展字段；
- 解析器只保留 `id/name/address/location/type/tel`；
- 规划模型最多选择 3 个 `hotel_ids`，且这些 ID 必须已经在候选集合中。

因此模型理解“汉庭／如家”并不代表执行层真的检索了这些品牌。

## 4. 评分与价格能力

将同一查询改为 `extensions=all` 后，高德返回 `biz_ext.rating`：

| 汉庭门店示例 | 高德返回评分 |
| --- | ---: |
| 开封汴西湖宋城路站店 | 4.7 |
| 开封河南大学大梁路店 | 4.6 |
| 开封清明上河园店 | 4.3 |
| 开封大学店 | 4.7 |
| 开封清明上河园西司夜市店 | 4.5 |

但本次 `cost` 和 `lowest_price` 都为空。评分是高德 POI 扩展数据，不保证和高德 App 当前展示完全一致，也不能直接证明房间环境、实时房量或用户评价内容。

当前代码使用 `extensions=base`，即使接口有评分也不会返回；即使改为 `all`，当前解析器也会丢弃 `biz_ext` 字典。

## 5. 当前 API 能否获取高德地图显示的所有酒店

不能保证“获取所有”。高德 Web 服务文本搜索是分页、排序后的 POI 检索接口，不是高德 App 酒店数据的完整导出接口。

可通过增加 `offset`、翻页和品牌／类型关键词取得更多候选，但仍存在边界：

- 结果取决于关键词、城市、分类和排序；
- `citylimit=true` 可能包含整个地级行政区的区县；
- 高德 App 可能结合地图视野、用户位置、周边搜索、个性化排序或其他酒店业务数据；
- 暂停营业、重复名称、住宿相关 POI 和行政区外相近结果需要过滤；
- API 返回数量和数据覆盖不构成“所有门店”的完整性承诺；
- 价格、房型、库存和实时活动通常需要酒店预订平台或对应开放接口核验。

因此合理目标应是“获得足够完整且与要求匹配的候选集”，而不是宣称同步高德地图上全部酒店。

## 6. 推荐解决方案

### P0：让品牌要求进入搜索关键词

将住宿要求结构化为：

```json
{
  "requested": true,
  "preferred_brands": ["汉庭", "如家"],
  "brand_mode": "required",
  "quality": "环境好",
  "minimum_rating": null
}
```

搜索顺序：

1. `汉庭酒店`
2. `如家酒店`
3. 用户说“这些连锁酒店”且允许相似品牌时，再补充“经济型连锁酒店”或品牌集团别名
4. 只有用户表达“优先／比如”而非硬性要求时，品牌结果不足才回退普通“酒店”

用户说“要求汉庭、如家”时，应采用严格模式。若没有品牌结果，明确说明未找到，不应静默改推无关独立酒店。

### P0：扩大并分页候选池

- 每次品牌查询请求 10–20 条；
- 至少查询 1–2 页，设置总候选上限；
- 按 POI ID 去重；
- 过滤名称含“暂停营业”等状态；
- 记录实际查询关键词、页数和检索时间，便于解释。

不建议无上限翻页，会增加配额、延迟和 QPS 风险。本次第一次密集验证就触发了高德 `10021 CUQPS_HAS_EXCEEDED_THE_LIMIT`，按 1.1 秒间隔后才稳定完成。

### P1：读取评分和行政区

使用 `extensions=all`，解析并保存：

- `biz_ext.rating`
- `biz_ext.cost`
- `biz_ext.lowest_price`
- `adname`
- `business_area`

评分需做可选字段处理，不能因为缺失而伪造。价格为空时继续显示“实时价格未知”。用户只说“评分高”但没有阈值时，可以优先排序；若要硬筛选，需追问最低评分，例如 4.5 分。

### P1：按行程位置排序

品牌搜索结果可能遍布开封市及下辖县。建议：

- 优先保留主城区，或让用户指定住宿区域；
- 用行程景点坐标计算酒店到每日核心景点的距离；
- 以品牌匹配为第一优先级，评分和到景点的综合距离作为后续排序；
- 不使用未核实的价格参与排序。

示例排序条件：

```text
品牌严格匹配
→ 排除暂停营业
→ 主城区／用户指定区域
→ 评分降序
→ 到行程核心景点的平均距离升序
```

### P1：品牌集团与别名

“华住会旗下”不只等于汉庭，还可能包括全季、桔子、星程、海友等；“如家旗下”可能包括如家、如家商旅、如家精选、和颐等。建议用项目内可维护配置描述品牌集团和搜索别名，不让模型临时猜测完整品牌清单。

用户明确只要汉庭／如家时，只查这些品牌；用户说“华住会或如家旗下类似连锁”时，才扩展集团候选。

## 7. 验收建议

1. 原句“酒店要求汉庭酒店、如家酒店这些连锁酒店”必须实际产生品牌查询，不得只有通用“酒店”。
2. 候选中至少包含接口实际返回的汉庭／如家门店；严格模式下不得选择无关独立酒店。
3. 通用酒店、品牌酒店和品牌集团三种模式分别测试。
4. 分页、去重、QPS 重试和缓存有上限。
5. 评分缺失、价格缺失、暂停营业和郊县门店正确处理。
6. 模型只能从服务端过滤后的候选中选择，不能编造品牌、评分或房价。
7. 最终回复显示查询依据和局限：POI／评分参考时间、实时价格与库存未知。

本轮仅进行了分析和只读高德查询，没有修改代码、正式行程或候选草稿，也没有启动 `run_web.py`。
