# 酒店与餐饮候选整体优化方案

日期：2026-09-24  
状态：已审核并实施；验证与交付结果见 `hotel-dining-recommendation-delivery-2026-09-24.md`  
适用：QQ 与 Web 共用的行程服务  
关系：本方案整合并替代酒店专项方案作为后续实施依据，原文档保留供追溯。

## 1. 目标与现状

目标：Agent 能理解用户自然语言中的住宿和餐饮要求，结合已有行程、品牌、评分、预算、交通方式生成有依据的候选。没有合适结果时，说明具体缺口并提供可比较的替代选择。

当前代码核查结果：

- `agents/trip_planner.py::collect_places` 仅分别增加“酒店”“餐馆”关键词。
- `infrastructure/amap_client.py::search_places` 固定使用文本搜索、第一页、5 条、`extensions=base`；没有保留评分及消费字段。
- `validate_plan` 中 `hotel_ids` 和 `restaurant_ids` 都是全程最多 3 个 ID，餐厅没有绑定日期和餐次。
- `core/trip_updates.py` 支持住宿文字和 `food` 预算，但没有独立的结构化餐饮要求；一次 `changes` 只有一个 `budget` 对象，不能完整表达同一条消息里的住宿和餐饮两种预算。
- `services/trip_service.py` 只输出名称和地址，没有每日距离、评分、预算匹配原因。
- 当前指定某天修改的校验会要求酒店、餐厅候选保持原样，需要改成按受影响范围更新，否则“只换第二天午餐”会被拦截。

酒店的品牌检索、评分能力已有前轮真实接口验证；餐饮评分、参考消费、营业时间字段的覆盖率尚未实测，本方案不承诺这些字段必然存在。

## 2. 酒店与餐饮的共同点和区别

| 维度 | 酒店 | 餐饮 |
| --- | --- | --- |
| 服务范围 | 默认一家酒店兼顾全程 | 按天、按餐次或指定景点附近推荐 |
| 检索要求 | 品牌、集团、连锁、区域 | 菜系、当地特色、具体菜品、品牌、商圈 |
| 位置目标 | 兼顾每天景点，避免某天过远 | 靠近用餐前后景点，尽量少绕路 |
| 预算单位 | 每间每晚，或明确的住宿总额 | 每人每餐、每人每天、整桌或全程餐费 |
| 质量参考 | 高德评分及用户明确要求 | 高德评分及菜系匹配；评分不等于口味保证 |
| 额外约束 | 入住日期、房间数等按需要补齐 | 忌口、过敏、饮食禁忌、餐次、营业时段 |
| 输出数量 | 默认最多 3 家供比较 | 每餐 1 家主选、最多 2 家备选；简单咨询仍给简短清单 |

共享 POI 检索、证据保存、限流和结果解释；酒店与餐饮使用不同的距离评估和预算规则。不建立复杂的通用推荐框架。

## 3. 产品规则与默认值

### 3.1 品牌与类别

- “只要汉庭或者如家”：指定品牌硬约束，不用其他品牌替代。
- “汉庭、如家等连锁酒店”：要求连锁，汉庭、如家优先，可扩展已知其他连锁。
- “华住会旗下”：使用可维护、注明核验时间的集团品牌配置；不让模型猜测完整集团清单。
- “吃开封当地特色”：按当地菜系及特色品类检索，不自动解释为必须连锁或必须网红店。
- “第二天吃某品牌”：只作用于第二天对应餐次；不替换全程餐饮要求。
- 品牌或菜品词可由 LLM 从用户语义及旅行背景产生，但酒店归属、菜品供应等事实必须来自证据。名称匹配不能证明门店官方授权或当前菜单。

### 3.2 评分

酒店沿用用户明确要求：

- 用户要求“好一点”“评分高”等且没有既有明确评分时，默认使用高德评分 **≥4.7**。
- 用户明确给出评分时优先采用；例如 4.5、4.8。已有用户明确评分不能被后续泛化表述“好一点”无声覆盖。
- 未要求高评分时，不给所有酒店强加 4.7 门槛。

餐饮新增建议，供本次审核：

- 用户要求“评分高”“评价好”但没有指定分数时，建议默认高德评分 **≥4.5**。
- 4.5 是拟定的产品规则，不是高德官方标准，也不是餐饮实测结论；单独配置，不复用酒店 4.7。
- 用户明确“餐厅也要 4.7 以上”时使用 4.7。
- 仅说“当地特色”“好吃的”时，以菜系匹配和已有评分排序，不推断必须达到某个分数。

两类共同规则：

- 标明评分平台；不混用高德、大众点评、携程等平台分数。
- 评分缺失不当作 0 分，也不当作符合门槛。
- 默认门槛用于首选筛选；不足时允许展示低于默认门槛的“放宽标准备选”，必须标明差异，不能改写用户条件。
- “必须 ≥4.8”属于硬约束，不自动放宽。可解释放宽后可能有哪些选择，但不能把不合格对象列为满足要求的主选。
- “尽量 ≥4.8”是优先条件，可有明确标注的备选。
- 评分只作为比较依据，不声称证明酒店环境、食品卫生或口味。

### 3.3 预算与距离

- 继承用户已有预算及单位；单位不明且影响比较时，只补问该项，不重新问城市和天数。
- “近一点”表示优先缩短距离，不擅自设为“必须 1 公里内”。用户明确 1 公里或步行 15 分钟等条件时才硬筛选。
- 默认酒店全程一家；餐饮默认按日匹配，通常避免反复推荐同一家。用户明确指定的餐厅可重复。
- 只修改酒店或餐厅，不更改已确定景点。餐饮候选作为行程附属内容，不占用每日主要活动数量。

## 4. 语义解析与约束保存

处理流程：

```text
当前消息 + 当前会话的行程/待确认草稿
→ LLM 识别本轮增量要求及原话依据
→ 服务端校验字段、数值、适用日期和单位
→ 合并已有约束，应用有来源标记的默认规则
→ 查询真实候选并计算距离
→ 服务端判定匹配情况和排序
→ 生成有证据的推荐预览
→ 沿用现有确认流程保存行程变更
```

不使用固定整句关键词触发作为主要入口。解析失败时保留旧行程和已理解条件，指出具体缺失信息。

建议在现有 `spec` 中增加 `hotel_preferences`、`dining_preferences`，保留原话字段并记录每项值的来源。最小字段包括：

| 酒店 | 餐饮 | 公共元信息 |
| --- | --- | --- |
| 品牌/集团、是否连锁 | 菜系、特色品类、指定餐厅/品牌 | 原话、显式/默认来源、硬性/优先 |
| 评分门槛 | 评分门槛 | 本轮适用范围和清除/替换动作 |
| 靠近全程景点、距离限制 | 就近/顺路、距离限制 | 预算及其单位、币种 |
| 全程一家 | 日期、早餐/午餐/晚餐、忌口 | 查询与核验时间 |

预算表达需同时支持住宿与餐饮：保留旧 `changes.budget` 兼容路径，新增按类别组织的 `changes.budgets`；同一请求不允许两条路径对同一类别给出冲突值。保存到现有 `spec.budgets.accommodation` 和 `spec.budgets.food`。

例如“酒店每间每晚 300 以内，吃饭每人每餐 60 以内，第二天午餐不要辣”，应一次保留两项预算，并只覆盖第二天午餐的口味要求。

## 5. 候选检索与证据

### 5.1 共用查询能力

- POI 文本检索支持类型、页数、每页条数及扩展字段；普通地点查询保留原兼容默认值。
- 酒店/餐饮专用请求建议每页 20 条、每个查询最多 2 页、单类最多 6 次查询、去重后最多 100 个候选。达到上限即说明范围有限，不能宣称全城没有结果。
- 先查询指定品牌/菜系和相关区域，结果不足再扩展；不用通用结果第一页代表全城酒店或餐馆。
- 支持高德周边检索用于景点附近餐厅；在当前 Key 权限和接口实测通过后启用。不可用时使用区域关键词检索并按坐标排序，标明覆盖局限。
- 查询采用类型过滤并二次验证，避免停车场、酒店附属设施、非餐饮 POI 混入。
- 按 POI ID 去重；不同门店不因同名而合并。
- 返回可用的 `rating`、`cost`、位置、行政区、商圈、来源和查询时间；营业时段等额外字段仅在接口实际支持且返回时保存。
- 基础营业状态未知不能写成“正常营业”；仅排除有明确暂停营业等证据的候选。

### 5.2 酒店检索

指定品牌分别查询；无品牌时按酒店类型及行程景点区域查询。品牌酒店也可能在下辖县，不按城市名称直接认定位置合适。

### 5.3 餐饮检索

综合菜系、当地特色、用户指定品牌和每日用餐区域生成查询。例如“开封特色、不要辣、午餐顺路”，先围绕上午终点与下午起点附近查询，再利用真实类型/菜单证据验证相关性。

“清淡”“素食”“无花生”等不能仅凭餐馆名字认定。可明确验证的冲突候选排除，未知条件作为待核实项。严重过敏或明确饮食禁忌不得自动放宽，也不能把缺乏配料证据的餐厅称为安全选择。

## 6. 酒店位置评估

1. 根据酒店和全部每日景点坐标计算直线距离，统计每日平均和最远距离，先筛出有限候选。
2. 全程平均近，但某一天特别远的酒店需要降级；尽量均衡各天。
3. 对头部候选按已有交通偏好核验“酒店到当天首个景点”和“当天最后景点回酒店”。返程单独计算，不能简单将去程乘二。
4. 展示直线距离与路线距离/时间的不同含义；不把直线 1 公里写成步行 1 公里。
5. 没有交通偏好时先显示直线距离，不擅自采用打车时间。交通失败或部分日期缺失时标记未知，不按零时间排第一。
6. 用户要求“每个景点都近”时，仍展示所有景点的最远距离；首尾通勤不能代替中间景点的距离核验。

休整日没有景点时不参与距离均值，也不假定酒店距离为零。已有三天行程不等于已知住两晚或三晚；计算总房费必须有实际入住、离店及房间数。

## 7. 餐饮位置与餐次评估

餐饮不使用“到三天所有景点的平均距离”，应按每餐所在位置匹配：

- 早餐：有住宿候选或已选酒店时参考住宿区域；没有早餐需求时不自动添加。
- 午餐：参考当天上午最后一个景点、下午第一个景点。
- 晚餐：参考下午/晚间景点；只有用户已选定酒店或明确住宿区域时，才考虑返程顺路，不能擅自选用第一个酒店候选作为住宿事实。
- 用户只说“推荐一些当地餐厅”，给区域化简短候选即可，不自动填满每天三餐。

先按坐标粗排；对少量主选候选核验真实路线。可比较额外绕行：

```text
额外绕行时间 = 前一景点 → 餐厅 → 后一景点的时间
             − 前一景点 → 后一景点的时间
```

三段必须使用相同交通方式及可比查询条件。数据缺失时只展示已知路线；没有后一景点时评估单程距离，不虚构“绕行时间”。用餐停留时间和未知排队时间不包含在通行时间中。

如果只有“上午/下午”安排，不能推断准确到店时间。营业时段有证据时可筛掉明确冲突项；未知或不具备精确到店时间时标为“营业时段待确认”，不承诺一定开门或有座位。

建议新增 `plan.dining_options`，每项关联 `day_index`、`meal`、主选/备选 POI 及证据。早餐/午餐/晚餐只是可选槽位，不要求全部填满。

旧 `restaurant_ids` 保留为兼容摘要，原有最多 3 家的展示不再作为新餐次列表的全程容量限制；新旧字段采用单一来源生成，避免两份候选互相矛盾。酒店仍默认最多展示 3 家。

## 8. 预算与匹配状态

预算数值由原话解析并校验，保留币种、上下限、计价单位、人数/房间数等已知信息。区分“硬上限”“目标区间”“左右”，不能把所有区间都视为不可突破的上下限。

| 数据 | 可以得出的结论 | 不能得出的结论 |
| --- | --- | --- |
| 高德酒店 POI/评分 | 位置、品牌线索、平台评分 | 指定入住日期房价和库存 |
| 酒店参考最低价 | 参考价格线索 | 实时每间每晚可订价格 |
| 餐厅参考消费，已确认单位为人均 | 参考人均与预算大致比较 | 实际账单保证不超预算 |
| 消费字段单位未确认 | 保留原始值待核实 | 自动当作人均/房费 |
| 有日期、房型等条件匹配的可靠报价 | 该报价时点下的预算比较 | 永久锁价或库存保证 |

餐饮日预算不能直接拿来与每餐人均比较。用户给出每天 150 元时，按已知餐次提供可见的分配建议，不能默认三餐均分后声称符合要求。多人合计、住宿总额同样只在必要参数明确时计算。

结果分为三个层次：

1. **满足已核验条件**：所有适用硬条件有相符证据；有预算要求时价格证据也必须与单位和范围匹配。
2. **部分条件待核实**：位置/品牌/评分合适，但房价、配料、营业时段等必要条件缺乏证据。
3. **需要放宽条件的备选**：已知低于默认评分、超过参考预算或更远，逐项写明差异。

未知价格不能进入“已确认预算内”分组。过敏、明确饮食禁忌、用户明确拒绝的品牌等不自动放宽。

严格要求没有结果时，可以如实返回没有主选；次优清单也必须有真实候选，不能为凑数生成商家。措辞使用“本次检索范围内未找到”，接口失败时使用“查询未完成”，不能说成当地没有。

## 9. 排序规则

先执行硬约束和证据分组，再在组内比较，不用一个总分掩盖预算超额或忌口冲突。

酒店：用户明确优先级 → 偏好品牌 → 已知预算匹配程度 → 最远一天距离/通勤 → 平均距离/通勤 → 高德评分。

餐饮：用户明确优先级 → 菜系/特色匹配 → 参考人均预算匹配 → 当餐绕行/距离 → 高德评分 → 行程内适度去重。

用户“离景点近最重要”时，距离优先于软品牌或菜系偏好，但不能突破其明确硬约束。不同候选路线证据不齐时用相同可比较的距离指标，不能拿一家直线距离与另一家公交分钟直接比较。

结果应解释两到三个主要原因，例如“符合连锁要求、达到 4.7、三天位置较均衡；房价待核验”，避免未经证据支持的“性价比最高”“当地人都去”。

## 10. 缓存、延迟与更新范围

- 沿用现有高德限速、限次重试；酒店与餐饮共享请求调度，缓存键必须包含类型、区域、分页、扩展字段与交通方式等实际参数。
- 酒店和餐饮合计，每次推荐最多增加 12 次路线请求（包含餐饮基准路线），复用已有路线证据；这属于初版配置建议。
- 三天 × 3 家酒店 × 每天往返已经需要 18 段查询，不能承诺所有候选都核验。按候选完整性依次核验，预算耗尽后其余展示直线距离和未核验标记。
- 对较长行程或许多餐次按需补充；失败不无限重试，也不重复发送同一检索。
- 缓存按现有短期策略起步；路线保存查询时间，展示“当前路线参考”，不作为未来某天的保证。
- 评分/预算改变时复用有效候选并重新筛选；景点变化时仅重算受影响日餐饮，以及酒店全程距离汇总。
- 只改餐饮不重选酒店，只改酒店不重排景点。确认更换住宿位置后，仅重算受影响的早餐/返程相关餐饮。

## 11. 展示方案与前后端

先复用现有 Markdown 消息展示，不新增复杂页面。Web 与 QQ 共用同一筛选服务和格式化事实；Web 可用小标题和简短条目展示，避免宽表格在窄屏溢出。

示例仅表示展示结构，名称和数值不是本轮真实查询：

```text
住宿候选
筛选：汉庭/如家优先，连锁酒店；高德 ≥4.7；200～300 元/间/晚。

候选 A
高德评分：4.8；三天位置较均衡。
第 1 天往返：公交约 30 分钟；第 2/3 天：路线待核验。
价格：尚未取得指定日期房价，预算是否满足待核验。

第 2 天 · 午餐
候选 B｜当地菜
高德评分：4.6；参考人均：约 55 元（非实际账单）。
距上午景点直线约 800 米；符合每人每餐 60 元的参考预算。
口味要求：不辣能否制作待商家确认。
备选 C：位置更近，但参考人均约 70 元，比预算高约 10 元。
```

在行程日下展示当天餐饮主选；详细备选按用户请求展开，避免默认输出三天九餐的大量列表。候选不等于已经订房、订座或用户已选定商家。

## 12. 实施模块与技术栈

保持现有 Python 服务、LLM JSON 意图解析、高德 HTTP API、SQLite 行程存储、React/TypeScript Web 与 QQ 适配器。无需新增向量数据库、独立推荐服务或 Docker 改动。

| 模块 | 改动 |
| --- | --- |
| `agents/intent_compiler.py`、`core/intent_ir.py` | 支持住宿/餐饮增量条件、日/餐次范围、两类预算同时表达；原话与字段校验同步升级 |
| `core/trip_updates.py` | 默认评分、继承/覆盖/清除、硬性与偏好、预算单位及范围验证 |
| `services/semantic_task_service.py` | 向解析器提供新条件和当前草稿，保持多轮上下文；仅追问缺失项 |
| `agents/trip_planner.py` | 搜索策略、已有景点保留、餐次关联；取消新餐次列表的全程三家限制 |
| 小型候选筛选模块（按代码规模决定是否拆出） | 纯函数处理坐标距离、约束判定、解释和稳定排序，便于独立测试 |
| `infrastructure/amap_client.py` | 可控分页、类型/周边检索、扩展字段解析、缓存及共享限流 |
| `services/trip_service.py` | 餐饮/住宿专属更新路径、预览与结果格式、事务保存 |
| 行程/草稿仓储、`services/planning_service.py` | 保存新字段和依据，兼容旧记录，草稿复用链路不得丢失条件 |
| Web 消息展示与已有回归测试 | 验证 Markdown 层级、手机宽度；只有必要时改样式 |

新行程字段使用可选值和版本标识，旧记录只读时保持原样；用户请求重新推荐时才补充证据。普通自由文本方案缺少唯一 POI/逐日结构时，先恢复结构并消歧；不能假定文字草稿天然有坐标，也不能凭描述计算距离。

如餐饮只是对原用餐活动补充商家，不重复新增主要活动。更新沿用现有版本检查、草稿确认及原子保存，旧提醒、预约关联只有其真实依赖发生变化才处理。

## 13. 分阶段交付

### P0：需求真正进入检索和筛选

- 酒店、餐饮语义与预算同时解析，增量继承。
- 酒店 4.7 默认和餐饮拟议 4.5 默认、用户显式阈值覆盖。
- 品牌/菜系/区域检索、有限分页、评分与参考消费解析。
- 真实候选校验、硬约束过滤、未知与未匹配原因展示。
- 酒店或餐饮修改不重新规划原景点。

验收：汉庭/如家要求产生相应搜索；当地菜要求不再只搜“餐馆”；评分/价格缺失不被当作达标。

### P1：根据行程位置推荐并完整展示

- 酒店全程距离、餐饮逐日逐餐位置、有限路线核验。
- 餐饮新结构、日预算处理、次优候选解释。
- 景点/预算/住宿变化后的按需重算。
- 草稿与已保存行程上下文、持久化、QQ/Web 展示兼容。

验收：三天行程的酒店兼顾三天；“只改第二天午餐”只更新该餐；超预算/评分不足/未知数据均明确标注。

本次范围不包括酒店实时预订价格接口、餐厅实时排队或菜单接口、支付订房订座、自动多酒店拆分住宿。为未来接入价格源保留证据字段即可，不预建未使用的适配体系。

## 14. 测试与最终验收

| 场景 | 预期 |
| --- | --- |
| “酒店好一点” | 酒店默认 ≥4.7，标明默认来源 |
| “酒店至少 4.5”之后“离景点近一点” | 保留用户明确 4.5，不回退默认 4.7 |
| “餐厅评价高些”“餐厅也至少 4.7” | 分别应用审核后的餐饮默认值、用户指定值 |
| 汉庭/如家严格与举例表达 | 区分品牌硬约束和品牌优先，不无声换成独立酒店 |
| 同轮住宿 300/晚、餐饮 60/人/餐 | 两项预算均保存，不互相覆盖 |
| 每人每天餐饮 150 | 不直接当作每餐 150，不隐式均分后承诺达标 |
| 一家酒店前两天近、第三天极远 | 排名体现最差一天，不能仅按全程平均掩盖 |
| 第二天午餐川菜改为清淡当地菜 | 只重选第二天午餐，其他餐、酒店、景点保留 |
| 移动第二天景点 | 重算相关餐饮与酒店距离，避免复用旧位置结果 |
| 评分/坐标/价格/菜单/营业时间缺失 | 显示未知；不伪造、不按零值获得优先排名 |
| 严重过敏与菜品信息不全 | 不声称餐厅满足过敏要求，不自动解除限制 |
| 无完全匹配或接口失败 | 区分未匹配、待核实、查询未完成；不承诺全城无结果 |
| 高德数组/空字符串/异常数值、限流 | 健壮解析、有界重试，旧行程不损坏 |
| 旧版三家餐厅记录、新餐次记录 | 均可读取，餐次列表不受旧容量规则错误拦截 |
| 待确认草稿连续补充品牌、评分、忌口 | 新旧条件完整保留，确认前不改写正式版本 |

自动化测试使用模拟 POI/路线覆盖边界与真实业务结果；另做小规模只读接口验证，记录餐饮字段实际覆盖和当前 Key 能力。不在正式会话写入测试数据。

对语义解析增加多种自然表达评估，避免仅用固定句式通过测试。对排名记录匹配依据、查询数量、缺失原因，不记录密钥。运行相应行程、上下文、Web/QQ 回归；如启动测试 Web 服务，结束后关闭本次启动的进程并核验端口释放。

## 15. 审核要点

1. 酒店默认评分继续采用已提出的 ≥4.7；餐饮高评分需求建议采用独立默认 ≥4.5，用户明确数值优先。
2. 酒店为全程候选，餐饮按实际请求关联日期/餐次；候选不自动转为已选商家。
3. 预算未知与不达标分开解释；参考人均只用于估算，不承诺实际账单。
4. 次优方案明确哪些条件需要放宽；不暗改品牌硬约束、过敏/禁忌和其他明确限制。
5. P0 与 P1 覆盖整个请求到执行再到展示的链路，而非只修改提示词。
