# 景点天数校验误拒绝修复

日期：2026-10-19  
状态：已修复，123 项相关回归通过。

## 实测日志确认

原会话的请求 #98 再次发送北京景点票价、开放时间和预约规则查询后，在 2026-10-19 11:34 左右返回“景点对应的游览天数与原方案不一致，尚未搜索”。

日志表明：

- 研究意图已通过，方案解析为 `unique_plan`。
- 原自我介绍草稿已经失效，北京方案已经修正为三天；本次没有重新选中错误方案。
- `intent_parse` 与 `research_targets` 模型调用均正常结束，`finish_reason=stop`。
- 失败发生在 `research_targets-v1` 的输出校验，搜索尚未开始，没有产生研究检查点。
- 当时没有持久化模型的景点输出原文，因此不能断言具体哪个景点或哪段引文触发了拒绝。

这是上一轮新增校验的实现问题。提示中的“不一致”是内部提取结果校验失败，不足以证明用户提供的旅行日期或原方案确实矛盾。

## 根因

旧代码用任意“第几天”字样切分正文，再要求模型的整段 `source_text` 完整落在指定天数片段内。存在三个问题：

1. 切片从“第一天”开始，丢掉了前面的 `### `。合法引文 `### 第一天：天安门—故宫—景山—什刹海` 包含 Markdown 前缀，因此无法作为完整子串落入该切片。
2. 一段合法引用可以跨段甚至跨天标题；景点实际属于哪一天，应看景点出现的位置，不能要求整段引文只属于一天。
3. 正文提到其他天数会被当成新标题；最后一天还会吞进后续预算、预约准备等总结章节。模型天数提示与这样的切片一旦不一致，整个研究请求就失败。

旧专项主要使用简化纯文本行程，漏测了真实 Markdown 标题和完整引文；其中还把错误天数的整单拒绝当成预期。本次补充真实原方案的行程节选，保留“模型输出为构造回归输入、并非原日志恢复”的边界。

## 修改

### 按行程结构确定景点所在天数

`agents/research_search_planner.py`：

- 优先识别真正的 Markdown 逐日标题，遇到同级/更高层级标题结束当前章节，不让“预算参考”“预约与准备”归入最后一天。
- 没有 Markdown 逐日标题时，兼容纯文本、英文 Day 标题及同一行的逐日安排。
- 普通正文中提到“第三天”不再直接切断已有 Markdown 行程；代码块和引用块中的示例不作为逐日证据。
- 根据合法引文中的**景点名称出现位置**映射到行程章节。引文带标题前缀或跨段不会被误拒绝。
- 总结处的引文没有日序证据时，再查该景点在实际逐日安排中的位置。
- 唯一定位时以原方案为准，自动纠正模型天数；无法唯一定位时设为 `null`，保留该景点继续研究。
- 模型提供的日序只用于判断是否发生纠正，不再单凭模型提示生成具体游览日。没有足够原文证据时，具体日期保持未知。
- 名称、引文连续性、参观方式、来源限制等原有校验继续保留；没有通过的景点不能靠放宽天数获得搜索授权。

### 研究继续执行，并说明未确定的日期

`services/research_service.py`：

- 已确定为第几天的景点，继续按游览开始日换算具体日期。
- 无法确定日序的景点仍查询票价、开放及预约信息，但不在外部查询中强行加入某个具体日期。
- 回复逐景点显示“第几天”或“游览日待确认”，事实的目标日期适用性继续按原规则核验。
- 记录景点总数、纠正天数数量 `day_corrected_count`、无法确定数量 `day_unresolved_count`，不记录任意引文或模型原文。

`infrastructure/execution_diagnostics.py` 同步允许以上诊断字段，提取提示词版本升级为 `research-targets-v2`。

没有因天数纠正增加模型调用，没有修改正式行程、提醒或历史聊天。
