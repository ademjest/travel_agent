# 酒店推荐检索、评分、距离与预算优化方案

日期：2026-09-24  
状态：待审核，尚未实施

## 1. 背景与问题

当前行程系统可以保存住宿要求和住宿预算，也能从高德获取酒店 POI，但酒店推荐仍存在以下问题：

1. 用户要求汉庭、如家等连锁酒店时，检索层仍只使用通用关键词“酒店”，品牌要求没有进入高德查询。
2. 通用酒店查询只获取第一页前 5 条，容易遗漏真实存在的品牌门店，并可能混入开封下辖县域的酒店。
3. 当前查询使用 `extensions=base`，没有读取高德评分、商圈和行政区信息。
4. 用户要求“好一点”“评分高”时，没有统一、可解释的默认评分标准。
5. 酒店候选没有根据三天行程景点的位置计算距离，模型只能凭酒店名称和地址选择。
6. 高德 POI 接口通常不能提供指定日期的可靠房价和库存，当前系统无法证明酒店符合住宿预算。
7. 找不到同时满足全部条件的酒店时，系统缺少“说明未满足条件并列出次优候选”的稳定降级逻辑。

本方案将酒店选择从“由模型在少量候选中自由挑选”调整为“LLM 理解要求，服务端检索、过滤、排序并提供证据”。

## 2. 目标与默认规则

### 2.1 目标

- 正确理解品牌、连锁类型、评分、预算和靠近每日行程等住宿要求。
- 酒店候选必须来自真实 POI 查询结果，不编造酒店、评分、距离或房价。
- 已有行程只调整酒店时，不重新生成或改变每日景点安排。
- 优先推荐同时满足品牌、评分、距离和预算证据的酒店。
- 没有完全匹配项时，明确说明未满足的条件，并列出相对合适的酒店。

### 2.2 产品默认值

1. 用户说“好一点的酒店”“评分高的酒店”“环境和评价好一些”，但没有给出具体评分时：
   - 默认最低高德评分为 **4.7 分**；
   - 评分来源必须标明为高德 POI 评分；
   - 评分缺失的酒店不能视为满足 4.7 分要求。
2. 用户明确指定评分时，以用户要求为准：
   - “4.5 分以上”使用 4.5；
   - “必须 4.8 以上”作为硬约束；
   - “尽量 4.8 以上”作为优先条件，找不到时允许降级并说明。
3. 默认整个行程使用同一家酒店，避免每天搬运行李。只有用户明确要求分段住宿或每天换酒店时才改变这一规则。
4. “汉庭、如家等连锁酒店”默认理解为：必须是连锁酒店，汉庭和如家优先；“只要汉庭或如家”“必须是汉庭/如家”才限定为指定品牌硬约束。
5. “离每天景点近一点”“不要太远”默认要求酒店兼顾所有行程日，不能只靠近其中一天。

## 3. 需求结构化

继续保留用户原始住宿要求 `accommodation_text`，同时增加可校验的结构化字段。建议在行程 `spec` 中保存：

```json
{
  "hotel_requested": true,
  "accommodation_text": "酒店好一点，汉庭、如家等连锁酒店，离每天景点不要太远",
  "hotel_preferences": {
    "preferred_brands": ["汉庭", "如家"],
    "brand_mode": "preferred",
    "chain_mode": "required",
    "minimum_rating": 4.7,
    "rating_mode": "required",
    "rating_origin": "default_high_quality",
    "near_itinerary": true,
    "same_hotel_for_trip": true
  },
  "budgets": {
    "accommodation": {
      "value": "200-300",
      "unit_text": "人民币每间每晚",
      "source": "价格在200-300区间"
    }
  }
}
```

字段含义：

- `preferred_brands`：用户明确提到的酒店品牌。
- `brand_mode`：`required` 表示只允许指定品牌，`preferred` 表示优先指定品牌。
- `chain_mode`：是否要求必须为连锁酒店。
- `minimum_rating`：明确评分，或由“好一点/评分高”应用的 4.7 默认值。
- `rating_mode`：评分是硬约束还是优先条件。
- `rating_origin`：区分用户明确指定与系统默认，便于回复解释。
- `near_itinerary`：是否需要根据已有行程计算住宿位置。
- `same_hotel_for_trip`：默认整个行程使用同一家酒店。

LLM 负责识别用户语义，服务端负责应用 4.7 默认值和字段校验。不得依赖固定整句字符匹配，也不让模型自行决定默认分数。

## 4. 意图理解与上下文规则

需要扩展住宿调整的语义编译规则，使以下表达都能形成统一的结构化变更：

| 用户表达 | 结构化结果 |
| --- | --- |
| 酒店好一点 | `minimum_rating=4.7`，来源为系统默认 |
| 推荐评分高的酒店 | `minimum_rating=4.7` |
| 酒店至少 4.5 分 | `minimum_rating=4.5`，来源为用户明确指定 |
| 尽量找 4.8 分以上 | `minimum_rating=4.8`，`rating_mode=preferred` |
| 只要汉庭或者如家 | 品牌为汉庭、如家，`brand_mode=required` |
| 汉庭、如家等连锁酒店 | 汉庭、如家优先，`chain_mode=required` |
| 离每天的景点近一点 | `near_itinerary=true` |
| 预算每晚 200 到 300 元 | 更新住宿预算及计价单位 |

上下文处理规则：

- 当前会话已有行程时，直接使用该行程的城市、天数、景点和交通偏好，不重新询问。
- 当前会话只有未保存的行程草稿时，使用草稿中的每日景点计算酒店距离。
- 用户只修改酒店要求时，只更新酒店候选及住宿约束，保持每天活动原样。
- 用户修改景点后，如果启用了 `near_itinerary`，自动重新计算酒店排序。
- 用户补充评分、品牌或预算时，应合并已有住宿条件，不能覆盖掉其他已知要求。

## 5. 高德酒店候选检索

### 5.1 查询策略

按照要求生成有限、可解释的搜索关键词：

1. 指定品牌：分别查询“汉庭酒店”“如家酒店”。
2. 连锁酒店：在允许扩展时查询配置中的连锁品牌别名，而不是让模型临时猜测品牌列表。
3. 无品牌但要求高评分：查询通用酒店候选，再按评分过滤和排序。
4. 品牌结果不足且 `brand_mode=preferred` 时，才扩展到其他连锁酒店。
5. `brand_mode=required` 时不得用无关酒店替代。

每个关键词建议：

- 每页 10～20 条；
- 查询 1～2 页；
- 按 POI ID 去重；
- 设置整体候选上限；
- 沿用当前至少约 1 秒的高德请求间隔和 `10021` 限流重试；
- 使用短期缓存，避免同一行程重复消耗配额。

### 5.2 返回字段

高德查询改为 `extensions=all`，解析并保存：

- `id`
- `name`
- `address`
- `location`
- `type`
- `tel`
- `adname`
- `business_area`
- `biz_ext.rating`
- `biz_ext.cost`
- `biz_ext.lowest_price`

其中评分、参考消费和最低价均为可选字段。字段缺失时保持未知，不得补造。

### 5.3 基础过滤

- 排除暂停营业、停车场、酒店附属设施等非酒店主体 POI。
- 根据名称、类型和品牌别名验证连锁及品牌匹配。
- 优先保留行程景点所在城区附近的酒店，用距离过滤掉兰考、尉氏等明显偏离行程的候选。
- 对名称相同但地址不同的门店保留不同 POI，不按名称直接合并。

## 6. 与每日行程的距离计算

### 6.1 第一阶段：坐标粗排

所有景点和酒店候选已有高德坐标。先在本地计算酒店到每天景点的直线距离，得到：

- 每天平均距离；
- 每天最远景点距离；
- 全行程平均距离；
- 全行程最远距离。

排序时同时考虑平均值和最差一天，避免酒店只靠近某一天、却离另一天非常远。此阶段不增加高德 API 请求。

### 6.2 第二阶段：路线核验

只对粗排后的前 3～5 家候选调用路线接口，避免三天行程乘以大量酒店导致延迟和限流。

每一天重点核验：

```text
酒店 → 当天第一个景点
当天最后一个景点 → 酒店
```

如果用户已有交通偏好：

- 优先公交/地铁：使用公共交通路线时间；
- 优先步行：仅在合理距离内使用步行时间，过远时按已有交通规则处理；
- 自驾：使用驾车路线时间；
- 未指定：先显示坐标距离，路线时间标记为未核验，或采用项目统一的默认交通方式。

最终记录每家酒店的每日往返时间、平均往返时间和最远一天往返时间。无法取得路线时保留候选，但明确标记路线未核验。

## 7. 评分筛选规则

候选按以下方式分组：

1. `minimum_rating` 为空：评分只用于排序，评分缺失的候选可以保留。
2. `rating_mode=required`：评分缺失或低于阈值的酒店不属于完全匹配项。
3. `rating_mode=preferred`：优先选择达到阈值的酒店，不足时允许列出较低评分候选。
4. 用户只说“好一点/评分高”时，应用默认 4.7 分，并在回复中说明这是默认筛选标准。
5. 用户明确评分时，不再应用 4.7 默认值。

如果当地没有查到 4.7 分以上且符合其他条件的酒店，应说明：

```text
本次没有查到同时满足连锁品牌、距离和高德评分 4.7 以上的酒店。
以下候选未完全达到评分要求，但在品牌和位置上相对合适。
```

不得静默将阈值从 4.7 降到 4.5。

## 8. 预算判断与价格真实性

### 8.1 当前能力边界

高德 POI 的 `cost` 和 `lowest_price` 经常为空，也不一定代表指定入住日期、房型和实时库存。仅依赖当前高德接口，无法可靠证明酒店每晚价格符合 200～300 元预算。

因此候选价格状态必须区分为：

- `verified_in_budget`：指定日期价格已经由可靠价格源核验，并在预算内；
- `verified_over_budget`：指定日期价格已经核验，但超过预算；
- `reference_price_only`：只有高德或其他来源的非实时参考价；
- `unknown`：没有可用价格证据。

在未接入酒店预订价格源前，主要会落入后两类。系统只能“尽量筛选”，不能宣称价格已经满足预算。

### 8.2 预算排序与降级

存在可靠价格时：

1. 优先预算内且满足品牌、评分和距离的酒店；
2. 没有完全匹配项时，说明是哪项条件未满足；
3. 列出最接近预算、位置相对合适的候选。

没有可靠价格时：

1. 不把未知价格当作预算内；
2. 先按品牌、评分和距离筛选；
3. 明确说明“当前接口未取得指定日期实时房价，无法确认是否在预算内”；
4. 展示可供用户去预订平台核验的候选，不声称当地没有预算内酒店。

如果用户没有提供入住日期，即使将来接入预订平台，也只能给参考价或要求补充日期，不能提供实时预算结论。

## 9. 确定性排序与结果分组

模型不直接决定最终酒店排名。服务端按已验证字段进行确定性分组和排序。

### 9.1 完全匹配组

必须满足所有硬约束：

- 指定品牌或连锁类型；
- 最低评分；
- 行程区域没有明显偏离；
- 有可靠价格时符合预算；
- 未暂停营业。

组内排序建议：

```text
品牌匹配程度
→ 预算状态
→ 最远一天通勤时间
→ 全行程平均通勤时间
→ 高德评分
```

“最远一天通勤时间”优先于平均时间，保证酒店对每一天都不过分偏远。

### 9.2 次优候选组

没有完全匹配项时，按缺失条件最少的顺序列出最多 3 家，并为每家标明：

- 满足了哪些条件；
- 未满足哪些条件；
- 高德评分；
- 每日或整体距离；
- 价格证据状态。

严格品牌要求下，次优候选仍应保持指定品牌；除非用户允许扩展，否则不能推荐无关独立酒店。

## 10. 回复格式

推荐结果至少应包含：

```text
住宿筛选条件：
- 连锁酒店；优先汉庭、如家
- 高德评分至少 4.7（因你要求“好一点”，使用默认标准）
- 兼顾三天行程位置
- 预算 200～300 元/间/晚

推荐 1：汉庭酒店（示例门店）
- 高德评分：4.7
- 第一天往返：约 xx 分钟
- 第二天往返：约 xx 分钟
- 第三天往返：约 xx 分钟
- 价格状态：未取得指定日期实时房价，预算符合性待核验
- 推荐原因：品牌匹配，三天最远通勤相对较短
```

没有完全匹配项时，先给出事实说明，再展示候选：

```text
本次没有查到同时满足“指定品牌、高德评分 4.7 以上、三天位置合适、已核验价格在预算内”的酒店。
主要原因是当前接口没有返回指定日期实时房价。以下酒店在品牌、评分和位置上相对合适，价格需要进一步核验。
```

## 11. 代码改动范围

### P0：语义和品牌检索

- `agents/intent_compiler.py`
  - 扩展住宿语义结构，识别品牌、连锁要求、评分和靠近行程。
- `core/trip_updates.py`
  - 校验并合并 `hotel_preferences`，应用“高品质但未指定评分时默认 4.7”的服务端规则。
- `agents/trip_planner.py`
  - 使用品牌和连锁要求生成酒店搜索关键词；不再只添加固定“酒店”。
- `infrastructure/amap_client.py`
  - 支持分页、可控条数和 `extensions=all`；解析评分、行政区和商圈字段。
- `services/trip_service.py`
  - 在结果中展示实际住宿筛选条件和数据限制。

### P1：距离、评分和预算降级

- `agents/trip_planner.py`
  - 增加本地坐标距离计算、候选过滤和确定性排序。
  - 对少量头部候选补充路线证据。
  - 用户只修改住宿时保持每日行程不变。
- `services/trip_service.py`
  - 展示完全匹配项、次优候选、每日距离和价格状态。
- 现有仓储层
  - 随行程保存酒店评分、距离依据、查询时间和价格证据状态，保证刷新后可解释。

不在本次范围内：

- 接入携程、美团、同程等酒店预订平台；
- 下单、锁价、房型和库存预订；
- 默认每天更换不同酒店。

## 12. 测试方案

### 12.1 意图与约束测试

1. “酒店好一点”得到默认最低评分 4.7。
2. “酒店至少 4.5 分”覆盖默认值。
3. “尽量 4.8 分以上”生成优先评分要求。
4. “只要汉庭或如家”生成严格品牌要求。
5. “汉庭、如家等连锁酒店”生成连锁硬约束和品牌优先项。
6. “离每天景点近一点”启用行程位置筛选。
7. 一句话同时包含品牌、评分、距离和预算时全部保留。
8. 多轮补充要求时不重新询问已有城市、日期和行程。

### 12.2 酒店候选测试

1. 品牌要求实际产生“汉庭酒店”“如家酒店”查询。
2. 严格品牌模式不得选择独立酒店。
3. 评分 4.6 的酒店不能进入 4.7 硬约束完全匹配组。
4. 评分缺失不能被当作达到 4.7。
5. 郊县酒店因明显偏离行程位置被降级或排除。
6. 同时考虑三天距离，不能只按第一天距离排序。
7. 无完全匹配项时返回有原因的次优候选，而不是返回空结果或无关酒店。
8. 没有价格证据时明确显示未知，不声称预算内。

### 12.3 回归测试

- 修改酒店要求不改变原有每日景点。
- 修改每日景点后重新计算酒店距离。
- 没有住宿要求时不额外查询酒店。
- 高德评分字段缺失、接口限流和路线查询失败时仍能给出诚实的降级结果。
- 原有 QQ 和 Web 两个入口得到一致的酒店筛选结果。

## 13. 验收标准

1. 用户要求汉庭、如家时，实际查询对应品牌，不能只查“酒店”。
2. 用户说“好一点/评分高”且未指定分数时，明确使用高德评分 4.7 作为默认标准。
3. 用户指定评分时，以用户值为准，不再应用默认 4.7。
4. 酒店推荐同时考虑所有行程日，并显示可理解的距离或通勤依据。
5. 只调整酒店时，三天行程景点保持不变。
6. 没有完全符合预算、评分、品牌和距离要求的酒店时，明确说明原因并列出最多 3 个次优候选。
7. 价格未知时不能声称符合预算，也不能误报“当地没有预算内酒店”。
8. 所有酒店、评分、位置和路线信息都有高德查询或其他明确数据来源，不由模型编造。
9. 查询数量有上限、缓存和限流控制，不因酒店筛选频繁触发高德 QPS 错误。

## 14. 实施顺序

1. 先完成 P0：结构化住宿要求、4.7 默认规则、品牌查询、评分字段解析。
